--- Beginner - Fundamentals ---
Beginner Fundamentals 1. What is PySpark and how is it different from Apache Spark?
Answer: PySpark is the Python API for Apache Spark, a distributed computing framework. Apache Spark itself is written in Scala and runs on the JVM. PySpark bridges the Python and JVM worlds using Py4J, which allows Python programs to communicate with Spark's Scala core. The key differences are:
  - Language & API: PySpark lets you write Spark jobs in Python; native Spark uses Scala/Java.
  - Performance: Pure Python UDFs run in a separate Python process (via Arrow or pickle serialization), adding overhead. DataFrame operations that use Spark's built-in functions are compiled to JVM bytecode by the Catalyst optimizer and perform identically regardless of API language.
  - Serialization: PySpark must serialize data between the JVM executor and the Python worker (using Arrow or pickle), which can be a bottleneck for Python-heavy code.
  - Ecosystem: PySpark integrates naturally with the Python data ecosystem (pandas, scikit-learn, NumPy), making it the preferred choice for data scientists and ML engineers.

Beginner Fundamentals 2. What is the role of SparkContext in a PySpark application?
Answer: SparkContext is the entry point to Spark's core functionality. It coordinates all Spark operations on the cluster: it connects to the cluster manager, allocates executors, tracks task assignment, and manages distributed variables (broadcasts and accumulators). Every Spark application has exactly one SparkContext (JVM-wide). In older code you created it manually via SparkConf. Since Spark 2.0, SparkSession encapsulates SparkContext, so you typically access it as spark.sparkContext. Key responsibilities include:
  - Establishing the connection to the cluster manager (Standalone, YARN, K8s).
  - Requesting and releasing executor resources.
  - Sending task closures and serialized code to executors.
  - Maintaining the DAG of RDD dependencies for fault recovery via lineage.
  - Managing accumulators and broadcast variables.

Beginner Fundamentals 3. What is SparkSession and why is it important?
Answer: SparkSession, introduced in Spark 2.0, is the unified entry point for Spark applications. It subsumes SparkContext, SQLContext, HiveContext, and StreamingContext into a single object. You create it with SparkSession.builder.getOrCreate(). Its importance:
  - Unified API: One object to read/write DataFrames, execute SQL, create UDFs, manage catalogs, and configure settings.
  - DataFrame/SQL access: Methods like read(), sql(), table(), and catalog provide the full SQL and DataFrame surface.
  - Configuration: Builder pattern lets you set app name, master URL, config options, and enable Hive support in one chain.
  - Backward compatibility: The underlying SparkContext is accessible via spark.sparkContext for RDD and low-level operations.
  - Session isolation: Multiple SparkSessions can share the same SparkContext but have independent catalogs, temporary views, and configurations—useful for multi-tenant scenarios.

Beginner Fundamentals 4. Explain the purpose of a Spark application, job, stage, and task.
Answer:
  - Application: The top-level user program submitted to Spark. It consists of a driver process and a set of executor processes. One application can produce multiple jobs over its lifetime.
  - Job: Triggered by an action (e.g., collect, count, write). Each action creates a job that the DAGScheduler breaks into stages. A job is the unit of work submitted to the cluster for one action.
  - Stage: A collection of tasks that can run in parallel without a shuffle. Stages are delimited by shuffle boundaries (wide transformations like groupBy, join, repartition). Each stage contains pipelined narrow transformations that run on the same partition data.
  - Task: The smallest unit of work, sent to one executor. One task processes one partition of data. The number of tasks in a stage equals the number of partitions at that stage's input. Tasks are what actually execute your user code on the data.

Beginner Fundamentals 5. What is a cluster manager in Spark?
Answer: A cluster manager allocates resources (CPU, memory) across applications on a cluster. Spark supports several cluster managers:
  - Standalone: Spark's built-in manager. Simple to set up; good for testing and small clusters.
  - Apache YARN: Hadoop's resource manager. Widely used in Hadoop ecosystems; provides resource isolation and multi-tenancy.
  - Kubernetes (K8s): Container orchestration platform. Growing in popularity for cloud-native deployments; offers fine-grained resource control and auto-scaling.
  - Amazon EC2 / Databricks managed: Cloud providers offer managed Spark clusters with built-in cluster management.
The cluster manager negotiates with the Spark driver to launch executor processes on worker nodes. It does not participate in task scheduling within an application—that is the DAGScheduler and TaskScheduler's job. It only manages coarse-grained resource allocation at the application level.
Beginner Fundamentals 6. What are worker nodes and executors?
Answer: Worker nodes are the physical or virtual machines in a cluster that run Spark compute work. Each worker node hosts one or more executor processes.
  - Worker node: The machine itself. It reports its available resources (CPU cores, memory) to the cluster manager. The cluster manager starts executor JVM processes on worker nodes at the application's request.
  - Executor: A JVM process launched on a worker node for a specific Spark application. Each executor:
    - Runs tasks assigned by the driver.
    - Stores in-memory data for caches and broadcasts assigned to it.
    - Reports task status and metrics back to the driver.
    - Has its own allocated memory (executor memory) and cores (executor cores).
  Executors are launched at application start and persist for the application's lifetime (unless dynamic allocation adds/removes them). Multiple applications on the same cluster get separate executors—they do not share executor processes.

Beginner Fundamentals 7. How does PySpark execute code on a cluster?
Answer: PySpark execution follows these steps:
  1. The user's Python driver program creates a SparkSession, which initializes a SparkContext on the JVM via Py4J.
  2. Transformations on DataFrames/RDDs build a logical plan (for DataFrames) or a lineage graph (for RDDs). No execution happens yet—this is lazy evaluation.
  3. When an action is called, the driver:
     a. Converts the logical plan into a physical plan (Catalyst optimizer for DataFrames).
     b. The DAGScheduler splits the plan into stages at shuffle boundaries.
     c. The TaskScheduler assigns tasks to executors based on data locality.
  4. Serialized task code and closures are sent to executor JVMs.
  5. For Python UDFs or RDD Python functions, the executor spawns a Python worker process and communicates via Arrow or pickle serialization.
  6. Tasks execute on partitions of data. Results are returned to the driver (for collect) or written to storage (for write actions).
  7. On task failure, Spark retries on a different executor using lineage to recompute lost partitions.

Beginner Fundamentals 8. What is a driver program in Spark?
Answer: The driver program is the process that runs the user's main() function and coordinates the Spark application. It is the JVM process where SparkContext/SparkSession lives. Key responsibilities:
  - Holds the SparkContext/SparkSession and all program-level state.
  - Builds the execution plan (DAG) from transformations.
  - The DAGScheduler divides the DAG into stages.
  - The TaskScheduler dispatches tasks to executors and monitors their completion.
  - Collects results from actions like collect(), count(), take().
  - Manages broadcast variables and accumulators.
  - Serves the Spark UI (usually on port 4040) during application execution.
The driver is the brain of the application. If the driver process crashes, the application fails (unless high availability is configured). In cluster mode, the driver runs on a cluster node; in client mode, it runs on the machine where the application was submitted.

Beginner Fundamentals 9. What is a partition in Spark?
Answer: A partition is a logical chunk of a distributed dataset. In Spark, every RDD or DataFrame is divided into partitions, and each partition is processed by one task on one executor. Key characteristics:
  - Partitions are the unit of parallelism: more partitions = more parallel tasks = better utilization of cluster cores.
  - Each partition fits on one executor; a partition cannot span multiple executors.
  - The number of partitions is configurable: repartition(), coalesce(), and the spark.default.parallelism setting control it.
  - For DataFrames, the initial partition count depends on the input source (e.g., number of input files for Parquet, or 200 shuffle partitions by default after a shuffle).
  - Partition size matters: too many small partitions cause task scheduling overhead; too few large partitions cause memory pressure and underutilization. A common guideline is 128 MB–256 MB per partition for balanced workloads.

Beginner Fundamentals 10. Why is data partitioning important?
Answer: Data partitioning is critical because it directly determines parallelism, performance, and data skew:
  - Parallelism: The number of partitions sets the maximum number of concurrent tasks. With too few partitions, you underuse the cluster. With the right number, all cores are busy.
  - Shuffle reduction: If data is partitioned by the join key (e.g., using repartition or bucketing), Spark can perform a map-side join and avoid shuffling entirely.
  - Data skew: Uneven partitioning causes some tasks to process far more data than others, creating stragglers. Salting or custom partitioners can mitigate this.
  - Memory: Each partition must fit in executor memory. Oversized partitions cause OOM errors or spills to disk.
  - Partition pruning: When reading partitioned tables (by date, region), Spark skips irrelevant partitions, dramatically reducing I/O.
  - Locality: Well-partitioned data allows Spark to schedule tasks close to the data (process-local or node-local), reducing network transfer.
Beginner Fundamentals 11. What is the difference between a transformation and an action?
Answer: Transformations and actions are the two fundamental operation types in Spark:
  - Transformation: Creates a new RDD/DataFrame from an existing one. Examples: map, filter, select, groupBy, join, withColumn. Transformations are lazy—they build up a lineage/DAG but do not execute immediately. They return a new RDD/DataFrame reference.
  - Action: Triggers actual computation. Examples: collect, count, take, show, write, save. Actions cause the DAGScheduler to submit a job, which launches tasks on executors to compute the result. Actions return a value to the driver or write output to storage.
  Key distinction: transformations define "what to compute" (the plan); actions say "now compute it." Without an action, no work happens.

Beginner Fundamentals 12. What is lazy evaluation in Spark?
Answer: Lazy evaluation means Spark does not execute transformations until an action is called. When you write df.filter(...).select(...).groupBy(...), Spark records each step in a DAG/lineage graph but does not process any data. Only when you call an action (e.g., show(), count(), write()) does Spark materialize the entire pipeline. This applies to both RDDs (lineage graph) and DataFrames (Catalyst logical/physical plan).

Beginner Fundamentals 13. Why is lazy evaluation useful for optimization?
Answer: Lazy evaluation enables several key optimizations:
  - Pipeline fusion: Multiple narrow transformations on the same partition are fused into a single task, avoiding intermediate materialization.
  - Predicate pushdown: Filters can be pushed down to the data source (e.g., Parquet, JDBC), so Spark reads only relevant data.
  - Column pruning: If a DataFrame has 20 columns but only 3 are referenced, Spark only reads those 3 from columnar formats like Parquet.
  - Plan optimization: The Catalyst optimizer sees the full logical plan before execution and can reorder filters, combine projections, choose optimal join strategies, and eliminate unnecessary operations.
  - Reduced I/O: Because Spark knows the full pipeline, it can skip reading or writing intermediate data that would be discarded anyway.
  - Fault recovery: If a partition is lost, Spark recomputes it from the lineage graph rather than relying on checkpoints of intermediate data.

Beginner Fundamentals 14. What is a Resilient Distributed Dataset?
Answer: An RDD (Resilient Distributed Dataset) is Spark's core low-level abstraction—a fault-tolerant, immutable, distributed collection of objects. Key properties:
  - Resilient: RDDs track their lineage (the sequence of transformations that created them). If a partition is lost, Spark can recompute it from the lineage graph.
  - Distributed: Data is split into partitions across multiple nodes in the cluster.
  - Immutable: Once created, an RDD cannot be changed. Transformations create new RDDs from existing ones.
  - Lazily evaluated: Transformations build lineage; actions trigger execution.
  - Typed: RDDs have a type parameter (e.g., RDD[String], RDD[(Int, String)]), and elements are processed as Python objects (in PySpark) or JVM objects (in Scala).
  RDDs offer full control over low-level operations (map, reduce, partitioning) but lack the optimizations of DataFrames (no Catalyst optimizer, no Tungsten execution).

Beginner Fundamentals 15. Why is RDD still relevant in PySpark?
Answer: Despite DataFrames being preferred for most workloads, RDDs remain relevant for:
  - Custom low-level algorithms: If your logic cannot be expressed with DataFrame operations or SQL, RDDs give you full control over each element and partition.
  - Unstructured data: For text processing, log parsing, or binary data without a schema, RDDs are more natural than DataFrames.
  - Fine-grained partition control: RDDs let you use custom partitioners, mapPartitions, and partition-level operations that are harder with DataFrames.
  - Legacy code: Many existing Spark pipelines are written with RDDs.
  - Streaming: The DStream API (older Spark Streaming) is built on top of RDDs.
  - Debugging/education: Understanding RDDs helps you understand how Spark works internally, since DataFrames are compiled to RDD-level operations.
  However, for any SQL-like or structured work, DataFrames should be preferred for performance and simplicity.
Beginner Fundamentals 16. What is a DataFrame in PySpark?
Answer: A DataFrame is a distributed collection of data organized into named columns, conceptually equivalent to a table in a relational database. In Spark, DataFrames are backed by RDDs of Row objects but have a schema (column names and types). Key characteristics:
  - Schema-aware: Spark knows the column names and data types, enabling optimizations like column pruning, predicate pushdown, and type-safe operations.
  - Optimized: DataFrames go through the Catalyst query optimizer, which transforms a logical plan into an optimized physical plan. The Tungsten execution engine then generates efficient JVM bytecode.
  - SQL integration: You can register a DataFrame as a temporary view and query it with SQL. You can also use the DataFrame DSL (domain-specific language) with methods like select, filter, groupBy.
  - Language-agnostic performance: Whether you use Python, Scala, Java, or R, DataFrame operations compile to the same JVM bytecode, so performance is equivalent (except for Python UDFs).
  - Creation: From files (CSV, JSON, Parquet, ORC), from existing RDDs, from Hive tables, from external databases (JDBC), or programmatically with createDataFrame().

Beginner Fundamentals 17. How is a DataFrame different from an RDD?
Answer:
  - Schema: DataFrames have a known schema (column names and types); RDDs are untyped collections of arbitrary objects.
  - Optimization: DataFrames are optimized by the Catalyst optimizer and Tungsten engine. RDDs have no built-in optimizer—you must optimize manually.
  - API: DataFrames use a declarative DSL (select, filter, groupBy) or SQL. RDDs use an imperative API (map, filter, reduceByKey) where you write explicit functions.
  - Performance: DataFrame operations run as optimized JVM bytecode. RDD operations, especially in PySpark, require Python-to-JVM serialization per element, which is much slower.
  - Type safety: In Scala, RDDs are compile-time typed (RDD[Person]). DataFrames are typed at the schema level but lose compile-time type safety (data is Row objects). Datasets combine both (type-safe + optimized).
  - Use case: Use DataFrames for structured data and SQL-like operations. Use RDDs for unstructured data and custom low-level algorithms.

Beginner Fundamentals 18. What is a Dataset in Spark?
Answer: A Dataset is a strongly-typed, distributed collection of objects, combining the benefits of RDDs (type safety, lambda functions) with DataFrames (Catalyst optimization, Tungsten execution). Key points:
  - Available in Scala and Java. In Python, there is no Dataset API—PySpark DataFrames are the equivalent (Python is dynamically typed, so type-safe APIs add no value).
  - A Dataset[T] carries compile-time type information (e.g., Dataset[Person]) while still being optimized by Catalyst.
  - Internally, a Dataset is a DataFrame plus an Encoder that serializes/deserializes JVM objects to/from Spark's internal binary format (Tungsten format).
  - Encoders allow Datasets to operate on domain objects (case classes in Scala, POJOs in Java) with the efficiency of DataFrames.
  - You can convert between DataFrame and Dataset: df.as[Person] (DataFrame to Dataset) and ds.toDF() (Dataset to DataFrame).
  - Use Datasets when you need type safety and object-oriented programming with Catalyst-level performance.

Beginner Fundamentals 19. What is schema inference in Spark?
Answer: Schema inference is the process by which Spark automatically determines the column names and data types of a dataset without the user explicitly defining them. When you call spark.read.csv("file.csv", header=True, inferSchema=True), Spark reads a sample of the data and infers types (e.g., integers, strings, dates, doubles). Key points:
  - Cost: Schema inference requires an extra pass over the data (or a sample), which adds overhead. For large files, this can be expensive.
  - Accuracy: Inference may guess wrong types—e.g., a column of numeric strings could be inferred as integers, or a column with mixed formats may be inferred as string.
  - Control: You can explicitly define a schema using StructType and StructField for full control over types and nullability.
  - Best practice: For production pipelines, define an explicit schema to ensure consistency and avoid the cost and uncertainty of inference. Use inference for quick exploration.

Beginner Fundamentals 20. What is the difference between narrow and wide transformations?
Answer:
  - Narrow transformation: Each input partition contributes to exactly one output partition. Data does not need to move between nodes. Examples: map, filter, select, withColumn, union. Narrow transformations are pipelined within a single stage—no shuffle is needed. They are fast and efficient.
  - Wide transformation: Input partitions contribute to multiple output partitions, requiring data to be redistributed across the cluster (a shuffle). Examples: groupBy, join, distinct, repartition, orderBy. Wide transformations create stage boundaries in the DAG. They are expensive because:
    - Data must be serialized, sent over the network, and deserialized on the receiving end.
    - Disk I/O occurs when shuffle data spills to disk.
    - The shuffle write/read is often the dominant cost in Spark jobs.
  Understanding which transformations are narrow vs. wide is essential for performance tuning.
Beginner Fundamentals 21. What happens during a shuffle in Spark?
Answer: A shuffle redistributes data across partitions so that all records with the same key end up on the same executor. Steps:
  1. Shuffle write: Each executor writes its partition data to local disk, organized by target partition (using a hash or sort-based shuffle). Data is serialized and sorted by key.
  2. Network transfer: The executors fetch the shuffle blocks they need from other executors' local disks over the network.
  3. Shuffle read: Each reducer task reads, deserializes, and merges the fetched blocks into the target partitions.
  Shuffles are expensive because they involve disk I/O, network transfer, serialization/deserialization, and memory for buffering. They create stage boundaries in the DAG. Minimizing shuffles (e.g., using broadcast joins, pre-partitioning, or co-locating data) is one of the most effective Spark optimizations.

Beginner Fundamentals 22. How does Spark manage memory?
Answer: Spark divides executor memory into several regions:
  - Execution memory (60%): Used for shuffles, joins, aggregations, and other internal operations. This is where Spark performs computation.
  - Storage memory (40%): Used for caching/persisting DataFrames and RDDs and broadcasting variables. If execution memory is full, Spark can evict cached blocks. If storage memory is not in use, execution can borrow from it (and vice versa, via unified memory management since Spark 1.6).
  - User memory (remaining after reserved + Spark overhead): Used for user-defined data structures, UDF internal state, and internal objects in RDD operations.
  - Reserved memory: A small fixed amount reserved for Spark internals.
  Key settings: spark.executor.memory (total executor heap), spark.memory.fraction (fraction for Spark + user), spark.memory.storageFraction (fraction of Spark memory for storage). When execution or storage memory is insufficient, Spark spills to disk, which is slower but prevents OOM.

Beginner Fundamentals 23. What is caching in Spark?
Answer: Caching stores a DataFrame or RDD in memory (or memory + disk) so that subsequent actions don't recompute it from the lineage. You call df.cache() or df.persist(StorageLevel.MEMORY_ONLY). Key points:
  - cache() is shorthand for persist(MEMORY_ONLY) for RDDs and persist(MEMORY_AND_DISK) for DataFrames.
  - Caching is lazy: data is only cached when an action materializes it, not at the cache() call.
  - Use cases: When the same DataFrame is used multiple times (e.g., in a loop or multiple queries), caching avoids recomputation.
  - Memory pressure: If cached data exceeds available storage memory, Spark evicts partitions (LRU). With MEMORY_ONLY, evicted partitions are recomputed. With MEMORY_AND_DISK, evicted partitions spill to disk.
  - Best practice: Cache only if the DataFrame is reused and the recomputation cost is high. Unpersist with df.unpersist() when done to free memory.

Beginner Fundamentals 24. How is persistence different from caching?
Answer: cache() and persist() are functionally the same, but persist() lets you choose the storage level:
  - MEMORY_ONLY: Store in JVM heap; evicted partitions are recomputed. Default for RDDs.
  - MEMORY_AND_DISK: Store in heap; evicted partitions spill to disk. Default for DataFrames.
  - MEMORY_ONLY_SER: Store serialized in heap (saves memory, adds CPU for serialization).
  - MEMORY_AND_DISK_SER: Serialized in heap, spilling to disk.
  - DISK_ONLY: Store on disk only, recompute is avoided but reads are slow.
  - OFF_HEAP: Store in off-heap memory (requires sun.misc.Unsafe and configuration).
  Caching (cache()) always uses the default storage level. Persistence (persist(level)) gives you control over the memory-disk trade-off. Choose MEMORY_AND_DISK for large DataFrames reused multiple times; MEMORY_ONLY for small frequently-accessed DataFrames.

Beginner Fundamentals 25. What is broadcast in PySpark?
Answer: Broadcast variables allow you to efficiently send a large read-only variable to all executors, rather than sending it with every task. Example: a lookup table or dictionary that tasks need. Without broadcast, Spark would serialize and send the variable with each task closure, wasting bandwidth and memory. With broadcast:
  1. The driver serializes the variable and sends it to each executor once.
  2. Each executor stores it locally and references it in all tasks.
  3. If an executor is lost, the broadcast is re-sent to the replacement.
  Usage: broadcast_var = sc.broadcast(my_dict); value = broadcast_var.value[key] in a UDF or map function. Also, Spark uses broadcast internally for broadcast joins—when one side of a join is small enough, it broadcasts it to all executors for a map-side join.
Beginner Fundamentals 26. What is an accumulator in PySpark?
Answer: Accumulators are shared variables that workers can only add to (via associative and commutative operations). They are used for counters, sums, and debugging. Key points:
  - The driver creates an accumulator with an initial value (e.g., acc = sc.accumulator(0)).
  - Executors add to it (acc.add(1)) inside transformations.
  - Only the driver can read the accumulator's value (acc.value). Executors cannot read it.
  - Accumulators are fault-tolerant: if a task is retried, the accumulator is not double-counted (for actions; for transformations, they may be double-counted if the transformation is recomputed).
  - Use cases: counting bad records, summing metrics, tracking how many rows match a condition.
  - In PySpark 2.0+, you can create named accumulators with custom types using AccumulatorV2.

Beginner Fundamentals 27. What is serialization in distributed data processing?
Answer: Serialization is the process of converting objects into a byte stream for transmission over the network or storage to disk. In distributed computing, it is essential because:
  - Task closures (your function + referenced variables) must be serialized on the driver and deserialized on each executor.
  - Shuffle data must be serialized before network transfer and deserialized on the receiving executor.
  - Broadcast variables are serialized before being sent to executors.
  Spark supports two serializers:
  - Java Serialization (default): Uses Java's ObjectInputStream/ObjectOutputStream. Flexible but slow. Any class implementing Serializable can be serialized.
  - Kryo Serialization (spark.serializer=org.apache.spark.serializer.KryoSerializer): Much faster (10x) and more compact. Requires classes to be registered. Recommended for performance-sensitive workloads.
  In PySpark, an additional serialization layer exists between the JVM and Python workers (using Py4J + pickle or Arrow). Arrow-based serialization is much faster and is enabled with spark.sql.execution.arrow.enabled.

Beginner Fundamentals 28. What is the difference between local mode and cluster mode?
Answer:
  - Local mode: Spark runs on a single machine (the driver's machine) using threads to simulate parallelism. Set via .master("local[2]") (2 threads) or .master("local[*]") (all cores). Used for development, testing, and small datasets. No cluster manager needed.
  - Cluster mode: Spark runs on a multi-node cluster managed by YARN, K8s, or Standalone. The driver can run:
    - In cluster deploy mode: The driver itself runs on a cluster node (submitted via spark-submit --deploy-mode cluster). The client can disconnect after submission.
    - In client deploy mode: The driver runs on the machine where spark-submit was executed. Executors run on cluster nodes. The client must stay alive for the application's duration.
  Local mode is for development; cluster mode is for production at scale.

Beginner Fundamentals 29. What is cluster mode in PySpark?
Answer: Cluster mode (deploy-mode cluster) means the driver program runs on a node within the cluster (e.g., a YARN ApplicationMaster or K8s pod), not on the submitting machine. The flow:
  1. You submit the application with spark-submit --deploy-mode cluster.
  2. The cluster manager allocates a container for the driver.
  3. The driver starts on that container and requests executor containers.
  4. The client machine can disconnect; the application runs independently.
  5. Results are written to storage or the driver logs.
  Advantages: No dependency on the submitting machine staying connected; better for production pipelines and scheduled jobs. Disadvantages: Cannot get interactive results directly (no collect() output to your terminal); debugging requires checking driver logs on the cluster.

Beginner Fundamentals 30. What is a local variable in a Spark transformation?
Answer: A local variable referenced inside a Spark transformation (e.g., in a map or filter function) is captured by the closure and serialized to executors. Key points:
  - The value at the time of task serialization is sent to executors. If the variable changes on the driver after the task is launched, executors won't see the new value (stale closure problem).
  - For large variables (e.g., lookup tables), use broadcast variables to avoid sending a copy with every task.
  - For accumulators, use Spark's Accumulator API rather than Python globals.
  - Avoid referencing non-serializable objects (e.g., open file handles, database connections) in transformations—they will cause serialization errors.
  - Each executor gets its own copy of the variable; modifications in one task do not affect others or the driver (no shared mutable state).
Beginner Fundamentals 31. What is a UDF and when should you avoid it?
Answer: A User-Defined Function (UDF) lets you apply custom Python logic to DataFrame columns. You register it with spark.udf.register() or use pyspark.sql.functions.udf(). Avoid UDFs when:
  - Built-in Spark SQL functions can do the same job (they are Catalyst-optimized and run in the JVM).
  - Performance matters: Python UDFs require serializing each row, sending it to a Python worker process, executing the Python function, and serializing the result back. This is much slower than JVM-native operations.
  - You need type safety: UDFs return generic types and Spark cannot optimize them within the Catalyst plan (they are black boxes).
  Alternatives: Use built-in functions (F.concat, F.when, F.regexp_replace, etc.), SQL expressions via F.expr(), or pandas UDFs (vectorized UDFs using Arrow, which are much faster than row-at-a-time UDFs).

Beginner Fundamentals 32. How do you create a SparkSession?
Answer:
  from pyspark.sql import SparkSession
  spark = SparkSession.builder \
      .appName("MyApp") \
      .master("local[*]") \
      .config("spark.sql.shuffle.partitions", "200") \
      .getOrCreate()
  Key points:
  - getOrCreate() returns an existing session if one exists, or creates a new one.
  - appName sets the application name shown in the Spark UI.
  - master sets the cluster URL (local[*] for local, yarn for YARN, k8s://... for Kubernetes).
  - config() sets Spark configuration options.
  - For Hive support: .enableHiveSupport() to access Hive metastore and Hive UDFs.
  - You can create multiple sessions: SparkSession.newSession() gives a new session with an independent catalog but sharing the same SparkContext.

Beginner Fundamentals 33. How do you read a text file into a DataFrame?
Answer:
  df = spark.read.text("path/to/file.txt")
  This creates a DataFrame with a single column named "value" containing each line as a string. Alternatively:
  df = spark.read.format("text").load("path/to/file.txt")
  For CSV files with headers:
  df = spark.read.csv("path/to/file.csv", header=True, inferSchema=True)
  For JSON:
  df = spark.read.json("path/to/file.json")
  You can also read from an RDD: spark.read.rdd(rdd_of_strings) or spark.createDataFrame(rdd, schema).

Beginner Fundamentals 34. How do you read a CSV file in PySpark?
Answer:
  df = spark.read \
      .option("header", "true") \
      .option("inferSchema", "true") \
      .option("sep", ",") \
      .option("nullValue", "NA") \
      .option("mode", "PERMISSIVE") \
      .csv("path/to/file.csv")
  Or shorthand: spark.read.csv("path", header=True, inferSchema=True)
  Key options:
  - header: Whether the first row contains column names.
  - inferSchema: Automatically detect column types (costs an extra scan).
  - sep: Column delimiter (default comma).
  - nullValue: What string represents null.
  - mode: PERMISSIVE (puts bad records in _corrupt_record), DROPMALFORMED, FAILFAST.
  - escape: Escape character (default backslash).
  - quote: Quote character (default double quote).
  For production, define an explicit schema with StructType instead of inferSchema.

Beginner Fundamentals 35. How do you create an empty DataFrame?
Answer:
  from pyspark.sql.types import StructType, StructField, StringType, IntegerType
  schema = StructType([
      StructField("name", StringType(), True),
      StructField("age", IntegerType(), True)
  ])
  empty_df = spark.createDataFrame([], schema)
  This creates a DataFrame with the defined schema but zero rows. Useful for:
  - Defining a schema template for union operations.
  - Initializing a DataFrame before appending in a loop.
  - Testing schema-dependent code without loading data.
  You can also create an empty DataFrame from an existing schema: empty_df = spark.createDataFrame([], other_df.schema)

Beginner Fundamentals 38. What is show() used for in PySpark?
Answer: show() is an action that prints the first N rows of a DataFrame to the console in tabular format. Key parameters:

Beginner Fundamentals 39. How do you count rows in a DataFrame?
Answer:
  df.count()  # Returns the total number of rows (Long). Triggers a full scan.

Beginner Fundamentals 40. How do you select a single column?
Answer:

  df.select(df.name)               # By column attribute
  df.select(col("name"))           # Using col() function
  df.select(df["name"])            # By bracket notation
  All return a new DataFrame with only the specified column. For multiple columns, pass multiple arguments: df.select("name", "age", "city").

Beginner Fundamentals 41. How do you select multiple columns?
Answer:
  df.select("name", "age", "city")           # Multiple string names
  df.select(col("name"), col("age"))         # Using col() function
  df.select(df.name, df.age)               # Using attribute access

Beginner Fundamentals 42. What does distinct() do?
Answer: distinct() returns a new DataFrame with duplicate rows removed, keeping only unique rows. It considers all columns. Example: df.distinct() returns one row per unique combination of all column values. It requires a shuffle (wide transformation), so it is expensive on large DataFrames. For distinct based on a subset of columns, use dropDuplicates(subset).

Beginner Fundamentals 43. What does dropDuplicates() do?
Answer: dropDuplicates() removes duplicate rows. Unlike distinct() (which considers all columns), dropDuplicates can take a subset of columns to deduplicate on:
  df.dropDuplicates(["name", "date"])  # Keep one row per unique name+date combination
  df.dropDuplicates()  # Same as distinct()—all columns
  The first occurrence is kept. It requires a shuffle. Use it when you want to deduplicate on specific keys while preserving all columns.

Beginner Fundamentals 44. What does filter() do?
Answer: filter() returns a new DataFrame containing only rows that satisfy a condition. Examples:
  df.filter(df.age > 25)
  df.filter("age > 25")           # SQL string
  df.filter((df.age > 25) & (df.city == "NYC"))  # Multiple conditions
  df.filter(col("name").startswith("A"))
  filter() is a narrow transformation (no shuffle). It is equivalent to where().

Beginner Fundamentals 45. What does where() do?
Answer: where() is an alias for filter(). They are functionally identical:
  df.where(df.age > 25)
  df.where("age > 25")
  Use whichever reads more naturally in your context—some developers prefer where() for SQL-style code and filter() for DataFrame DSL code.

Beginner Fundamentals 46. What does groupBy() do?
Answer: groupBy() groups rows by one or more columns and returns a GroupedData object, on which you apply aggregation functions:
  df.groupBy("department").count()
  df.groupBy("department", "city").agg({"salary": "avg", "age": "max"})  # Multiple aggregations
  df.groupBy("department").agg(avg("salary").alias("avg_salary"), count("*").alias("emp_count"))
  groupBy() is a wide transformation (requires shuffle). The result has one row per group key. You can also use groupBy() with pivot(), cube(), and rollup() for multi-dimensional analysis.
Beginner Fundamentals 47. What does orderBy() do?
Answer: orderBy() returns a new DataFrame sorted by one or more columns. Examples:
  df.orderBy("age")                          # Ascending by age
  df.orderBy(col("age").desc())               # Descending by age
  df.orderBy(col("age").desc(), col("name").asc())  # Multiple sort keys
  df.orderBy("age", ascending=False)          # Shorthand
  orderBy() is a wide transformation (requires a global shuffle to sort). For large datasets, sorting is expensive. If you only need top-N, use df.orderBy("age").limit(N) to reduce shuffle data after the sort. For sorting within partitions only (no global sort), use sortWithinPartitions().

Beginner Fundamentals 48. What does limit() do?
Answer: limit(n) returns a new DataFrame with only the first n rows. It is a transformation (lazy), but in practice it triggers early materialization of partitions until n rows are found. Key points:
  - It does not guarantee which n rows you get unless combined with orderBy.
  - df.orderBy("age").limit(10) gives the top 10 by age (Spark optimizes this to use a TakeOrdered operation).
  - limit() after a wide transformation may still require a shuffle.

Beginner Fundamentals 49. What does join() do?
Answer: join() combines two DataFrames based on a common column or condition. Syntax:
  df1.join(df2, df1.id == df2.id)              # Inner join (default)
  df1.join(df2, df1.id == df2.id, "left")      # Left outer join
  df1.join(df2, df1.id == df2.id, "right")     # Right outer join
  df1.join(df2, df1.id == df2.id, "outer")     # Full outer join
  df1.join(df2, "id")                           # Join on same-named column (drops duplicate)
  df1.join(df2, ["id1", "id2"])                # Multiple join keys
  Join types: inner (default), left (left_outer), right (right_outer), outer (full), left_semi, left_anti, cross.
  Joins are wide transformations. Spark chooses between broadcast join (small table) and sort-merge join (large tables) based on table sizes.

Beginner Fundamentals 50. What is a left join in Spark?
Answer: A left (outer) join returns all rows from the left DataFrame and matched rows from the right. If no match, right columns are null.
  df1.join(df2, df1.id == df2.id, "left")
  Use cases: Finding unmatched records (filter where right.id is null), enriching data while preserving all left rows, optional lookups.

Beginner Fundamentals 51. What is an inner join in Spark?
Answer: An inner join returns only rows that have matching keys in both DataFrames. Non-matching rows from either side are dropped.
  df1.join(df2, df1.id == df2.id, "inner")
  It is the default join type. Use it when you only need matched records.

Beginner Fundamentals 52. How do you rename a column?
Answer:
  df.withColumnRenamed("old_name", "new_name")  # Rename one column
  df.withColumn("new_name", col("old_name")).drop("old_name")  # Alternative
  df.selectExpr("old_name as new_name")  # Using SQL expression
  df.select(col("old_name").alias("new_name"))  # Using alias()
  For multiple renames: chain withColumnRenamed calls or use a select with aliases.

Beginner Fundamentals 53. How do you cast a column to a different type?
Answer:
  df.withColumn("age", col("age").cast("int"))
  df.withColumn("price", col("price").cast(DoubleType()))
  df.selectExpr("cast(age as int) as age")
  Common casts: string, int, long, double, float, boolean, date, timestamp. Invalid casts produce null (not an error) in Spark. Be cautious with string-to-number casts if the string contains non-numeric values.

Beginner Fundamentals 54. What are null values in Spark?
Answer: Null represents missing or unknown data. In Spark, null is different from empty string, 0, or NaN. Key null behavior:
  - Comparisons with null return null (not false): df.filter("col == null") is wrong; use df.filter(col("col").isNull()).
  - Aggregations skip nulls: sum(), avg(), count() ignore nulls. count(*) counts all rows including nulls; count(col) counts non-null values.
  - Nulls propagate through arithmetic: null + 5 = null.
  - Use isNull(), isNotNull(), isnull(), nanvl() for null handling.
  - In joins, null != null, so null keys don't match. Use <=> for null-safe equality.

Beginner Fundamentals 55. How do you handle null values in DataFrames?
Answer:
  df.na.drop()                        # Drop rows with any null
  df.na.drop(subset=["name", "age"])   # Drop if specific columns are null
  df.na.drop(thresh=3)                # Drop if fewer than 3 non-null values
  df.na.fill(0)                       # Replace all nulls with 0
  df.na.fill({"name": "unknown", "age": 0})  # Replace per column
  df.fillna({"name": "unknown"})       # Pandas-like API
  df.withColumn("name", when(col("name").isNull(), "unknown").otherwise(col("name")))  # Conditional
  Also use coalesce(col1, col2, lit("default")) to take the first non-null value.

Beginner Fundamentals 56. What is the importance of column names?
Answer: Column names are critical in Spark because:
  - They define the schema and enable column pruning (Spark reads only needed columns from columnar formats).
  - They are used for join conditions, group-by keys, and SQL references.
  - Duplicate column names after joins cause ambiguity—use alias() to disambiguate.
  - Case sensitivity depends on configuration (spark.sql.caseSensitive, default false—names are case-insensitive).
  - Clean, consistent names make downstream SQL queries and code more maintainable.
  - Special characters in names require backtick quoting in SQL.

Beginner Fundamentals 58. What is a temporary view?
Answer: A temporary view is a named, session-scoped reference to a DataFrame that lets you query it with SQL. Created with:

  spark.sql("SELECT * FROM my_view WHERE age > 25")
  Key points:
  - Session-scoped: exists only within the current SparkSession. Other sessions cannot see it.
  - Not persisted: it's a reference to the DataFrame, not a materialized table.

  - For global views across sessions: createOrReplaceGlobalTempView("my_view") and query as global_temp.my_view.

Beginner Fundamentals 59. How do you register a DataFrame as a table?

Beginner Fundamentals 60. What is the purpose of SQL queries on DataFrames?
Answer: SQL queries on DataFrames allow users to express transformations declaratively using standard SQL syntax. Benefits:
  - Familiarity: SQL is widely known; team members who aren't Python experts can still query data.
  - Readability: Complex joins, aggregations, and window functions may be clearer in SQL than in the DataFrame DSL.
  - Interoperability: SQL queries can be shared across tools (BI tools, notebooks, CLI).
  - Optimization: Both SQL and DataFrame DSL compile to the same Catalyst logical plan, so performance is identical.
  You can mix SQL and DataFrame APIs freely: create a temp view, query with SQL, then continue with DataFrame operations.

Beginner Fundamentals 61. What is the difference between DataFrame and SQL table?
Answer:
  - DataFrame: An in-memory distributed dataset defined in code. It exists for the session's lifetime unless persisted. Schema is defined at creation.
  - SQL table: A persistent entity registered in a catalog (Hive metastore or Unity Catalog). Data is stored on disk. Tables can be queried by any session with access.
  - A DataFrame can be registered as a temporary view for SQL access, but it is not a persistent table.
  - A table can be loaded into a DataFrame: df = spark.read.table("my_table").
  - Tables support ACID transactions (with Delta), schema enforcement, and partitioning metadata. DataFrames are transient.

Beginner Fundamentals 62. What is a row object in PySpark?

  - Row is a tuple-like object; you can iterate over it.
  - Created by: Row(name="Alice", age=30) or returned by collect(), take(), etc.

Beginner Fundamentals 67. What is writing data to Parquet in PySpark?

--- Beginner - Theory ---
Beginner Theory 1. What is lazy evaluation in the Spark execution model?
Answer: In Spark's execution model, lazy evaluation means that transformations (map, filter, select, join, groupBy) are not executed immediately. Instead, Spark records them as a DAG (for RDDs) or a logical plan (for DataFrames). When an action is called (collect, count, show, write), Spark triggers the entire pipeline. This allows Spark to see the full computation graph and optimize it as a whole—for example, pushing filters before joins, pruning unused columns, and fusing multiple narrow transformations into a single pass. Without lazy evaluation, each intermediate step would materialize full datasets, wasting memory and I/O.

Beginner Theory 2. How does Spark optimize transformations before execution?
Answer: Spark optimizes transformations through the Catalyst optimizer (for DataFrames/SQL), which has several phases:
  1. Parsing: Converts the SQL/DSL query string into an unresolved logical plan (a tree of relational operators).
  2. Analysis: Resolves column names, types, and functions against the catalog (using schema information). Produces a resolved logical plan.
  3. Logical optimization: Applies rule-based optimizations—predicate pushdown, column pruning, constant folding, null propagation, simplification of expressions, and reordering of operations. Produces an optimized logical plan.
  4. Physical planning: Generates multiple physical plans and selects the best one (cost-based). For example, choosing between broadcast join vs. sort-merge join based on table sizes.
  5. Code generation: Tungsten generates optimized JVM bytecode for the selected physical plan.
  For RDDs, there is no optimizer—Spark simply pipelines narrow transformations within a stage and creates shuffle boundaries for wide transformations.

Beginner Theory 3. What is the role of the Catalyst optimizer?
Answer: Catalyst is Spark SQL's query optimization framework. It transforms a user's DataFrame operations or SQL query into an efficient physical execution plan. Its role:
  - Analysis: Resolves references (column names, functions, tables) against the catalog.
  - Logical optimization: Applies rules like predicate pushdown (moving filters earlier), column pruning (dropping unused columns), constant folding (evaluating constants at compile time), and join reordering.
  - Physical planning: Chooses the best physical implementation (e.g., broadcast join vs. sort-merge join, hash aggregation vs. sort aggregation).
  - Cost-based optimization: Uses table statistics (row count, column cardinality) to estimate plan costs.
  - Extensibility: Developers can add custom optimization rules.
  Catalyst is the reason DataFrames outperform hand-written RDD code—the optimizer can see the full plan and make global optimizations that a developer writing step-by-step RDD code cannot.

Beginner Theory 4. How does Spark build a logical plan?
Answer: Spark builds a logical plan in these stages:
  1. Unresolved Logical Plan: When you call DataFrame operations, Spark constructs a tree of logical operators (Project, Filter, Join, Aggregate, etc.) with unresolved references. Column names and types are not yet validated.
  2. Resolved Logical Plan: The analyzer resolves all references against the catalog (table schemas, function signatures, column types). This catches errors like referencing non-existent columns.
  3. Optimized Logical Plan: Catalyst's optimizer applies rule-based transformations (predicate pushdown, column pruning, join reordering, constant folding) to produce the most efficient logical plan.
  The logical plan describes WHAT to compute, not HOW. The physical plan (next step) determines the execution strategy.

Beginner Theory 5. What is a physical plan in Spark SQL?
Answer: The physical plan describes HOW Spark will execute the logical plan. It is generated by the physical planner from the optimized logical plan. Key aspects:
  - Join strategy: BroadcastHashJoin (small table), SortMergeJoin (large tables), BroadcastNestedLoopJoin (cross join).
  - Aggregation strategy: HashAggregate (fast, in-memory) vs. SortAggregate (for sorted data or spill scenarios).
  - Exchange (shuffle) operators: Indicate where data needs to be redistributed.
  - Scan operators: FileScan (Parquet, CSV), JDBCScan, etc. Include pushed-down filters and projected columns.
  - Partitioning: Number of partitions, distribution (hash, range, broadcast).
  The physical plan is what actually runs on the cluster. You can view it with df.explain() or df.explain(True) to see all plan stages.

Beginner Theory 6. Explain the concept of lineage in RDDs.
Answer: Lineage is the record of all transformations that produced an RDD. Each RDD stores a reference to its parent RDD(s) and the function used to create it. This forms a directed acyclic graph (DAG) of dependencies. For example:
  rdd3 = rdd1.filter(f1).map(m1).reduceByKey(r1)
  Here rdd3's lineage is: rdd1 -> filter(f1) -> map(m1) -> reduceByKey(r1).
  Lineage is the foundation of Spark's fault tolerance. If a partition of rdd3 is lost (due to executor failure), Spark recomputes only that partition by replaying the lineage from the parent partitions. No replication or checkpointing of intermediate data is needed—only the original source data and the lineage graph are required.

Beginner Theory 7. Why does Spark use lineage for fault tolerance?
Answer: Spark uses lineage instead of data replication for fault tolerance because:
  - Efficiency: No overhead of replicating every intermediate RDD across nodes. Only the lineage graph (metadata) is stored on the driver.
  - Targeted recovery: When a partition is lost, Spark recomputes only the lost partition, not the entire dataset. It traces the lineage back to the last cached/checkpointed RDD or the original source.
  - Cost: Data replication would double storage requirements. Lineage recovery only pays the cost of recomputation when failures actually occur.
  - Generality: Works for any RDD, regardless of data type or transformation chain.
  - Limitation: For very long lineage chains, recomputation can be expensive. Checkpointing (saving an RDD to stable storage) truncates the lineage to avoid this.

Beginner Theory 8. What is task scheduling in Spark?
Answer: Task scheduling is the process of assigning tasks (units of work) to executors for execution. Spark's scheduling has two levels:
  1. DAG Scheduler: Divides the DAG into stages based on shuffle boundaries (wide transformations). Each stage is a set of pipelined narrow transformations. It submits stages in order, respecting dependencies.
  2. Task Scheduler: Within each stage, the Task Scheduler assigns individual tasks (one per partition) to executors. It considers:
     - Data locality: Prefers executors that have the data locally (process-local > node-local > rack-local > any).
     - Speculative execution: If a task is slow (straggler), a duplicate copy is launched on another executor; the first to finish wins.
     - Task retries: Failed tasks are retried up to a configurable limit (spark.task.maxFailures, default 4).
  Fair scheduling and FIFO scheduling are the two built-in scheduling policies for inter-application job scheduling.

Beginner Theory 9. What is the purpose of DAG scheduling?
Answer: The DAG Scheduler's purpose is to convert the logical DAG of RDD operations into a set of stages that can be executed. It:
  - Analyzes the RDD lineage and identifies shuffle boundaries (wide transformations like groupBy, join, repartition).
  - Groups consecutive narrow transformations (map, filter) into a single stage (pipeline fusion).
  - Determines stage dependencies (which stages must complete before others can start).
  - Submits stages to the TaskScheduler for execution.
  - Handles stage-level failures by resubmitting failed stages.
  The DAG Scheduler is the bridge between the logical plan (what to compute) and the physical execution (how to run it on the cluster).

Beginner Theory 10. What is a DAG in Spark?
Answer: A DAG (Directed Acyclic Graph) in Spark represents the dependency graph of RDD operations. Each node is an RDD, and edges represent transformations (parent to child). It is:
  - Directed: Transformations flow in one direction (from source to result).
  - Acyclic: No cycles—operations always move forward; you never get back to the same RDD through transformations.
  - Used for: Fault tolerance (recompute lost partitions by replaying the DAG), scheduling (divide into stages at shuffle boundaries), and optimization (pipeline narrow transformations).
  For DataFrames, the DAG is represented as a logical plan tree, but the concept is the same: Spark tracks dependencies and uses the graph for execution planning and recovery.
Beginner Theory 11. How does a DAG help execution?
Answer: A DAG helps execution in several ways:
  - Pipelining: Narrow transformations within a stage are pipelined—data flows through map, filter, select without materializing intermediate results, saving memory and I/O.
  - Parallelism: Tasks within a stage run in parallel across partitions. Different stages run sequentially (if dependent) or in parallel (if independent).
  - Fault tolerance: If a task fails, Spark only recomputes the affected partition by replaying the DAG from its parents.
  - Optimization: The Catalyst optimizer can reorder operations, push filters, and choose join strategies by analyzing the full DAG.
  - Scheduling: The DAG scheduler divides the DAG into stages at shuffle boundaries, enabling efficient task assignment and resource utilization.

Beginner Theory 12. What is the difference between an action and a transformation?
Answer: (See also Beginner Fundamentals 11.)
  - Transformation: Defines a computation step (map, filter, select, join, groupBy). Lazy—does not trigger execution. Returns a new DataFrame/RDD. Builds the DAG/lineage.
  - Action: Triggers execution (collect, count, take, show, write, save). Causes Spark to compute the full pipeline and return a result or write output. Creates a job in the DAG scheduler.
  Without actions, no work is done. A pipeline with only transformations has zero output.

Beginner Theory 13. What is a stage boundary in Spark?
Answer: A stage boundary is a point in the execution DAG where data must be shuffled between executors. It separates two stages. Stage boundaries are created by wide transformations (groupByKey, reduceByKey, join, repartition, distinct, orderBy). At a stage boundary:
  - The current stage's tasks write shuffle data to local disk.
  - The next stage's tasks fetch that data over the network.
  - The DAG scheduler cannot pipeline across a stage boundary.
  Minimizing stage boundaries (and thus shuffles) is one of the most effective performance optimizations in Spark.

Beginner Theory 14. What creates a stage boundary?
Answer: Stage boundaries are created by wide transformations that require data redistribution:
  - groupBy / groupByKey: All records with the same key must go to the same partition.
  - join: Records from both sides with the same join key must be co-located.
  - distinct: Requires global deduplication.
  - repartition / coalesce(numPartitions): Explicitly changes partition count.
  - orderBy / sortBy: Requires global sort.
  - reduceByKey / aggregateByKey: Although they perform map-side aggregation first, they still require a shuffle to aggregate across partitions.
  Narrow transformations (map, filter, select, union) do NOT create stage boundaries—they are pipelined within the same stage.

Beginner Theory 15. What is a shuffle and how does it affect performance?
Answer: A shuffle is the process of redistributing data across partitions so that all records with the same key are on the same executor. It involves:
  - Shuffle write: Each executor writes data to local disk, partitioned by target partition.
  - Network transfer: Data is fetched across the network by the destination executors.
  - Shuffle read: Receiving tasks read, deserialize, and sort/merge the fetched data.
  Performance impact: Shuffles are typically the most expensive operation in Spark. They involve disk I/O, network transfer, serialization, and memory pressure. Shuffle data can spill to disk, further degrading performance. Strategies to reduce shuffle:
  - Broadcast joins for small tables.
  - Pre-partitioning data by join keys.
  - Using reduceByKey instead of groupByKey (map-side aggregation reduces shuffle data).
  - Increasing parallelism to spread the shuffle load.

Beginner Theory 16. Why are wide transformations expensive?
Answer: Wide transformations are expensive because they require a shuffle:
  - Network I/O: Data must be transferred across the network between executors.
  - Disk I/O: Shuffle data is written to and read from local disk.
  - Serialization/deserialization: Data must be serialized for transfer and deserialized on the receiving end.
  - Memory pressure: Buffers for shuffle write/read consume significant memory.
  - Stage boundaries: Each wide transformation creates a new stage, preventing pipeline fusion.
  - Skew amplification: If keys are unevenly distributed, some shuffle partitions get much more data than others, causing stragglers.
  In contrast, narrow transformations (map, filter) are pipelined within a stage with no data movement, making them orders of magnitude cheaper.

Beginner Theory 17. What is data locality in Spark?
Answer: Data locality refers to Spark's preference for running tasks on the executors where the data is already stored, minimizing network transfer. Spark has five locality levels:
  - PROCESS_LOCAL: Data is in the same JVM as the task (ideal).
  - NODE_LOCAL: Data is on the same node (different process or HDFS block).
  - RACK_LOCAL: Data is on the same rack (one network hop).
  - NO_PREF: Data is equally available everywhere (e.g., broadcast data).
  - ANY: Data is on a different rack (worst).
  Spark waits a configurable time (spark.locality.wait, default 3s) before dropping to a lower locality level. Good locality reduces network I/O and improves throughput, especially for the first stage that reads from storage.

Beginner Theory 18. How does Spark choose execution locations?
Answer: Spark chooses task execution locations based on:
  - Data locality: Prefers executors where the input data resides (process-local first, then node-local, rack-local, any).
  - Locality wait: Spark waits up to spark.locality.wait (default 3s) for a better locality level before launching the task at a worse locality.
  - Resource availability: Only assigns tasks to executors with free cores.
  - Speculative execution: If a task is a straggler (running much slower than median), Spark launches a duplicate on another executor.
  - Preferred locations: For HDFS-backed data, Spark uses the block locations from the NameNode. For shuffle data, the locations of the shuffle files determine preferred locations.
  - Pipeline fusion: Narrow transformations in the same stage are scheduled to run on the same executor that holds the input data.

Beginner Theory 19. What is the difference between executor memory and driver memory?
Answer:
  - Executor memory (spark.executor.memory): Allocated to each executor JVM for storing task data, shuffle buffers, cached RDDs/DataFrames, and broadcast variables. Typically 4–32 GB per executor. The executor processes run on worker nodes and do the actual computation.
  - Driver memory (spark.driver.memory): Allocated to the driver JVM for storing the SparkContext, collecting results from actions (collect, take), and managing broadcast/accumulator state. Typically 1–8 GB. The driver coordinates the application and does not process data directly (except for results returned by collect).
  If the driver runs out of memory, the application crashes. If an executor runs out of memory, its tasks fail and are retried (or the executor is lost). Setting both appropriately is critical for stability.

Beginner Theory 20. What is memory spill in Spark?
Answer: Memory spill occurs when Spark runs out of in-memory buffer space during a shuffle or aggregation and writes excess data to disk. There are two types:
  - Sort spill: During sorting (e.g., orderBy, sort-merge join), if the data exceeds the sort buffer, Spark spills sorted runs to disk and merges them later.
  - Spill to disk for aggregations: During groupBy aggregations, if the hash table exceeds memory, Spark spills partial results to disk.
  Spill degrades performance because it adds disk I/O. You can monitor spill in the Spark UI (task details show spill memory and disk metrics). To reduce spill:
  - Increase executor memory or shuffle partitions.
  - Reduce data size per partition (more partitions).
  - Use reduceByKey (map-side aggregation) instead of groupByKey.
  - Use broadcast joins to avoid large shuffles.
Beginner Theory 21. What is GC overhead in Spark jobs?
Answer: GC (Garbage Collection) overhead refers to time spent by the JVM's garbage collector managing memory. In Spark, GC can become a significant bottleneck:
  - Large heaps: Executors with large heaps (10+ GB) can experience long GC pauses (full GC), pausing all processing.
  - Many objects: RDD operations create many short-lived objects (especially in Python UDFs), triggering frequent minor GCs.
  - Impact: Long GC pauses cause task timeouts, executor heartbeats to fail, and speculative execution to kick in unnecessarily.
  Mitigation:
  - Use DataFrames instead of RDDs (Tungsten uses off-heap memory, reducing GC pressure).
  - Tune JVM GC: Use G1GC (spark.executor.extraJavaOptions=-XX:+UseG1GC) for large heaps.
  - Reduce executor memory (more smaller executors can be better than one large one).
  - Use Kryo serialization to reduce object size.
  - Monitor GC in the Spark UI executor tab.

Beginner Theory 22. What is the purpose of the driver process?
Answer: The driver process is the JVM that runs the user's main() function and hosts the SparkContext/SparkSession. Its purposes:
  - Creates and configures the SparkSession.
  - Holds the logical execution plan (DAG) for all transformations.
  - The DAGScheduler converts the DAG into stages.
  - The TaskScheduler dispatches tasks to executors and monitors completion.
  - Collects results from actions (collect, take) into driver memory.
  - Manages broadcast variables (serialization and distribution).
  - Manages accumulators (aggregating values from executors).
  - Serves the Spark UI (typically port 4040).
  - Coordinates fault recovery (re-submitting failed stages/tasks).
  If the driver fails, the entire application fails (unless high availability is configured). The driver is the brain of the Spark application.

Beginner Theory 23. What is the purpose of executors?
Answer: Executors are JVM processes running on worker nodes that perform the actual computation for a Spark application. Each executor:
  - Runs tasks assigned by the driver (one task per core).
  - Stores in-memory data for cached DataFrames/RDDs and broadcast variables.
  - Writes shuffle data to local disk during wide transformations.
  - Reports task status, metrics, and heartbeats back to the driver.
  - Has its own allocated memory (executor memory) and cores (executor cores).
  Executors are launched at application start (or dynamically added with dynamic allocation) and persist for the application's lifetime. They are the muscle of the Spark application.

Beginner Theory 24. What is a cluster manager in distributed computing?
Answer: A cluster manager is a service that manages resources (CPU, memory) across a cluster of machines and allocates them to applications. It provides:
  - Resource negotiation: Applications request resources (cores, memory) and the cluster manager grants or denies based on availability.
  - Process management: Launches and monitors executor processes on worker nodes.
  - Multi-tenancy: Multiple applications can share the cluster, with isolation and fair resource allocation.
  - Failure handling: Restarts failed processes and reclaims resources from failed applications.
  Spark supports Standalone (built-in), YARN (Hadoop), and Kubernetes. The cluster manager does NOT manage task scheduling within a Spark application—that is the driver's job via DAGScheduler and TaskScheduler.

Beginner Theory 25. How does Spark work with YARN?
Answer: On YARN, Spark submits an application to the YARN ResourceManager, which allocates a container for the ApplicationMaster (the Spark driver in cluster mode, or a YARN application master in client mode). Steps:
  1. spark-submit contacts the YARN ResourceManager.
  2. ResourceManager allocates the first container for the ApplicationMaster.
  3. ApplicationMaster requests executor containers from ResourceManager.
  4. NodeManagers start executor JVMs on worker nodes.
  5. Executors register with the ApplicationMaster/Spark driver.
  6. Tasks are dispatched to executors.
  YARN provides resource isolation, queue-based scheduling, and integration with the Hadoop ecosystem (HDFS, Hive). Deploy mode: cluster (driver runs in YARN container) or client (driver runs on submit machine).

Beginner Theory 26. How does Spark work with Kubernetes?
Answer: On Kubernetes, Spark runs the driver and executors as pods in a K8s cluster. Steps:
  1. spark-submit sends the application to the K8s API server.
  2. K8s creates a driver pod (in cluster mode) or the driver runs on the submit machine (client mode).
  3. The driver requests executor pods from K8s.
  4. K8s schedules executor pods on worker nodes.
  5. Executors register with the driver and run tasks.
  6. On completion, executor pods are deleted.
  Benefits: Container-level isolation, fine-grained resource control, auto-scaling, cloud-native deployment. Spark on K8s supports client and cluster deploy modes, with Docker images for the Spark runtime.

Beginner Theory 27. How does Spark work with standalone mode?
Answer: Spark Standalone is Spark's built-in cluster manager. Architecture:
  - Master node: Runs the Master process, which manages worker nodes and application scheduling.
  - Worker nodes: Run Worker processes that register with the Master and host executor processes.
  Steps:
  1. Start the Master and Workers (via start-master.sh / start-slaves.sh or start-all.sh).
  2. spark-submit --master spark://master:7077 submits the application.
  3. The Master allocates resources and launches the driver (cluster mode) or accepts the driver (client mode).
  4. Workers start executor processes as requested.
  5. Tasks are dispatched and run.
  Standalone mode is simple to set up and good for testing, development, and small clusters. It lacks the advanced resource management and multi-tenancy of YARN or K8s.

Beginner Theory 28. Why is data skew a common challenge?
Answer: Data skew occurs when some keys have far more records than others, causing uneven partition sizes after a shuffle. This is a common challenge because:
  - Uneven key distribution: Real-world data is rarely uniform (e.g., a few popular products, a few active users).
  - Hash partitioning: Spark uses hash-based partitioning for shuffles, so all records with the same key go to the same partition. A hot key creates a huge partition.
  - Impact: The task processing the large partition takes much longer than others (straggler), wasting cluster resources while other tasks sit idle.
  - Cascading: Skew in an early stage propagates to downstream stages.
  - Memory: Large partitions can cause OOM errors or excessive spill.
  Solutions: Salting (adding random prefixes to split hot keys), broadcast joins (avoid shuffle for small tables), adaptive query execution (AQE) which can split skewed partitions automatically (Spark 3.0+).

Beginner Theory 29. What is the difference between repartition and coalesce?
Answer:
  - repartition(n): Changes the number of partitions to n. Always triggers a full shuffle. Data is redistributed across the network. Use when you need more partitions (to increase parallelism) or a different distribution.
  - coalesce(n): Reduces the number of partitions to n. By default, does NOT trigger a full shuffle—it merges adjacent partitions. Use when you want fewer partitions (e.g., before writing output) without the cost of a shuffle. If you need to increase partitions, coalesce can be called with shuffle=True, but repartition is more explicit for that.
  Key rule: Use coalesce to reduce partitions without shuffle. Use repartition to increase or fully redistribute partitions.

Beginner Theory 30. How do you reduce data skew in PySpark?
Answer: Strategies to reduce data skew:
  - Salting: Add a random prefix (0-9) to hot keys to split them into multiple partitions. After aggregation, remove the salt and re-aggregate.
  - Broadcast join: If one side of a join is small, broadcast it to avoid the shuffle entirely.
  - Adaptive Query Execution (AQE): Enable spark.sql.adaptive.enabled=true. AQE can automatically split skewed partitions (skew join handling).
  - Custom partitioner: For RDDs, use a custom partitioner that distributes keys more evenly.
  - Pre-aggregation: Use reduceByKey (which does map-side aggregation) instead of groupByKey to reduce shuffle data volume.
  - Increase shuffle partitions: spark.sql.shuffle.partitions (default 200) to spread the data across more partitions.
  - Repartition by range: Use repartitionByRange to distribute data by range of keys, which can help if keys have a natural ordering.
Beginner Theory 31. What is a wide transformation and why is it expensive?
Answer: A wide transformation requires data from multiple input partitions to be combined into output partitions, necessitating a shuffle. Examples: groupBy, join, distinct, repartition, orderBy. It is expensive because:
  - Network transfer: Data moves between executors over the network.
  - Disk I/O: Shuffle data is written to and read from local disk.
  - Serialization: Data must be serialized for transfer and deserialized on receipt.
  - Stage boundary: Creates a new stage, preventing pipeline fusion.
  - Memory: Shuffle buffers consume significant memory; spills to disk when buffers are full.
  Wide transformations are the primary performance bottleneck in most Spark jobs.

Beginner Theory 32. What is a narrow transformation and why is it efficient?
Answer: A narrow transformation processes each input partition independently to produce one output partition—no data movement needed. Examples: map, filter, select, withColumn, union. It is efficient because:
  - No shuffle: Data stays on the same executor; no network transfer or disk I/O.
  - Pipeline fusion: Multiple narrow transformations are combined into a single pass per partition.
  - No stage boundary: All narrow transformations in a chain run within one stage.
  - Low memory: No buffers needed for shuffle; each task processes its partition independently.
  Narrow transformations are the fastest operations in Spark and should be maximized in pipeline design.

Beginner Theory 33. What is checkpointing in Spark?
Answer: Checkpointing saves an RDD/DataFrame to reliable distributed storage (HDFS, S3) and truncates its lineage. After checkpointing:
  - The RDD is materialized and stored on disk.
  - Its lineage is cut—future failures will read from the checkpoint instead of recomputing from the original source.
  - Useful for long lineage chains where recomputation would be expensive.
  To use: sc.setCheckpointDir("hdfs://path"); rdd.checkpoint(). Note: checkpoint() is lazy—it only takes effect when an action is called afterward. You should count() or collect() after checkpointing to ensure it is materialized.

Beginner Theory 34. When should you use checkpointing?
Answer: Use checkpointing when:
  - Long lineage chains: If an RDD has many transformations, recomputing a lost partition requires replaying the entire chain. Checkpointing truncates the lineage to the checkpoint.
  - Iterative algorithms: ML algorithms (e.g., iterative optimization) repeatedly transform the same RDD. Checkpointing prevents the lineage from growing each iteration.
  - Expensive recomputation: If the source data is slow to read or the transformations are CPU-intensive, checkpointing avoids paying that cost twice.
  - Streaming: Spark Streaming checkpoints DStream state to recover from driver failures.
  Best practice: Cache before checkpointing—Spark first caches the RDD in memory, then writes to disk, avoiding recomputation during checkpoint materialization. Set a checkpoint directory with sc.setCheckpointDir().

Beginner Theory 35. What is cache() in Spark?
Answer: cache() stores a DataFrame or RDD in memory so subsequent actions don't recompute it. It is shorthand for:
  - RDDs: persist(MEMORY_ONLY)
  - DataFrames: persist(MEMORY_AND_DISK)
  cache() is lazy—it only caches when an action materializes the data. If memory is insufficient, cached partitions are evicted (LRU). With MEMORY_ONLY, evicted partitions are recomputed from lineage. With MEMORY_AND_DISK (DataFrames default), evicted partitions spill to disk.
  Use cache() when a DataFrame is used multiple times in a pipeline and recomputation is expensive. Always unpersist() when done.

Beginner Theory 36. What is persist() in Spark?
Answer: persist(StorageLevel) stores a DataFrame/RDD with a specified storage level:
  - MEMORY_ONLY: In JVM heap only. Evicted partitions are recomputed.
  - MEMORY_AND_DISK: In heap; evicted partitions spill to disk.
  - MEMORY_ONLY_SER: Serialized in heap (compact but CPU overhead).
  - MEMORY_AND_DISK_SER: Serialized in heap, spilling to disk.
  - DISK_ONLY: On disk only.
  - OFF_HEAP: Off-heap memory (requires configuration).
  persist() gives you control over the memory-disk-CPU trade-off. Choose the level based on your workload: MEMORY_ONLY for small frequently-accessed data, MEMORY_AND_DISK for large reused data, DISK_ONLY for very large data that doesn't fit in memory but is expensive to recompute.

Beginner Theory 37. How do transformations become tasks?
Answer: The flow from transformations to tasks:
  1. Transformations build a logical plan (DataFrames) or lineage DAG (RDDs).
  2. When an action is called, the DAGScheduler converts the plan/DAG into stages by splitting at shuffle boundaries (wide transformations).
  3. Each stage contains one or more tasks—one task per partition at that stage's input.
  4. The TaskScheduler assigns each task to an executor with available cores.
  5. The executor runs the task: it applies all pipelined narrow transformations in the stage to its partition of data.
  6. Results are returned to the driver (for collect-like actions) or written to storage (for write actions).
  So: transformations -> DAG -> stages -> tasks (one per partition per stage).

Beginner Theory 38. What is query planning in Spark SQL?
Answer: Query planning is the process of converting a SQL query or DataFrame operation into an executable plan. Stages:
  1. Parsing: SQL string -> unresolved logical plan (relational algebra tree).
  2. Analysis: Resolve columns, tables, functions against catalog -> resolved logical plan.
  3. Optimization: Catalyst applies rule-based optimizations (predicate pushdown, column pruning, join reordering) -> optimized logical plan.
  4. Physical planning: Choose physical operators (BroadcastHashJoin vs SortMergeJoin, HashAggregate vs SortAggregate) -> physical plan.
  5. Code generation: Tungsten generates optimized JVM bytecode for the physical plan.
  The entire pipeline is lazy and happens when an action is called.

Beginner Theory 39. What is the execution engine in Spark SQL?
Answer: The execution engine (Tungsten) is Spark's optimized execution backend. Key features:
  - Off-heap memory: Manages data in off-heap memory to reduce GC pressure.
  - Binary format: Data is stored in a compact binary format (UnsafeRow) instead of JVM objects, reducing memory usage and serialization overhead.
  - Code generation: Generates JVM bytecode for the physical plan, avoiding interpreter overhead.
  - Vectorized execution (Spark 3.x with Photon on Databricks): Processes batches of rows together for CPU cache efficiency.
  - Cache-aware data structures: Organizes data to maximize CPU cache hits.
  Tungsten is why DataFrames are much faster than RDDs—it avoids Python-to-JVM serialization and uses optimized native execution.

Beginner Theory 40. How does Spark handle schema evolution?
Answer: Schema evolution refers to handling changes in a table's schema over time (adding, dropping, or renaming columns). Spark handles this through:
  - Parquet: Supports schema evolution for added columns (old files have nulls for new columns). Requires spark.sql.parquet.mergeSchema=true or table-level ALTER TABLE.
  - Delta Lake: Full schema evolution support. ALTER TABLE ADD COLUMNS, RENAME COLUMN, DROP COLUMN. Can read files written with different schemas.
  - DataFrame reads: By default, Spark reads the schema from the first file. With mergeSchema=true, it merges schemas from all files.
  - JSON: Flexible—missing fields are null, new fields are added automatically.
  - CSV: No built-in schema evolution; requires explicit schema management.
  Best practice: Use Delta Lake for production tables requiring schema evolution and enforcement.
Beginner Theory 41. What is adaptive query execution?
Answer: Adaptive Query Execution (AQE), introduced in Spark 3.0, dynamically adjusts the execution plan at runtime based on actual statistics collected during execution. Key features:
  - Dynamic coalescing of shuffle partitions: Merges small post-shuffle partitions to avoid overhead.
  - Dynamic switch join strategy: Can switch from sort-merge join to broadcast join at runtime if one side turns out to be small enough.
  - Dynamic skew handling: Splits skewed partitions into smaller ones to balance load across tasks.
  Enabled with spark.sql.adaptive.enabled=true. AQE uses runtime statistics (actual partition sizes) that weren't available at plan time, leading to better decisions. It is especially useful for complex queries where static planning can't predict data sizes accurately.

Beginner Theory 42. What is the purpose of predicate pushdown?
Answer: Predicate pushdown moves filter conditions as close to the data source as possible, so Spark reads only relevant data. Benefits:
  - Reduced I/O: For columnar formats (Parquet), predicates are pushed to the file reader, which skips irrelevant row groups based on min/max statistics.
  - For JDBC sources: Filters are translated to WHERE clauses in the SQL query sent to the database, so only matching rows are transferred.
  - For partitioned tables: Filters on partition columns cause partition pruning—Spark skips entire partitions/files.
  - Reduced computation: Fewer rows flow through the pipeline, reducing CPU and memory usage.
  Example: df.filter("age > 25").select("name") with a Parquet source will only read the "name" column for rows where age > 25, skipping irrelevant row groups entirely.

Beginner Theory 43. What is vectorized execution?
Answer: Vectorized execution processes data in batches (vectors) rather than one row at a time, improving CPU efficiency:
  - Batch processing: Multiple rows are processed together in CPU cache-friendly batches.
  - SIMD: Modern CPUs can use Single Instruction Multiple Data (SIMD) to process multiple values per instruction.
  - Reduced function call overhead: One function call processes a batch, not one per row.
  - Columnar format: Works naturally with columnar storage (Parquet, ORC) where data is already organized by column.
  Spark's Parquet reader uses vectorized decoding. On Databricks, Photon provides full vectorized execution for all operators. Vectorized execution can be 2-10x faster than row-at-a-time execution for scan-heavy workloads.

Beginner Theory 44. How does Spark optimize joins?
Answer: Spark optimizes joins through several strategies:
  - Broadcast hash join: If one side is small (< spark.sql.autoBroadcastJoinThreshold, default 10MB), Spark broadcasts it to all executors for a map-side join. No shuffle needed. Fastest.
  - Sort-merge join: Both sides are sorted by the join key and merged. Requires a shuffle (to sort by key) but handles large tables. Most common for large-large joins.
  - Shuffle hash join: One side is shuffled and hashed, the other side is shuffled and probed against the hash table. Used when one side is small enough to build a hash table but too large for broadcast.
  - Broadcast nested loop join: Used for non-equi joins (cross join). Very expensive.
  - Join reordering: Catalyst reorders joins based on table statistics to minimize intermediate result sizes.
  - Predicate pushdown: Filters are applied before joins to reduce data volume.
  - AQE: Can dynamically switch join strategies at runtime based on actual data sizes.

Beginner Theory 45. What is a broadcast join?
Answer: A broadcast join (BroadcastHashJoin) sends the smaller table to all executors, where each executor performs a local hash join with the large table's partitions. No shuffle is needed for the large table.
  - Threshold: Tables smaller than spark.sql.autoBroadcastJoinThreshold (default 10MB) are eligible.
  - Manual broadcast: df1.join(broadcast(df2), "id") forces a broadcast join.
  - Benefits: Eliminates the shuffle of the large table, which is the most expensive part of a join. The small table is sent once per executor, not per task.
  - When to use: Small dimension tables joined with large fact tables. Common in star schema queries.
  - Risk: If the "small" table is actually large, broadcasting can cause OOM errors on executors.

Beginner Theory 46. What is sort-merge join?
Answer: Sort-merge join (SortMergeJoin) is the default join strategy for large tables in Spark. Steps:
  1. Shuffle: Both tables are shuffled by the join key so matching keys are on the same partition.
  2. Sort: Each partition of both tables is sorted by the join key.
  3. Merge: The sorted partitions are merged by iterating through both sorted streams and matching keys.
  Benefits: Handles arbitrarily large tables (no memory limit for the join itself). Scalable to petabyte-scale data.
  Drawbacks: Requires a full shuffle of both tables (expensive network and disk I/O). Both sides must be sorted, adding CPU overhead.
  Used when neither table is small enough for broadcast join. With AQE, Spark can dynamically switch to broadcast if one side turns out small enough at runtime.

Beginner Theory 47. What is a map-side join?
Answer: A map-side join is a join where one side (typically the small table) is broadcast to all executors, and each executor performs the join locally without a shuffle. It is equivalent to a broadcast join. Benefits:
  - No shuffle: The large table's data stays on its executor; no network transfer.
  - Fast: Each executor does a simple hash lookup against the broadcast table.
  - Scalable on the large side: Only limited by the small table's size (must fit in executor memory).
  Map-side joins are the fastest join strategy and should be used whenever one side is small enough. In Spark, this is achieved via broadcast(df_small) or automatically when the small table is under the broadcast threshold.

Beginner Theory 48. How is partition pruning useful?
Answer: Partition pruning skips reading partitions that don't match the filter condition, dramatically reducing I/O. Example:
  spark.read.parquet("/data/sales/year=2023/month=01/")
  If you filter df.filter("year = 2023 AND month = 01"), Spark skips all other year/month partitions entirely—no file is read.
  Benefits:
  - Reduces data scanned: Only relevant partitions are read.
  - Faster execution: Fewer tasks, less I/O, less CPU.
  - Cost savings: In cloud environments, you pay for data scanned.
  Works with partitioned tables (by date, region, category). The filter must reference the partition column. With Delta Lake, data skipping extends this to non-partition columns using min/max statistics.

Beginner Theory 49. What does file format choice affect in Spark?
Answer: File format affects:
  - Read performance: Columnar formats (Parquet, ORC) enable column pruning and vectorized reads. Row formats (CSV, JSON) require full scans.
  - Write performance: Columnar formats require sorting and encoding; row formats are simpler to write.
  - Compression: Parquet/ORC have built-in compression (snappy, gzip). CSV/JSON need external compression.
  - Schema: Parquet/ORC embed schema. CSV/JSON require external schema or inference.
  - Predicate pushdown: Parquet/ORC support predicate pushdown (skip row groups). CSV/JSON do not.
  - Splittability: Parquet/ORC are splittable (parallel reads). Gzipped text is not.
  - Evolution: Parquet/Delta support schema evolution. CSV has no native schema evolution.
  Best practice: Use Parquet or Delta for analytics. Use CSV/JSON for data ingestion/exchange only.

Beginner Theory 50. Why is Parquet preferred for analytics workloads?
Answer: Parquet is preferred because:
  - Columnar storage: Only needed columns are read (column pruning), reducing I/O for queries that select a few columns from many.
  - Predicate pushdown: Min/max statistics per row group allow skipping irrelevant data.
  - Compression: Columnar data compresses well (similar values are adjacent). Snappy for speed, gzip for size.
  - Splittable: Files can be read in parallel by multiple tasks.
  - Embedded schema: No external schema definition needed.
  - Vectorized reading: Spark's Parquet reader uses vectorized decoding for CPU efficiency.
  - Schema evolution: Supports adding columns without rewriting old files.
  - Wide support: Supported by Spark, Hive, Presto, Impala, Athena, and many other tools.
  For these reasons, Parquet (or Delta, which is Parquet-based) is the recommended format for Spark analytics workloads.
Beginner Theory 51. What is a data lakehouse pattern in Spark?
Answer: A data lakehouse combines the best of data lakes and data warehouses:
  - Data lake: Cheap storage (S3, ADLS, GCS), open formats (Parquet), supports all data types (structured, semi-structured, unstructured).
  - Data warehouse: ACID transactions, schema enforcement, data quality, BI-friendly query performance, metadata management.
  In Spark, the lakehouse pattern is implemented with Delta Lake (or Apache Iceberg / Apache Hudi). Delta Lake adds:
  - ACID transactions on Parquet files.
  - Time travel (query older versions of data).
  - Schema enforcement and evolution.
  - Upsert, delete, and merge operations.
  - Streaming and batch unified API.
  The lakehouse enables reliable, governed data pipelines on cheap cloud storage without a separate data warehouse.

Beginner Theory 52. What is the purpose of a metastore?
Answer: A metastore is a central metadata repository that stores information about databases, tables, partitions, schemas, and table locations. In Spark:
  - Hive metastore: The traditional metastore used by Spark when Hive support is enabled. Stores table metadata in a relational database (MySQL, PostgreSQL).
  - Unity Catalog (Databricks): A unified governance layer that stores metadata, access controls, and lineage for all data assets.
  Purpose:
  - Catalog: List tables, databases, columns.
  - Schema: Store and retrieve table schemas.
  - Location: Map table names to physical file paths.
  - Partition metadata: Track partition values and locations for partitioned tables.
  - Access control: (Unity Catalog) Manage permissions on tables, schemas, catalogs.
  Without a metastore, you'd need to know file paths and schemas manually. The metastore enables SQL-like table access (spark.read.table("db.table")).

Beginner Theory 53. What is the difference between logical and physical plans?
Answer:
  - Logical plan: Describes WHAT to compute. It is a tree of relational operators (Project, Filter, Join, Aggregate) without specifying how they are executed. Includes unresolved, resolved, and optimized logical plans.
  - Physical plan: Describes HOW to compute. It specifies the actual execution strategy: BroadcastHashJoin vs SortMergeJoin, FileScan vs JDBCScan, HashAggregate vs SortAggregate. It includes partitioning, shuffle, and data distribution details.
  The Catalyst optimizer converts logical plans to physical plans. The physical plan is what actually runs on the cluster as RDD operations.

Beginner Theory 54. How does Spark handle fault tolerance?
Answer: Spark handles fault tolerance at multiple levels:
  - RDD lineage: If a partition is lost, Spark recomputes it from the lineage DAG. No data replication needed.
  - Task retries: Failed tasks are retried up to spark.task.maxFailures (default 4) times.
  - Stage retries: If all tasks in a stage fail, the stage is resubmitted.
  - Executor loss: If an executor is lost (crash, OOM, node failure), its tasks are retried on other executors. Cached data on the lost executor is recomputed from lineage.
  - Checkpointing: Truncates lineage by saving to stable storage, preventing long recomputation chains.
  - Write-ahead logs (Streaming): Spark Streaming saves received data to HDFS before processing, enabling recovery from driver failures.
  - Delta Lake: ACID transactions ensure data integrity; failed writes can be rolled back.

Beginner Theory 55. Why is lineage important for recovery?
Answer: Lineage is important because:
  - No replication overhead: Unlike Hadoop MapReduce (which replicates intermediate data), Spark only stores the lineage graph (metadata). Recovery only requires recomputing lost partitions.
  - Targeted recovery: Only the lost partitions are recomputed, not the entire dataset. Spark traces the lineage of the lost partition back to the last cached/checkpointed RDD or the source.
  - Efficiency: For narrow dependencies, only the parent partitions that the lost partition depends on are recomputed. For wide dependencies, all parent partitions may be needed.
  - Automatic: Recovery is automatic—no user intervention needed. The driver detects failed tasks/executors and resubmits.
  - Limitation: Very long lineage chains make recovery expensive. Checkpointing mitigates this by truncating the lineage.

Beginner Theory 56. What are task retries in Spark?
Answer: When a task fails (due to OOM, network error, executor crash, or exception), Spark automatically retries it:
  - Max retries: spark.task.maxFailures (default 4). After this many failures, the stage fails and the job is aborted.
  - Different executor: Retried tasks are assigned to a different executor (if available).
  - Fetch failure: If a task fails because it can't fetch shuffle data (the source executor died), Spark may re-run the entire upstream stage that produced the shuffle data.
  - Impact: Retries improve reliability but add latency. Excessive retries indicate a systemic problem (data skew, OOM, bad data).
  - Speculative execution: Separate from retries—launches a duplicate of a slow (not failed) task.

Beginner Theory 57. Why do jobs fail on executor loss?
Answer: Jobs can fail on executor loss because:
  - Lost shuffle data: If an executor holding shuffle output dies, downstream tasks can't fetch the shuffle data. Spark must re-run the stage that produced the shuffle data.
  - Lost cached data: Cached DataFrames on the lost executor are gone. Spark recomputes them from lineage.
  - Task failures: Tasks running on the lost executor are marked as failed and retried. If max retries are exceeded, the job fails.
  - Heartbeat timeout: If the driver doesn't receive a heartbeat from an executor within spark.network.timeout (default 120s), the executor is marked as lost.
  Common causes of executor loss: OOM (task exceeds executor memory), node failure, network partition, GC pauses causing heartbeat timeout.

Beginner Theory 58. What is a shuffle file?
Answer: A shuffle file is a temporary file written to an executor's local disk during a shuffle. It contains the data that needs to be transferred to other executors. Structure:
  - Shuffle write: Each map task writes its output partitioned by target partition number. Data is sorted by key and serialized.
  - Shuffle fetch: Reduce tasks fetch their partition's data from the map tasks' shuffle files over the network.
  - Shuffle block: A portion of a shuffle file corresponding to one target partition. Each reduce task fetches one block from each map task.
  - Cleanup: Shuffle files are deleted when the application ends (or when the corresponding stage is no longer needed).
  Shuffle files are stored in the executor's local directory (spark.local.dir). If disk space is insufficient, shuffle files spill or tasks fail.

Beginner Theory 59. What is reduceByKey used for?
Answer: reduceByKey(func) is an RDD transformation that merges values for each key using the provided associative and commutative function. Example:
  rdd.reduceByKey(lambda a, b: a + b)  # Sum values per key
  Key advantages over groupByKey:
  - Map-side aggregation: Before shuffling, each partition locally combines values for the same key, reducing shuffle data volume.
  - Efficient: Much less network transfer because only the combined results are shuffled, not all individual values.
  - Use cases: Sum, count, min, max per key. For DataFrames, use groupBy().agg() or reduceByKey via RDD.
  For complex aggregations (multiple metrics, non-commutative operations), use aggregateByKey or combineByKey.

Beginner Theory 60. What is groupByKey and why can it be expensive?
Answer: groupByKey() groups all values for each key into an iterable collection. Unlike reduceByKey, it does NOT perform map-side aggregation—all values are shuffled across the network before grouping. This is expensive because:
  - Large shuffle: Every value is sent over the network, not just combined results.
  - Memory pressure: All values for a key must fit in memory on the receiving executor. For hot keys with many values, this causes OOM.
  - No pre-aggregation: No reduction happens before the shuffle.
  Best practice: Use reduceByKey or aggregateByKey instead of groupByKey whenever possible. Only use groupByKey when you truly need all values per key (e.g., to compute non-associative statistics or to collect values for further processing).
Beginner Theory 61. What is the difference between map and flatMap?
Answer:
  - map(func): Applies func to each element, producing exactly one output element per input. Input RDD of N elements -> output RDD of N elements.
    Example: rdd.map(lambda x: x * 2)  # [1,2,3] -> [2,4,6]
  - flatMap(func): Applies func to each element, producing zero or more output elements. func returns an iterable, which is flattened into individual elements. Input RDD of N elements -> output RDD of M elements (M can differ from N).
    Example: rdd.flatMap(lambda x: x.split(" "))  # ["hello world", "foo bar"] -> ["hello", "world", "foo", "bar"]
  Use map for 1:1 transformations. Use flatMap for 1:many (splitting, exploding) or 1:0 (filtering) transformations.

Beginner Theory 62. How does Spark create tasks from partitions?
Answer: For each stage, Spark creates one task per partition of the stage's input RDD/DataFrame. The process:
  1. The DAGScheduler divides the DAG into stages at shuffle boundaries.
  2. For each stage, the number of tasks = number of partitions in the last RDD/DataFrame before the stage's shuffle boundary.
  3. Each task processes one partition: it applies all pipelined narrow transformations in the stage to that partition's data.
  4. The TaskScheduler assigns tasks to executors based on data locality and resource availability.
  5. If there are 200 partitions and 10 executor cores, 10 tasks run simultaneously; the rest queue until cores free up.
  The number of partitions directly controls parallelism. Too few = underutilization; too many = scheduling overhead.

Beginner Theory 63. What is dynamic allocation?
Answer: Dynamic allocation allows Spark to dynamically add and remove executor resources during an application's runtime based on workload. Configured with:
  spark.dynamicAllocation.enabled=true
  Key parameters:
  - spark.dynamicAllocation.minExecutors: Minimum executors to keep.
  - spark.dynamicAllocation.maxExecutors: Maximum executors allowed.
  - spark.dynamicAllocation.initialExecutors: Starting number.
  - spark.dynamicAllocation.executorIdleTimeout: Remove idle executors after this time (default 60s).
  Benefits: Efficient resource usage—executors are added when there's pending work and removed when idle. Especially useful in multi-tenant clusters where applications have varying workloads.
  Requirements: External shuffle service must be enabled (so shuffle data survives executor removal).

Beginner Theory 64. Why is dynamic allocation useful?
Answer: Dynamic allocation is useful because:
  - Elasticity: Scale up when there's more work (more partitions pending) and scale down when idle. Avoids over-provisioning.
  - Multi-tenant efficiency: In shared clusters, idle executors from one application can be reclaimed for another.
  - Cost savings: In cloud environments (AWS, GCP, Azure), you only pay for executors you actually use.
  - Adaptive: Handles variable workloads (e.g., a pipeline with a small step followed by a large step) without manual sizing.
  - Limitation: Requires external shuffle service to preserve shuffle data when executors are removed. Not all cluster managers support it equally.

Beginner Theory 65. How does Spark distribute work at the partition level?
Answer: Spark distributes work by:
  1. Splitting data into partitions: Each DataFrame/RDD is divided into partitions. Partitions are the unit of parallelism.
  2. Assigning partitions to executors: The TaskScheduler assigns one task per partition to executors with free cores. Each task processes its partition independently.
  3. Data locality: Spark prefers to assign tasks to executors where the partition's data is already stored (HDFS block location, cached partition, shuffle file location).
  4. Pipelining: Narrow transformations within a stage are applied to a partition in sequence by the same task, without materializing intermediate results.
  5. Shuffle: At wide transformations, data is redistributed so all records with the same key are on the same executor for the next stage.
  6. Parallelism: The number of concurrent tasks = min(total partitions, total executor cores). More partitions = more parallel tasks (up to the cluster's core count).

Beginner Theory 66. What is the role of the DAG scheduler?
Answer: The DAG scheduler converts the logical DAG (from transformations) into a set of physical stages. Its roles:
  - Stage creation: Splits the DAG at shuffle boundaries (wide transformations) to create stages.
  - Pipeline fusion: Groups consecutive narrow transformations into a single stage.
  - Dependency tracking: Tracks which stages depend on which (parent stages must complete before child stages).
  - Stage submission: Submits stages to the TaskScheduler in dependency order.
  - Failure handling: Resubmits failed stages, potentially re-running upstream stages if shuffle data is lost.
  - Locality: Passes preferred locations for each stage's tasks to the TaskScheduler.
  The DAG scheduler is the brain of execution planning—it decides the structure of execution.

Beginner Theory 67. How does Spark estimate the cost of a query?
Answer: Spark estimates query cost using:
  - Table statistics: Row count, file size, and column statistics (min, max, distinct count, null count) collected via ANALYZE TABLE or automatically.
  - Cardinality estimation: Estimates the number of rows output by each operator (e.g., a filter with selectivity 0.1 on a 1M-row table produces ~100K rows).
  - Cost model: Assigns costs to operators based on estimated rows, I/O (scan bytes), and CPU (hash, sort). The optimizer selects the plan with the lowest estimated cost.
  - Column statistics: Help with join ordering (join the most selective filter first to minimize intermediate results).
  Without statistics, Spark falls back to uniform distribution assumptions, which can lead to poor plan choices. Running ANALYZE TABLE COMPUTE STATISTICS is critical for cost-based optimization.

Beginner Theory 68. How do statistics help Spark optimize queries?
Answer: Statistics enable cost-based optimization (CBO), which helps Spark make better decisions:
  - Join ordering: With table sizes and filter selectivity, Spark can order joins to minimize intermediate results (join the most selective tables first).
  - Join strategy: If statistics show one table is small enough, Spark can choose broadcast join instead of sort-merge join.
  - Partition sizing: Statistics help AQE decide how to coalesce or split partitions.
  - Filter estimation: Column statistics (min, max, distinct count) help estimate how many rows a filter will produce, affecting downstream operator choices.
  - Without statistics: Spark uses heuristic defaults (e.g., assume all filters have the same selectivity), which can lead to suboptimal plans.
  Collect statistics with: ANALYZE TABLE db.table COMPUTE STATISTICS (table-level) or ANALYZE TABLE db.table COMPUTE STATISTICS FOR COLUMNS col1, col2 (column-level).

Beginner SQL 1. How do you create a temporary view from a DataFrame?

Beginner SQL 2. How do you run a SQL query against a DataFrame?
Answer:
  df.createOrReplaceTempView("people")
  result = spark.sql("SELECT name, age FROM people WHERE age > 25 ORDER BY age DESC")
  result.show()
  spark.sql() returns a new DataFrame. You can chain DataFrame operations after it or call show()/collect().

Beginner SQL 3. What is the syntax for selecting all columns from a table?
Answer:
  SELECT * FROM table_name
  Or for specific columns: SELECT col1, col2 FROM table_name
  In DataFrame API: df.select("*") or df

Beginner SQL 4. How do you filter rows with a WHERE clause in Spark SQL?
Answer:
  SELECT * FROM table WHERE age > 25 AND city = 'NYC'
  SELECT * FROM table WHERE age BETWEEN 25 AND 65
  SELECT * FROM table WHERE name LIKE 'A%'
  SELECT * FROM table WHERE department IN ('Sales', 'Marketing')
  WHERE filters rows before grouping. It supports operators: =, !=, <, >, <=, >=, AND, OR, NOT, IN, BETWEEN, LIKE, IS NULL, IS NOT NULL.

Beginner SQL 5. How do you group data using GROUP BY?
Answer:
  SELECT department, COUNT(*) as emp_count, AVG(salary) as avg_salary
  FROM employees
  GROUP BY department
  GROUP BY groups rows by the specified columns, and you apply aggregate functions (COUNT, SUM, AVG, MIN, MAX) to each group. The result has one row per group key. Non-aggregated columns in SELECT must appear in GROUP BY.

Beginner SQL 6. How do you count rows with SQL?
Answer:
  SELECT COUNT(*) FROM table           -- Total rows (including nulls)
  SELECT COUNT(column) FROM table      -- Non-null values in column
  SELECT COUNT(DISTINCT column) FROM table  -- Distinct non-null values
  COUNT(*) counts all rows. COUNT(column) counts non-null values of that column. COUNT(DISTINCT column) counts unique non-null values.

Beginner SQL 7. How do you sort rows using ORDER BY?
Answer:
  SELECT * FROM table ORDER BY age ASC, name DESC
  SELECT * FROM table ORDER BY salary DESC
  ORDER BY sorts the result set by one or more columns. ASC (default) for ascending, DESC for descending. Multiple sort keys are applied left to right. ORDER BY is a wide transformation (requires a shuffle for global sort).

Beginner SQL 8. What is the purpose of LIMIT in SQL?
Answer:
  SELECT * FROM table LIMIT 10
  LIMIT restricts the number of rows returned. It is useful for:
  - Quick data inspection (preview first N rows).
  - Top-N queries: SELECT * FROM table ORDER BY score DESC LIMIT 10 (top 10 scores).
  - Pagination: LIMIT 10 OFFSET 20 (rows 21-30).
  LIMIT after ORDER BY is optimized by Spark to use a TakeOrdered operation (only sorts the top N, not the entire dataset).

Beginner SQL 9. How do you join two tables in Spark SQL?
Answer:
  SELECT a.name, b.department_name
  FROM employees a
  JOIN departments b ON a.dept_id = b.dept_id
  Join types: INNER JOIN (default), LEFT JOIN, RIGHT JOIN, FULL OUTER JOIN, CROSS JOIN, LEFT SEMI JOIN, LEFT ANTI JOIN.
  Multiple conditions: ON a.dept_id = b.dept_id AND a.active = 1
  Spark optimizes joins by choosing broadcast, sort-merge, or shuffle-hash based on table sizes.

Beginner SQL 10. What is an inner join in SQL?
Answer:
  SELECT * FROM a INNER JOIN b ON a.id = b.id
  An inner join returns only rows that have matching keys in both tables. Non-matching rows from either side are excluded. It is the default join type (JOIN without a qualifier is INNER JOIN). Use it when you only need matched records.
Beginner SQL 11. What is a left join in SQL?
Answer:
  SELECT * FROM a LEFT JOIN b ON a.id = b.id
  A left (outer) join returns ALL rows from the left table and matched rows from the right. If no match exists, right columns are NULL. Use it to find unmatched records (WHERE b.id IS NULL) or to preserve all left rows while optionally enriching with right data.

Beginner SQL 12. What is a right join in SQL?
Answer:
  SELECT * FROM a RIGHT JOIN b ON a.id = b.id
  A right (outer) join returns ALL rows from the right table and matched rows from the left. If no match exists, left columns are NULL. It is the mirror of a left join. In practice, most developers rewrite right joins as left joins for readability (swap table order).

Beginner SQL 13. What is a full outer join?
Answer:
  SELECT * FROM a FULL OUTER JOIN b ON a.id = b.id
  A full outer join returns ALL rows from BOTH tables. Matched rows are combined. Unmatched rows from either side are included with NULLs for the other table's columns. Use it to find rows that exist in only one of two tables (data reconciliation, gap analysis).

Beginner SQL 14. How do you handle duplicate values in SQL?
Answer:
  - DISTINCT: SELECT DISTINCT col1, col2 FROM table  -- Unique rows
  - GROUP BY: SELECT col1 FROM table GROUP BY col1  -- Unique values per group
  - ROW_NUMBER: Use window function to deduplicate and keep latest
  - dropDuplicates in DataFrame API: df.dropDuplicates(["col1", "col2"])
  Choose based on whether you want to remove all duplicates, or keep one representative row per group.

Beginner SQL 15. How do you remove duplicate rows with DISTINCT?
Answer:
  SELECT DISTINCT * FROM table                    -- All unique rows
  SELECT DISTINCT col1, col2 FROM table           -- Unique combinations of col1, col2
  DISTINCT considers all selected columns. It requires a shuffle (wide transformation). For large datasets, consider using dropDuplicates with a subset of columns or ROW_NUMBER() for controlled deduplication.

Beginner SQL 16. How do you rename a column in SQL?
Answer:
  SELECT old_name AS new_name FROM table
  SELECT old_name new_name FROM table  -- AS is optional
  For permanent rename in a table: ALTER TABLE table RENAME COLUMN old_name TO new_name (Delta Lake)
  In DataFrame API: df.withColumnRenamed("old_name", "new_name")

Beginner SQL 17. How do you alias a column in SQL?
Answer:
  SELECT salary * 1.1 AS adjusted_salary, name AS employee_name FROM employees
  Aliasing provides a readable name for computed columns or renamed columns. AS is optional but recommended for clarity. Aliases are used in ORDER BY, GROUP BY, and HAVING clauses.

Beginner SQL 18. How do you check for null values in SQL?
Answer:
  SELECT * FROM table WHERE column IS NULL      -- Rows where column is null
  SELECT * FROM table WHERE column IS NOT NULL   -- Rows where column is not null
  Note: WHERE column = NULL does NOT work (NULL != NULL in SQL). Always use IS NULL / IS NOT NULL.
  For null-safe equality: WHERE a <=> b (returns true if both are NULL or both are equal)

Beginner SQL 19. How do you replace null values with SQL?
Answer:
  SELECT COALESCE(column, 'default') FROM table        -- First non-null value
  SELECT IFNULL(column, 0) FROM table                   -- Replace null with 0 (MySQL-style)
  SELECT NVL(column, 'default') FROM table             -- Oracle-style
  SELECT CASE WHEN column IS NULL THEN 'default' ELSE column END  -- CASE expression
  In DataFrame API: df.na.fill(0) or df.fillna({'col': 'default'})
  COALESCE is the most flexible—it accepts multiple arguments and returns the first non-null.

Beginner SQL 20. How do you use CASE WHEN in Spark SQL?
Answer:
  SELECT
    CASE
      WHEN score >= 90 THEN 'A'
      WHEN score >= 80 THEN 'B'
      WHEN score >= 70 THEN 'C'
      ELSE 'F'
    END AS grade
  FROM students
  CASE WHEN evaluates conditions sequentially and returns the first matching result. ELSE provides a default. In DataFrame API: when(condition, value).otherwise(default).
Beginner SQL 21. How do you calculate aggregates in SQL?
Answer:
  SELECT department, COUNT(*) as cnt, SUM(salary) as total, AVG(salary) as avg_sal, MIN(salary) as min_sal, MAX(salary) as max_sal
  FROM employees
  GROUP BY department
  Aggregate functions: COUNT, SUM, AVG, MIN, MAX. They operate on groups defined by GROUP BY. Without GROUP BY, they aggregate over the entire table (one row result).

Beginner SQL 22. How do you use SUM, AVG, MIN, and MAX?
Answer:
  SELECT SUM(salary) FROM employees              -- Total salary
  SELECT AVG(salary) FROM employees              -- Average salary
  SELECT MIN(hire_date), MAX(hire_date) FROM employees  -- Earliest and latest hire dates
  SELECT department, SUM(sales) FROM orders GROUP BY department  -- Sum per department
  All aggregate functions ignore NULL values. COUNT(*) counts all rows; COUNT(column) counts non-null values.

Beginner SQL 23. How do you write a subquery in Spark SQL?
Answer:
  -- Scalar subquery (returns one value)
  SELECT * FROM employees WHERE salary > (SELECT AVG(salary) FROM employees)
  -- IN subquery (returns a list)
  SELECT * FROM orders WHERE customer_id IN (SELECT id FROM customers WHERE active = 1)
 -- Correlated subquery (references outer query)
  SELECT name, (SELECT COUNT(*) FROM orders WHERE orders.customer_id = customers.id) as order_count
  FROM customers
  -- Subquery in FROM (derived table)
  SELECT dept, avg_sal FROM (SELECT department as dept, AVG(salary) as avg_sal FROM employees GROUP BY department) t WHERE avg_sal > 50000

Beginner SQL 24. How do you use EXISTS in SQL?
Answer:
  SELECT * FROM customers c WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
  )
  EXISTS returns true if the subquery returns at least one row. It is often more efficient than IN for large datasets because it can short-circuit (stop scanning after finding the first match). NOT EXISTS finds rows with no matching records (anti-join pattern).

Beginner SQL 25. How do you use IN with a list of values?
Answer:
  SELECT * FROM employees WHERE department IN ('Sales', 'Marketing', 'HR')
  SELECT * FROM products WHERE category_id IN (1, 2, 3, 5, 8)
  IN checks if a value matches any value in the list. NOT IN finds values not in the list. For large lists, consider using a join with a lookup table or a subquery instead. Note: NULL in the list can cause unexpected results with NOT IN.

Beginner SQL 26. How do you combine two queries using UNION?
Answer:
  SELECT name, 'employee' as type FROM employees
  UNION
  SELECT name, 'contractor' as type FROM contractors
  UNION combines the results of two queries and removes duplicates. Both queries must have the same number of columns with compatible types. Use UNION ALL to keep duplicates (faster, since no deduplication shuffle is needed).

Beginner SQL 27. How do you combine queries using UNION ALL?
Answer:
  SELECT name, 'employee' as type FROM employees
  UNION ALL
  SELECT name, 'contractor' as type FROM contractors
  UNION ALL combines results WITHOUT removing duplicates. It is faster than UNION because it avoids the deduplication shuffle. Use UNION ALL when you know there are no duplicates or when duplicates are acceptable.

Beginner SQL 28. How do you write a self-join in Spark SQL?
Answer:
  SELECT a.name as employee, b.name as manager
  FROM employees a
  JOIN employees b ON a.manager_id = b.id
  A self-join joins a table with itself using aliases. Use cases: employee-manager hierarchies, finding pairs of records in the same table, comparing rows. Always use different aliases for the two instances of the table.

Beginner SQL 29. How do you use window functions in Spark SQL?
Answer:
  SELECT name, salary, department,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) as rank,
    AVG(salary) OVER (PARTITION BY department) as dept_avg,
    SUM(salary) OVER (ORDER BY hire_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) as running_total
  FROM employees
  Window functions perform calculations across a set of rows (the "window") related to the current row. They do not collapse rows (unlike GROUP BY). PARTITION BY divides data into groups, ORDER BY defines ordering within each partition, and the frame clause (ROWS BETWEEN...) defines the window range.

Beginner SQL 30. What is a partitioned table in Spark SQL?
Answer:
  A partitioned table physically organizes data into directories by partition column values:
  /data/sales/year=2023/month=01/  /data/sales/year=2023/month=02/
  CREATE TABLE sales (id INT, amount DOUBLE) PARTITIONED BY (year INT, month INT)
  Benefits: Partition pruning (skip irrelevant partitions during reads), faster queries on subsets, organized storage. Common partition columns: date, region, category. Over-partitioning creates many small files—aim for 128MB+ per partition.

Beginner SQL 35. How do you use HAVING in SQL?
Answer:
  SELECT department, COUNT(*) as emp_count, AVG(salary) as avg_salary
  FROM employees
  GROUP BY department
  HAVING COUNT(*) > 10 AND AVG(salary) > 50000
  HAVING filters groups AFTER aggregation. WHERE filters rows BEFORE aggregation. Use HAVING to filter on aggregate results (e.g., only show departments with more than 10 employees).

Beginner SQL 36. What is the difference between WHERE and HAVING?
Answer:
  - WHERE: Filters individual rows BEFORE grouping. Cannot use aggregate functions.
    SELECT * FROM table WHERE age > 25
  - HAVING: Filters groups AFTER grouping. Can use aggregate functions.
    SELECT dept, COUNT(*) FROM table GROUP BY dept HAVING COUNT(*) > 5
  Both can be used in the same query: WHERE filters rows, then GROUP BY groups them, then HAVING filters groups.

Beginner SQL 37. How do you filter on aggregated results?
Answer:
  SELECT department, AVG(salary) as avg_sal
  FROM employees
  GROUP BY department
  HAVING AVG(salary) > 60000
  Use HAVING after GROUP BY to filter on aggregate values. You cannot use WHERE for this because WHERE runs before aggregation. Alternatively, use a subquery: SELECT * FROM (SELECT dept, AVG(salary) as avg_sal FROM emp GROUP BY dept) t WHERE avg_sal > 60000

Beginner SQL 38. How do you use LIKE for pattern matching?
Answer:
  SELECT * FROM table WHERE name LIKE 'A%'        -- Starts with A
  SELECT * FROM table WHERE name LIKE '%son'       -- Ends with son
  SELECT * FROM table WHERE name LIKE '%A%'        -- Contains A
  SELECT * FROM table WHERE name LIKE '_A%'       -- Second character is A (_ = single char)
  SELECT * FROM table WHERE name LIKE '%a_b%' ESCAPE '\\'  -- Escape special chars
  % matches any sequence, _ matches a single character. For regex, use RLIKE or REGEXP.

Beginner SQL 39. How do you use BETWEEN in SQL?
Answer:
  SELECT * FROM employees WHERE age BETWEEN 25 AND 65
  SELECT * FROM orders WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31'
  BETWEEN is inclusive on both ends. It is shorthand for >= AND <=. NOT BETWEEN excludes the range. Be cautious with date/time BETWEEN because it includes the start but also includes the exact end timestamp.

Beginner SQL 40. How do you use NOT IN?
Answer:
  SELECT * FROM employees WHERE department NOT IN ('Sales', 'Marketing')
  SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM inactive_customers)
  NOT IN finds values not in the list/subquery. Caution: if the subquery returns NULL, NOT IN returns no rows (because NULL comparison yields NULL/unknown). Use NOT EXISTS instead for safety with potentially NULL-containing subqueries.

Beginner SQL 41. How do you use COALESCE in Spark SQL?
Answer:
  SELECT COALESCE(col1, col2, 'default') FROM table  -- Returns first non-null value
  SELECT COALESCE(address, 'No address on file') FROM customers
  COALESCE accepts multiple arguments and returns the first non-null one. If all are null, returns null. Useful for null replacement, fallback columns, and conditional defaults.

Beginner SQL 42. How do you use CAST in SQL?
Answer:
  SELECT CAST('123' AS INT)                      -- String to integer
  SELECT CAST(salary AS DOUBLE)                   -- Integer to double
  SELECT CAST(order_date AS STRING)               -- Date to string
  SELECT CAST('2023-01-15' AS DATE)               -- String to date
  CAST converts a value to the specified type. Invalid conversions return NULL (not an error). Also works with TRY_CAST (returns NULL on failure without error).

Beginner SQL 43. How do you convert string to date in SQL?
Answer:
  SELECT to_date('2023-01-15')                          -- ISO format (yyyy-MM-dd)
  SELECT to_date('15/01/2023', 'dd/MM/yyyy')             -- Custom format
  SELECT to_timestamp('2023-01-15 10:30:00')             -- String to timestamp
  SELECT date_format(order_date, 'yyyy-MM-dd')           -- Date to formatted string
  to_date() and to_timestamp() parse strings into date/timestamp types. The format string follows Java's SimpleDateFormat patterns.

Beginner SQL 44. How do you format date values?
Answer:
  SELECT date_format(current_date(), 'yyyy-MM-dd')       -- 2023-01-15
  SELECT date_format(current_date(), 'MM/dd/yyyy')       -- 01/15/2023
  SELECT date_format(current_timestamp(), 'yyyy-MM-dd HH:mm:ss')  -- Full timestamp
  SELECT year(date), month(date), day(date)               -- Extract components
  date_format() converts date/timestamp to a formatted string. Also available: year(), month(), day(), dayofweek(), quarter(), weekofyear().

Beginner SQL 45. How do you handle nested fields in SQL?
Answer:
  -- Access struct fields with dot notation
  SELECT name, address.city, address.zip FROM people
  -- Access array elements by index
  SELECT scores[0] as first_score FROM students
  -- Explode arrays into rows
  SELECT name, explode(hobbies) as hobby FROM people
  Nested fields (struct, array, map) are common in JSON and Parquet. Use dot notation for structs, [] for arrays, and explode() for array expansion.

Beginner SQL 46. How do you explode an array in Spark SQL?
Answer:
  SELECT name, explode(hobbies) as hobby FROM people
  -- Input: name='Alice', hobbies=['reading', 'hiking']
  -- Output: two rows: ('Alice', 'reading'), ('Alice', 'hiking')
  -- explode_outer keeps rows with empty arrays (produces NULL)
  SELECT name, explode_outer(hobbies) as hobby FROM people
  -- posexplode includes position index
  SELECT name, posexplode(hobbies) as (pos, hobby) FROM people
  explode() converts an array column into multiple rows, one per array element.

Beginner SQL 47. How do you use array functions in Spark SQL?
Answer:
  SELECT array('a', 'b', 'c')                    -- Create array
  SELECT size(hobbies)                            -- Array length
  SELECT array_contains(hobbies, 'reading')      -- Check membership

  SELECT array_intersect(arr1, arr2)             -- Intersection
  SELECT array_sort(arr)                          -- Sort array
  SELECT element_at(arr, 1)                       -- Get element at position (1-indexed)
  Spark SQL provides rich array functions for manipulating array columns.

Beginner SQL 48. How do you use map functions in SQL?
Answer:
  SELECT map('key1', 'value1', 'key2', 'value2')  -- Create map
  SELECT map_keys(my_map)                           -- Get all keys as array
  SELECT map_values(my_map)                         -- Get all values as array
  SELECT my_map['key1']                             -- Access by key
  SELECT map_concat(map1, map2)                     -- Merge maps
  SELECT element_at(my_map, 'key1')                 -- Get value by key
  Map functions work with Spark's MAP type (key-value pairs).

Beginner SQL 49. How do you use struct fields in Spark SQL?
Answer:
  -- Create struct
  SELECT struct(name, age) as person FROM employees
  -- Access struct fields with dot notation
  SELECT person.name, person.age FROM people
  -- In DataFrame API
  df.select(col("person.name"), col("person.age"))
  SELECT struct_extract(person, 'name')  -- Alternative accessor
  Structs are nested objects with named fields, similar to JSON objects. They can be created with struct() and accessed with dot notation.

Beginner SQL 50. How do you write a correlated subquery?
Answer:
  SELECT name, salary,
    (SELECT AVG(salary) FROM employees e2 WHERE e2.department = e1.department) as dept_avg
  FROM employees e1
  A correlated subquery references a column from the outer query (e1.department). It is evaluated once per row of the outer query. Use cases: comparing a row's value to an aggregate of its group, finding relative rank, checking for existence of related records. Correlated subqueries can be slower than joins or window functions for large datasets.

Beginner SQL 51. How do you use ROW_NUMBER over a partition?
Answer:
  SELECT name, department, salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) as rn
  FROM employees
  ROW_NUMBER assigns a unique sequential number (1, 2, 3...) to each row within a partition, ordered by the specified column. Use it to: rank rows within groups, deduplicate (keep rn=1), or find top-N per group. Unlike RANK, ROW_NUMBER never produces ties.

Beginner SQL 52. What is the purpose of RANK and DENSE_RANK?
Answer:
  -- RANK: Gaps after ties (1, 1, 3, 4)
  SELECT name, salary, RANK() OVER (ORDER BY salary DESC) as rank FROM employees
  -- DENSE_RANK: No gaps after ties (1, 1, 2, 3)
  SELECT name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) as dense_rank FROM employees
  RANK gives the same rank to ties but skips the next ranks. DENSE_RANK gives the same rank to ties but does NOT skip. ROW_NUMBER gives unique numbers regardless of ties.

Beginner SQL 53. How do you use NTILE in Spark SQL?
Answer:
  SELECT name, salary, NTILE(4) OVER (ORDER BY salary DESC) as quartile FROM employees
  NTILE(n) divides ordered rows into n approximately equal groups and assigns a group number (1 to n). Common uses: quartiles (NTILE(4)), deciles (NTILE(10)), percentiles. Each group has approximately the same number of rows.

Beginner SQL 54. How do you use lead and lag window functions?
Answer:
  -- LAG: Access previous row's value
  SELECT date, revenue, LAG(revenue, 1) OVER (ORDER BY date) as prev_revenue,
    revenue - LAG(revenue, 1) OVER (ORDER BY date) as daily_change
  FROM daily_sales
  -- LEAD: Access next row's value
  SELECT date, revenue, LEAD(revenue, 1) OVER (ORDER BY date) as next_revenue
  FROM daily_sales
  LAG(offset, default) accesses a row at a given offset before the current row. LEAD accesses a row after. Useful for time-series analysis, day-over-day comparisons, and gap detection.

Beginner SQL 55. How do you aggregate with rollup?
Answer:
  SELECT year, month, region, SUM(sales) as total
  FROM sales
  GROUP BY ROLLUP(year, month, region)
  ROLLUP produces subtotals at each level of grouping hierarchy and a grand total:
  - (year, month, region) — detailed groups
  - (year, month, NULL) — subtotal per year+month
  - (year, NULL, NULL) — subtotal per year
  - (NULL, NULL, NULL) — grand total
  It is a shorthand for multiple GROUP BYs with decreasing column sets.

Beginner SQL 56. How do you use cube in SQL?
Answer:
  SELECT year, month, region, SUM(sales) as total
  FROM sales
  GROUP BY CUBE(year, month, region)
  CUBE produces subtotals for ALL combinations of the grouping columns (not just hierarchical like ROLLUP):
  - (year, month, region), (year, month), (year, region), (month, region), (year), (month), (region), ()
  Use CUBE for multi-dimensional analysis where you need cross-tabulations across all dimension combinations.

Beginner SQL 61. How do you join on multiple conditions?

  SELECT * FROM a JOIN b ON a.id = b.id WHERE a.active = 1 AND b.status = 'approved'
  Multiple conditions in ON specify the join keys. Conditions in WHERE filter the result after the join. Use ON for join conditions and WHERE for post-join filters.

Beginner SQL 62. How do you use cross join in SQL?

  SELECT * FROM a CROSS JOIN b       -- Cartesian product
  SELECT * FROM a, b                -- Implicit cross join (comma syntax)
  SELECT * FROM a CROSS JOIN b ON a.x = b.x  -- Not valid; cross join has no ON
  A cross join produces the Cartesian product (every row of a paired with every row of b). It is very expensive for large tables (M x N rows). Use only for small tables or when explicitly needed.

Beginner SQL 63. How do you use semi join and anti join?
Answer:
  -- LEFT SEMI JOIN: Returns left rows that have a match in right (only left columns)
  SELECT * FROM a LEFT SEMI JOIN b ON a.id = b.id
  -- LEFT ANTI JOIN: Returns left rows that have NO match in right
  SELECT * FROM a LEFT ANTI JOIN b ON a.id = b.id
  Semi join is an existence check (like IN/EXISTS). Anti join finds missing records (like NOT IN/NOT EXISTS). Both are more efficient than full joins when you only need left columns.

Beginner SQL 64. How do you use aggregate functions with conditional logic?

    SUM(CASE WHEN salary > 50000 THEN salary ELSE 0 END) as high_salary_total
  FROM employees GROUP BY department
  CASE WHEN inside an aggregate function creates conditional aggregation. This is equivalent to COUNT_IF (for counting) or filtered aggregation. Very useful for pivoting data without the PIVOT clause.

--- Beginner - RDD ---
Beginner RDD 1. What is an RDD in PySpark?
Answer: An RDD (Resilient Distributed Dataset) is Spark's core low-level abstraction—a fault-tolerant, immutable, distributed collection of objects. Each RDD is split into partitions that can be processed in parallel across cluster nodes. RDDs track their lineage (the chain of transformations that created them), enabling automatic recovery if partitions are lost. They are lazily evaluated—transformations build a DAG, and actions trigger execution. In PySpark, RDD elements are Python objects, and operations use Python functions serialized to executors.

Beginner RDD 2. How do you create an RDD from a Python list?
Answer:
  rdd = spark.sparkContext.parallelize([1, 2, 3, 4, 5])
  rdd = sc.parallelize([1, 2, 3], numSlices=4)  # Specify partition count
  The parallelize() method distributes the Python list across the cluster. The numSlices parameter controls the number of partitions (default based on spark.default.parallelism).

Beginner RDD 3. How do you create an RDD from a file?
Answer:
  rdd = spark.sparkContext.textFile("path/to/file.txt")     # Text file, one line per element
  rdd = sc.textFile("hdfs://path/*.txt")                      # Wildcard for multiple files
  rdd = sc.wholeTextFiles("path/to/dir/")                    # (filename, content) pairs
  rdd = sc.binaryFiles("path/to/dir/")                        # (filename, binary content) pairs
  textFile splits the file by lines. Each line becomes one element in the RDD. The number of partitions depends on the file's HDFS block locations or spark.default.parallelism.

Beginner RDD 4. What is the difference between map and flatMap on an RDD?
Answer:
  - map(func): 1:1 transformation. Each input element produces one output element.
    rdd.map(lambda x: x * 2)  # [1,2,3] -> [2,4,6]
  - flatMap(func): 1:many transformation. Each input element produces zero or more output elements (func returns an iterable, which is flattened).
    rdd.flatMap(lambda x: x.split(" "))  # ["a b", "c d"] -> ["a","b","c","d"]
  Use map for element-wise transformation. Use flatMap for splitting/exploding.

Beginner RDD 5. How do you filter an RDD?
Answer:
  filtered_rdd = rdd.filter(lambda x: x > 5)
  filtered_rdd = rdd.filter(lambda x: x % 2 == 0)
  filter() is a transformation that keeps only elements for which the predicate returns True. It is a narrow transformation (no shuffle).

Beginner RDD 6. How do you transform an RDD using map()?
Answer:
  squared = rdd.map(lambda x: x ** 2)
  upper = rdd.map(lambda x: x.upper())
  pairs = rdd.map(lambda x: (x, 1))  # Convert to key-value pairs
  map() applies a function to each element, producing a new RDD with one output per input. It is a narrow transformation.

Beginner RDD 7. What does reduce() do on an RDD?
Answer:
  total = rdd.reduce(lambda a, b: a + b)  # Sum all elements
  maximum = rdd.reduce(lambda a, b: max(a, b))  # Find max
  reduce() is an action that aggregates all elements of an RDD using an associative and commutative binary function. It returns a single value to the driver. The function is applied in a tree-like fashion across partitions (each partition reduces locally, then results are combined).

Beginner RDD 8. What does collect() do on an RDD?
Answer:
  result = rdd.collect()  # Returns all elements as a Python list
  collect() is an action that retrieves all elements of the RDD to the driver as a list. Warning: For large RDDs, this can cause the driver to run out of memory. Use take(n) or first() for inspection instead. Only use collect() when the RDD is small enough to fit in driver memory.

Beginner RDD 9. What does take() do on an RDD?
Answer:
  first_10 = rdd.take(10)  # Returns first 10 elements as a list
  take(n) is an action that returns the first n elements. It is more memory-efficient than collect() because it only retrieves n elements. Spark scans partitions until n elements are found, so it may not scan the entire dataset.

Beginner RDD 10. What does first() do on an RDD?
Answer:
  first_element = rdd.first()  # Returns the first element
  first() is an action equivalent to take(1)[0]. It returns the first element of the RDD. If the RDD is empty, it raises an exception. Useful for quick inspection.

Beginner RDD 11. How do you count elements in an RDD?
Answer:
  count = rdd.count()          # Total elements (action)
  count_by_value = rdd.countByValue()  # Dict of {value: count} (action, returns to driver)
  count_by_key = rdd.countByKey()      # For pair RDDs: {key: count}
  count() triggers a full scan. countByValue() and countByKey() return dictionaries to the driver—use with caution on large RDDs.

Beginner RDD 12. What is distinct() on an RDD?
Answer:
  unique_rdd = rdd.distinct()  # Remove duplicate elements
  unique_rdd = rdd.distinct(numPartitions=10)  # Specify output partitions
  distinct() is a transformation that removes duplicate elements. It requires a shuffle (wide transformation) because duplicates may be in different partitions. Expensive for large RDDs.

Beginner RDD 13. What is union() on an RDD?
Answer:
  combined = rdd1.union(rdd2)  # All elements from both RDDs
  union() is a transformation that combines two RDDs. Duplicates are kept (unlike SQL UNION). It is a narrow transformation (no shuffle—just concatenates partitions). The schemas/types of both RDDs should be compatible.

Beginner RDD 14. What is intersection() on an RDD?
Answer:
  common = rdd1.intersection(rdd2)  # Elements in both RDDs
  intersection() is a transformation that returns elements present in both RDDs. It requires a shuffle (wide transformation) to find matching elements across partitions. Duplicates are removed in the result.

Beginner RDD 15. What is subtract() on an RDD?
Answer:
  diff = rdd1.subtract(rdd2)  # Elements in rdd1 but not in rdd2
  subtract() is a transformation that returns elements from the first RDD that are NOT in the second RDD. It requires a shuffle. Useful for finding missing records or set differences.

Beginner RDD 16. How do you sort an RDD?
Answer:
  sorted_rdd = rdd.sortBy(lambda x: x)           # Sort by identity
  sorted_rdd = rdd.sortBy(lambda x: x[1], ascending=False)  # Sort by second element, descending
  sorted_kv = rdd.sortByKey()                      # Sort pair RDD by key
  sortBy() is a transformation (but triggers a shuffle). sortByKey() works on pair RDDs. Both produce a globally sorted RDD. For large datasets, consider using DataFrames with orderBy() for better optimization.

Beginner RDD 17. What is groupByKey() on an RDD?
Answer:
  grouped = rdd.groupByKey()  # RDD of (key, iterable of values)
  for k, v in grouped.collect(): print(k, list(v))
  groupByKey() groups all values for each key. It is a wide transformation that shuffles ALL values across the network. It does NOT perform map-side aggregation, making it expensive for large datasets. Prefer reduceByKey() or aggregateByKey() whenever possible.

Beginner RDD 18. What is reduceByKey() on an RDD?
Answer:
  sums = rdd.reduceByKey(lambda a, b: a + b)  # Sum values per key
  reduceByKey() merges values for each key using an associative, commutative function. It performs map-side aggregation (combines values within each partition before shuffling), reducing shuffle data volume. Much more efficient than groupByKey() for aggregations like sum, count, min, max.

Beginner RDD 19. What is aggregateByKey() on an RDD?
Answer:
  result = rdd.aggregateByKey(
      zeroValue=0,
      seqFunc=lambda acc, val: acc + val,       # Within-partition aggregation
      combFunc=lambda acc1, acc2: acc1 + acc2   # Across-partition combination
  )
  aggregateByKey() is more flexible than reduceByKey—it supports a zero value and different functions for within-partition and cross-partition aggregation. Use it for non-commutative operations, computing multiple metrics in one pass, or when you need a different combine vs. reduce function.

Beginner RDD 20. What is join() on key-value RDDs?
Answer:
  joined = rdd1.join(rdd2)         # Inner join: (key, (val1, val2))
  left = rdd1.leftOuterJoin(rdd2)  # Left join: (key, (val1, Optional[val2]))
  right = rdd1.rightOuterJoin(rdd2) # Right join: (key, (Optional[val1], val2))
  full = rdd1.fullOuterJoin(rdd2)  # Full outer join
  join() on pair RDDs combines values by key. It requires a shuffle to co-locate matching keys. For DataFrames, use df.join() which supports optimizer-chosen join strategies.
Beginner RDD 21. What is cogroup() on RDDs?
Answer:
  grouped = rdd1.cogroup(rdd2)  # (key, (iterable1, iterable2))
  cogroup() groups values from multiple RDDs by key. The result contains all keys from both RDDs, with an iterable of values from each. It is the foundation for joins, intersections, and subtracts on pair RDDs. Use it when you need to compare or combine data from multiple keyed RDDs without performing a full join.

Beginner RDD 22. What is zip() on two RDDs?
Answer:
  zipped = rdd1.zip(rdd2)  # (elem1, elem2) pairs
  zip() combines two RDDs element by element—the first element of rdd1 with the first of rdd2, etc. Both RDDs must have the same number of partitions and elements per partition. The result is a pair RDD of (rdd1_elem, rdd2_elem) tuples.

Beginner RDD 23. What is cartesian() on an RDD?
Answer:
  product = rdd1.cartesian(rdd2)  # All pairs (a, b) where a in rdd1, b in rdd2
  cartesian() computes the Cartesian product of two RDDs. The result has M x N elements (M and N are the sizes of the two RDDs). This is extremely expensive for large RDDs—avoid unless absolutely necessary (e.g., for small lookup tables or testing).

Beginner RDD 24. What is sample() on an RDD?
Answer:
  sampled = rdd.sample(withReplacement=False, fraction=0.1)  # 10% without replacement
  sampled = rdd.sample(True, 0.5, seed=42)  # 50% with replacement
  sample() is a transformation that randomly samples a fraction of the RDD. withReplacement controls whether the same element can be picked multiple times. fraction is the sampling probability (not exact count). For an exact sample, use takeSample().

Beginner RDD 25. How do you repartition an RDD?
Answer:
  repartitioned = rdd.repartition(10)  # Exactly 10 partitions (full shuffle)
  repartition() changes the number of partitions with a full shuffle. Data is redistributed across the network. Use it to increase parallelism or redistribute skewed data. For reducing partitions without a shuffle, use coalesce().

Beginner RDD 26. How do you coalesce an RDD?
Answer:
  coalesced = rdd.coalesce(2)  # Reduce to 2 partitions without shuffle
  coalesce() reduces the number of partitions by merging adjacent partitions. By default, no shuffle occurs—much cheaper than repartition(). Use it before writing output to avoid too many small files. To increase partitions, use coalesce(n, shuffle=True) or repartition(n).

Beginner RDD 27. What is foreach() on an RDD?
Answer:
  rdd.foreach(lambda x: print(x))  # Apply function to each element
  foreach() is an action that applies a function to each element. Unlike map(), it does not return a new RDD—the function's side effects are the output. Useful for writing to external systems (databases, APIs). The function runs on executors, so results are not returned to the driver.

Beginner RDD 28. What is foreachPartition() on an RDD?
Answer:
  rdd.foreachPartition(lambda partition: write_to_db(list(partition)))
  foreachPartition() is an action that applies a function to each partition (as an iterator). It is more efficient than foreach() for operations that benefit from batch processing (e.g., opening a database connection once per partition rather than per element). The function receives an iterator of the partition's elements.

Beginner RDD 29. What is persist() on an RDD?
Answer:
  rdd.persist(StorageLevel.MEMORY_AND_DISK)
  rdd.persist(StorageLevel.MEMORY_ONLY_SER)
  persist() stores the RDD in memory/disk with a specified storage level. It is lazy—data is persisted when an action triggers computation. Storage levels: MEMORY_ONLY, MEMORY_AND_DISK, MEMORY_ONLY_SER, MEMORY_AND_DISK_SER, DISK_ONLY, OFF_HEAP. Call unpersist() when done to free resources.

Beginner RDD 30. What is cache() on an RDD?
Answer:
  rdd.cache()  # Shorthand for persist(MEMORY_ONLY)
  cache() stores the RDD in memory. It is shorthand for persist(StorageLevel.MEMORY_ONLY). If memory is insufficient, partitions are evicted and recomputed from lineage when needed. Use cache() when the RDD is used multiple times and recomputation is expensive.

Beginner RDD 31. What is the purpose of checkpointing an RDD?
Answer:
  sc.setCheckpointDir("hdfs://checkpoint/path")
  rdd.checkpoint()  # Materialize and save to stable storage
  checkpoint() saves the RDD to reliable storage (HDFS/S3) and truncates its lineage. After checkpointing, if a partition is lost, Spark reads from the checkpoint instead of recomputing the full lineage. Useful for long lineage chains or iterative algorithms. Best practice: cache before checkpoint to avoid recomputation during checkpoint materialization.

Beginner RDD 32. How do you check the number of partitions in an RDD?
Answer:
  num = rdd.getNumPartitions()  # Returns int
  num = rdd.partitions.size     # Alternative
  Use this to verify partitioning before and after operations. It is a metadata operation (no computation needed).

Beginner RDD 33. How do you set the number of partitions when creating an RDD?
Answer:
  rdd = sc.parallelize(data, numSlices=10)   # 10 partitions
  rdd = sc.textFile("path", minPartitions=8)  # At least 8 partitions
  For transformations that produce a shuffle:
  rdd = rdd.repartition(20)
  rdd = rdd.coalesce(5)
  The default number of partitions is determined by spark.default.parallelism (or the number of HDFS blocks for file-backed RDDs).

Beginner RDD 34. What is glom() on an RDD?
Answer:
  partition_data = rdd.glom()  # RDD of lists (one list per partition)
  glom() transforms each partition into a Python list. The result is an RDD where each element is a list containing all elements of one partition. Useful for debugging partition contents or performing per-partition aggregations without mapPartitions.

Beginner RDD 35. What is mapPartitions() on an RDD?
Answer:
  result = rdd.mapPartitions(lambda partition: [sum(partition)])
  result = rdd.mapPartitions(process_partition, preservesPartitioning=True)
  mapPartitions() applies a function to each partition (as an iterator) rather than each element. The function returns an iterator of output elements. It is more efficient than map() for operations that require per-partition setup (e.g., opening a database connection) because the setup runs once per partition, not per element.

Beginner RDD 36. Why would you use mapPartitions()?
Answer:
  - Per-partition setup: Initialize expensive resources (DB connections, ML models) once per partition instead of per element.
  - Batch processing: Process elements in batches within each partition.
  - Per-partition aggregation: Compute statistics per partition before a shuffle.
  - Memory efficiency: Avoid creating intermediate objects per element by reusing buffers.
  Example:
    def process(iter):
        conn = create_connection()  # Once per partition
        results = [conn.query(row) for row in iter]
        conn.close()
        return results
    rdd.mapPartitions(process)

Beginner RDD 37. What is flatMapValues() for key-value pairs?
Answer:
  rdd = sc.parallelize([("a", [1, 2, 3]), ("b", [4, 5])])
  result = rdd.flatMapValues(lambda x: x)  # [("a", 1), ("a", 2), ("a", 3), ("b", 4), ("b", 5)]
  flatMapValues() applies flatMap to the values of a pair RDD while keeping the keys. It is useful for exploding value lists or splitting value strings while preserving the key association.

Beginner RDD 38. What is keys() on an RDD?
Answer:
  keys_rdd = pair_rdd.keys()  # RDD of just the keys
  keys() is a transformation that extracts only the keys from a pair RDD. Useful for getting unique keys (keys().distinct()) or filtering.

Beginner RDD 39. What is values() on an RDD?
Answer:
  values_rdd = pair_rdd.values()  # RDD of just the values
  values() is a transformation that extracts only the values from a pair RDD. Useful for summing all values (values().reduce(add)) or getting value statistics.

Beginner RDD 40. How do you combine key-value pairs with combineByKey()?
Answer:
  result = rdd.combineByKey(
      createCombiner=lambda v: (v, 1),           # First value seen for a key
      mergeValue=lambda acc, v: (acc[0] + v, acc[1] + 1),  # Combine within partition
      mergeCombiners=lambda acc1, acc2: (acc1[0] + acc2[0], acc1[1] + acc2[1])  # Cross-partition
  )
  # Result: (key, (sum, count)) → can compute average as sum/count
  combineByKey() is the most general aggregation function for pair RDDs. It allows different logic for the first value, subsequent values, and cross-partition merging. aggregateByKey() is a simplified version.
Beginner RDD 41. What is fold() on an RDD?
Answer:
  total = rdd.fold(0, lambda a, b: a + b)  # Sum with zero value 0
  fold() is an action similar to reduce(), but it takes a zero value. The zero value is used as the initial accumulator for each partition and for the final combination. This makes fold() safer than reduce() for empty RDDs (reduce() throws an exception on empty RDDs).

Beginner RDD 42. What is foldByKey() on an RDD?
Answer:
  sums = rdd.foldByKey(0, lambda a, b: a + b)  # Sum values per key with zero value 0
  foldByKey() is like reduceByKey() but with a zero value. It merges values for each key using an associative function and a zero value. The zero value is added to each partition's accumulator and the final combination. Useful when keys may have no values in a partition.

Beginner RDD 43. What is countByKey() on an RDD?
Answer:
  counts = rdd.countByKey()  # Returns {key: count} dict to driver
  countByKey() is an action that counts the number of elements per key. It returns a Python dictionary to the driver. Warning: For large RDDs with many keys, this can overwhelm driver memory. For large-scale counting, use reduceByKey() and then collect a sample.

Beginner RDD 44. What is countApprox() on an RDD?
Answer:
  approx_count = rdd.countApprox(timeout=1000, confidence=0.95)
  countApprox() is an action that estimates the count within a given timeout and confidence level. It samples partitions and extrapolates. Useful when an exact count would take too long and an approximation is acceptable.

Beginner RDD 45. How do you get the top values from an RDD?
Answer:
  top_10 = rdd.top(10)                     # Top 10 (descending)
  top_10 = rdd.top(10, key=lambda x: x[1])  # Top 10 by second element
  min_5 = rdd.takeOrdered(5)               # Bottom 5 (ascending)
  min_5 = rdd.takeOrdered(5, key=lambda x: -x)  # Custom order
  top() and takeOrdered() use a bounded heap (priority queue) to avoid sorting the entire dataset. Much more efficient than sorting and then taking the first N.

Beginner RDD 46. What is sortByKey() on an RDD?
Answer:
  sorted_rdd = rdd.sortByKey(ascending=True)  # Sort pair RDD by key
  sorted_rdd = rdd.sortByKey(ascending=False, numPartitions=10)
  sortByKey() is a transformation that sorts a pair RDD by key. It requires a shuffle. The result is globally sorted. For large datasets, consider DataFrames orderBy() for better optimization.

Beginner RDD 47. How do you filter a key-value RDD by key?
Answer:
  filtered = pair_rdd.filter(lambda kv: kv[0] > 100)     # Key > 100
  filtered = pair_rdd.filter(lambda kv: kv[0] in keep_set)  # Key in a set
  filtered = pair_rdd.lookup("my_key")  # Get all values for a specific key (action)
  filter() works on the (key, value) tuple. lookup() is an action that returns all values for a given key.

Beginner RDD 48. What is the difference between map and foreach?
Answer:
  - map(): A transformation that applies a function to each element and returns a new RDD. It is lazy. The function's return value becomes an element in the new RDD.
  - foreach(): An action that applies a function to each element for side effects (printing, writing to DB). It does NOT return a new RDD. It is eager (triggers execution).
  Use map() when you need to transform data. Use foreach() when you need to perform side effects without returning data.

Beginner RDD 49. What is the difference between count and collect?
Answer:
  - count(): An action that returns the number of elements (Long). Does not bring data to the driver—only a count. Memory-safe for any RDD size.
  - collect(): An action that returns ALL elements as a Python list to the driver. Can cause OOM for large RDDs. Only safe for small RDDs.
  Use count() for sizing. Use collect() only for small RDDs or when you need all data on the driver.

Beginner RDD 50. What is the difference between repartition and coalesce?
Answer: (See also Beginner Theory 29.)
  - repartition(n): Full shuffle. Data is redistributed across the network. Can increase or decrease partitions. Always expensive.
  - coalesce(n): No shuffle (by default). Merges adjacent partitions. Can only decrease partitions efficiently. Cheaper than repartition.
  Use repartition to increase partitions or redistribute data. Use coalesce to decrease partitions without shuffle (e.g., before writing output).

Beginner RDD 51. How do you pipe data through an external command in Spark?
Answer:
  result = rdd.pipe("grep error | wc -l")
  result = rdd.pipe("sort | uniq -c | sort -rn")
  pipe() is a transformation that pipes each partition's data through an external shell command. The command runs on the executor where the partition is processed. Output lines become elements of the resulting RDD. Useful for integrating with external tools (awk, sed, grep, custom scripts).

Beginner RDD 52. What is wholeTextFiles() in Spark?
Answer:
  rdd = sc.wholeTextFiles("path/to/dir/")  # RDD of (filename, full_content) pairs
  Unlike textFile() (one line per element), wholeTextFiles() reads each file as a single string. Each element is a (filename, content) tuple. Useful for processing files as a whole (e.g., JSON/XML documents, log files). Caution: Each file must fit in memory on one executor.

Beginner RDD 53. How do you read binary files using RDDs?
Answer:
  rdd = sc.binaryFiles("path/to/files/")  # RDD of (filename, PortableDataStream)
  data = rdd.map(lambda fn_content: (fn_content[0], fn_content[1].toArray()))  # Get bytes
  binaryFiles() reads each file as binary data. Each element is (filename, PortableDataStream). The PortableDataStream can be converted to bytes. Useful for image processing, serialized data, or custom binary formats.

Beginner RDD 54. What is takeSample() on an RDD?
Answer:
  sample = rdd.takeSample(withReplacement=False, num=10)  # Exactly 10 elements
  sample = rdd.takeSample(True, 20, seed=42)  # 20 elements with replacement
  takeSample() is an action that returns an exact number of elements (unlike sample() which returns a fraction). It scans partitions until the requested number is found. Use when you need a specific count of random elements.

Beginner RDD 55. What is treeAggregate() on an RDD?
Answer:
  total = rdd.treeAggregate(0, lambda a, b: a + b, lambda a, b: a + b)
  treeAggregate() is like aggregate() but performs aggregation in a tree pattern (multi-level) instead of collecting all partition results to the driver. This reduces the load on the driver and is more scalable for large numbers of partitions. Useful for very large RDDs with many partitions.

Beginner RDD 56. What is aggregate() on an RDD?
Answer:
  result = rdd.aggregate(
      zeroValue=(0, 0),
      seqOp=lambda acc, val: (acc[0] + val, acc[1] + 1),   # Within partition
      combOp=lambda acc1, acc2: (acc1[0] + acc2[0], acc1[1] + acc2[1])  # Cross partition
  )
  # Result: (sum, count) → average = sum / count
  aggregate() is an action that combines elements with a zero value and two functions (within-partition and cross-partition). More flexible than reduce()—supports a zero value and different combine/reduce functions. Useful for computing multiple metrics in one pass.

Beginner RDD 57. How do you compute a sum of all numbers in an RDD?
Answer:
  total = rdd.reduce(lambda a, b: a + b)  # Simple sum
  total = rdd.fold(0, lambda a, b: a + b)  # With zero value (safe for empty)
  total = rdd.sum()  # Only for numeric RDDs (SparkStatFunctions)
  reduce() is the simplest. fold() is safer for empty RDDs.

Beginner RDD 58. How do you compute the maximum value in an RDD?
Answer:
  max_val = rdd.reduce(lambda a, b: max(a, b))
  max_val = rdd.max()  # Built-in action
  max_val = rdd.max(key=lambda x: x[1])  # Max by custom key
  max() is a built-in action. reduce() with a max function works for any comparable type.

Beginner RDD 59. How do you compute the minimum value in an RDD?
Answer:
  min_val = rdd.reduce(lambda a, b: min(a, b))
  min_val = rdd.min()  # Built-in action
  min_val = rdd.min(key=lambda x: x[1])  # Min by custom key
  min() is a built-in action. reduce() with a min function works for any comparable type.

Beginner RDD 60. How do you avoid memory issues when using large RDDs?
Answer:
  - Increase partitions: rdd.repartition(more) to reduce per-partition memory.
  - Avoid collect(): Use take(), first(), or write to storage instead.
  - Use mapPartitions: Process data in batches per partition instead of loading all at once.
  - Persist to disk: rdd.persist(StorageLevel.MEMORY_AND_DISK) to spill when memory is insufficient.
  - Checkpoint: Truncate lineage to avoid recomputation overhead.
  - Use DataFrames: Tungsten's off-heap memory is more memory-efficient than Python objects.
  - Avoid groupByKey: Use reduceByKey/aggregateByKey to reduce shuffle data.

Beginner RDD 61. How do you debug an RDD transformation issue?
Answer:
  - Inspect a sample: rdd.take(10) or rdd.first() to see data.
  - Check partitions: rdd.getNumPartitions() and rdd.glom().collect() to see partition contents.
  - Count elements: rdd.count() to verify size.
  - Print schema (if converted to DataFrame): rdd.toDF().printSchema().
  - Use local mode: Run with master("local[*]") for easier debugging.
  - Add logging: Use logging inside map/filter functions.
  - Check lineage: rdd.toDebugString() prints the DAG of transformations.
  - Spark UI: Check the Stages tab for task-level details and errors.

Beginner RDD 62. How do you inspect the contents of a partition in an RDD?
Answer:
  partitions = rdd.glom().collect()  # List of lists (one per partition)
  print(partitions[0])  # First partition's elements
  # Or using mapPartitions:
  rdd.mapPartitions(lambda iter: [list(iter)]).collect()
  # Count elements per partition:
  rdd.mapPartitions(lambda iter: [sum(1 for _ in iter)]).collect()
  glom() converts each partition to a list. Useful for debugging partition size, content, and skew.

Beginner RDD 63. How do you serialize custom objects in an RDD?
Answer:
  - Pickle (default in PySpark): Python objects are pickled when sent to executors. Objects must be picklable (no open file handles, DB connections, etc.).
  - Kryo: For better performance, use Kryo serialization (spark.serializer=org.apache.spark.serializer.KryoSerializer). Register classes for efficiency.
  - Make objects serializable: Implement __getstate__/__setstate__ or use only serializable attributes.
  - Broadcast large objects: Use sc.broadcast() for shared objects instead of including in each task.

Beginner RDD 64. What is RDD lineage and why is it important?
Answer: RDD lineage is the chain of transformations that created an RDD. Each RDD stores references to its parent RDDs and the transformation functions. Importance:
  - Fault tolerance: If a partition is lost, Spark recomputes it by replaying the lineage from the parent RDDs.
  - No data replication: Only the lineage graph (metadata) is stored, not copies of data.
  - Targeted recovery: Only lost partitions are recomputed, not the entire dataset.
  - Debugging: rdd.toDebugString() shows the full lineage DAG.
  - Limitation: Very long lineages make recovery expensive. Checkpointing truncates lineage.

Beginner RDD 65. How do you recover from a failed task using RDD lineage?
Answer: When a task fails (executor crash, OOM, network error):
  1. Spark detects the failed task via heartbeat timeout or task completion callback.
  2. The TaskScheduler retries the task on a different executor (up to spark.task.maxFailures).
  3. If the task's input partition was lost (executor died), Spark traces the RDD lineage to find the last available parent.
  4. It recomputes the lost partition by replaying transformations from the parent RDD.
  5. If cached/checkpointed RDDs exist in the lineage, recovery starts from there instead of the original source.
  This process is automatic and requires no user intervention.

Beginner RDD 66. What happens if an RDD is recomputed after a failure?
Answer: When an RDD is recomputed after failure:
  - Spark replays the transformations from the lost partition's parents to regenerate the data.
  - The recomputation is automatic and transparent to the user.
  - If the RDD was cached, the recomputed partition is cached again (in the new executor's memory).
  - If intermediate RDDs in the lineage were also lost, they are recomputed as well.
  - Performance impact: Recomputation adds latency. If the lineage is long, recovery can be slow. Checkpointing truncates the lineage to limit recomputation cost.
  - Correctness: The recomputed data is identical to the original (transformations are deterministic), ensuring correctness.

Beginner RDD 67. Why do RDDs remain useful for low-level operations?
Answer: RDDs remain useful because:
  - Full control: You control every element and partition—no abstraction layer hiding details.
  - Custom algorithms: For algorithms that can't be expressed with DataFrame/SQL operations (e.g., custom graph algorithms, text processing with complex state).
  - Unstructured data: For data without a schema (raw text, binary, logs).
  - Partition-level operations: mapPartitions, foreachPartition give per-partition control.
  - Custom partitioners: You can define custom partitioning logic.
  - Fine-grained state: Accumulators and broadcast variables work naturally with RDDs.
  - Lower-level debugging: RDD lineage (toDebugString) provides detailed DAG visibility.
  However, for structured data and SQL-like operations, DataFrames are strongly preferred for performance and simplicity.

--- Beginner - DataFrame ---
Beginner DataFrame 1. What is a DataFrame in PySpark?
Answer: A DataFrame is a distributed, immutable collection of data organized into named columns, like a table in a relational database. It has a defined schema (column names and types), is optimized by the Catalyst optimizer and Tungsten engine, supports SQL queries, and is the recommended API for structured data processing in Spark. (See also Beginner Fundamentals 16.)

Beginner DataFrame 2. How do you create a DataFrame from a list of dictionaries?
Answer:
  data = [{"name": "Alice", "age": 30}, {"name": "Bob", "age": 25}]
  df = spark.createDataFrame(data)
  Or with explicit schema:
  from pyspark.sql.types import StructType, StructField, StringType, IntegerType
  schema = StructType([StructField("name", StringType()), StructField("age", IntegerType())])
  df = spark.createDataFrame([("Alice", 30), ("Bob", 25)], schema)

Beginner DataFrame 3. What is the purpose of a schema in a DataFrame?
Answer: A schema defines column names, data types, and nullability. It enables: column pruning (skip unused columns), predicate pushdown (skip irrelevant data), type checking (catch errors at plan time), and optimized serialization (Tungsten uses the schema for efficient binary encoding). A schema can be inferred (inferSchema) or explicitly defined (StructType).

Beginner DataFrame 4. How do you define a schema explicitly?
Answer:
  from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DoubleType
  schema = StructType([
      StructField("name", StringType(), nullable=True),
      StructField("age", IntegerType(), nullable=False),
      StructField("salary", DoubleType(), nullable=True)
  ])
  df = spark.read.schema(schema).csv("path", header=True)
  Explicit schemas avoid the cost of inferSchema and ensure consistent types.

Beginner DataFrame 5. What is select() in DataFrame operations?
Answer: select() returns a new DataFrame with only the specified columns. It is a narrow transformation.
  df.select("name", "age")
  df.select(col("name"), col("age") * 2)
  df.selectExpr("name", "age * 2 as double_age")
  You can select columns by name, use column expressions, or use SQL expressions with selectExpr.

Beginner DataFrame 6. What is withColumn() used for?
Answer: withColumn(colName, col) adds a new column or replaces an existing one.
  df.withColumn("double_age", col("age") * 2)
  df.withColumn("category", when(col("age") > 18, "adult").otherwise("minor"))
  df.withColumn("name", upper(col("name")))  # Replace existing column
  It is a transformation (lazy). Each withColumn creates a new DataFrame reference.

Beginner DataFrame 7. What is drop() in DataFrame APIs?
Answer: drop() returns a new DataFrame with the specified column(s) removed.
  df.drop("unused_col")
  df.drop("col1", "col2", "col3")
  df.drop(df.col_name)  # Using column reference
  It is a narrow transformation. Useful for cleaning up DataFrames before joins or outputs.

Beginner DataFrame 8. What is alias() in DataFrame APIs?
Answer: alias() renames a column or a DataFrame.
  df.select(col("name").alias("employee_name"))  # Column alias
  df.alias("a").join(df2.alias("b"), col("a.id") == col("b.id"))  # DataFrame alias for joins
  Column aliases improve readability and disambiguate columns after joins. DataFrame aliases are essential for self-joins.

Beginner DataFrame 9. How do you rename a column in a DataFrame?
Answer:
  df.withColumnRenamed("old_name", "new_name")
  df.select(col("old_name").alias("new_name"))
  df.selectExpr("old_name as new_name")
  For multiple renames, chain withColumnRenamed calls or use a select with aliases.

Beginner DataFrame 10. What does filter() do on a DataFrame?
Answer: filter() returns rows matching a condition. Equivalent to where().
  df.filter(col("age") > 25)
  df.filter("age > 25 AND city = 'NYC'")  # SQL string
  df.filter((col("age") > 25) & (col("active") == True))
  It is a narrow transformation (no shuffle). Predicate pushdown may push the filter to the data source.

Beginner DataFrame 11. What is where() in DataFrame APIs?
Answer: where() is an alias for filter(). They are functionally identical. Use whichever reads more naturally.
  df.where(col("age") > 25)
  df.where("age > 25")

Beginner DataFrame 12. How do you sort a DataFrame by a column?
Answer:
  df.orderBy("age")  # Ascending
  df.orderBy(col("age").desc())  # Descending
  df.orderBy(col("age").desc(), col("name").asc())  # Multiple keys
  df.sort(col("age").desc())  # sort() is an alias for orderBy()
  orderBy/sort is a wide transformation (requires global shuffle).

Beginner DataFrame 13. How do you group and aggregate data in a DataFrame?
Answer:
  df.groupBy("department").count()
  df.groupBy("department").agg(avg("salary").alias("avg_sal"), sum("revenue").alias("total_rev"))
  df.groupBy("dept", "city").agg({"salary": "avg", "age": "max"})  # Dictionary syntax
  groupBy() returns a GroupedData object. You must call an aggregation function (count, sum, avg, min, max, agg) to get a DataFrame.

Beginner DataFrame 14. What is count() on a DataFrame?
Answer:
  df.count()  # Returns total row count (Long). Triggers a full scan.
  df.groupBy("dept").count()  # Count per group
  count() is an action. For large DataFrames, it requires a full scan. Cache before counting if you also need to show data.

Beginner DataFrame 15. What is distinct() on a DataFrame?
Answer:
  df.distinct()  # Unique rows (all columns considered)
  Returns a new DataFrame with duplicate rows removed. Requires a shuffle. For distinct on a subset of columns, use dropDuplicates(subset).
Beginner DataFrame 16. How do you drop duplicates from a DataFrame?
Answer:
  df.dropDuplicates()  # Remove exact duplicate rows
  df.dropDuplicates(["name", "date"])  # Deduplicate on subset of columns
  dropDuplicates() keeps the first occurrence. It requires a shuffle. Use it when you want to remove duplicates based on specific columns while preserving all columns.

Beginner DataFrame 17. What is union() in DataFrame APIs?
Answer:
  combined = df1.union(df2)  # Concatenate rows (positional column matching)
  union() combines two DataFrames. Columns are matched by position, not name—both DataFrames must have the same number of columns in the same order. Duplicates are kept (like UNION ALL). It is a narrow transformation (no shuffle).

Beginner DataFrame 18. What is unionByName() in DataFrame APIs?
Answer:
  combined = df1.unionByName(df2)  # Match columns by name
  combined = df1.unionByName(df2, allowMissingColumns=True)  # Allow different columns
  unionByName() matches columns by name rather than position, which is safer when column order may differ. Columns missing in one DataFrame are filled with null (with allowMissingColumns=True).

Beginner DataFrame 19. What is join() in DataFrame APIs?
Answer:
  df1.join(df2, "id")                         # Inner join on same-named column
  df1.join(df2, df1.id == df2.id, "left")       # Left join with condition
  df1.join(df2, ["id1", "id2"])                # Multiple join keys
  Join types: inner (default), left, right, outer, left_semi, left_anti, cross. Spark chooses broadcast vs sort-merge based on table sizes.

Beginner DataFrame 20. How do you do an inner join on DataFrames?
Answer:
  result = df1.join(df2, "id")
  result = df1.join(df2, df1.id == df2.id, "inner")
  An inner join returns only rows with matching keys in both DataFrames. Non-matching rows are dropped.

Beginner DataFrame 21. What is a left join in DataFrame operations?
Answer:
  result = df1.join(df2, "id", "left")
  Returns all rows from df1 and matched rows from df2. Unmatched df2 columns are null. Use for enriching data while preserving all left rows.

Beginner DataFrame 22. What is a right join in DataFrame operations?
Answer:
  result = df1.join(df2, "id", "right")
  Returns all rows from df2 and matched rows from df1. Unmatched df1 columns are null.

Beginner DataFrame 23. What is a full join in DataFrame operations?
Answer:
  result = df1.join(df2, "id", "outer")
  Returns all rows from both DataFrames. Unmatched rows from either side have nulls for the other side. Use for data reconciliation.

Beginner DataFrame 24. How do you add a new column based on other columns?
Answer:
  df.withColumn("total", col("price") + col("tax"))
  df.withColumn("full_name", concat(col("first"), lit(" "), col("last")))
  df.withColumn("category", when(col("score") > 90, "A").otherwise("B"))
  withColumn() adds or replaces a column. The expression can reference any existing columns.

Beginner DataFrame 25. How do you split a column into multiple columns?
Answer:
  split_col = split(col("name"), " ")
  df.withColumn("first_name", split_col.getItem(0))
     .withColumn("last_name", split_col.getItem(1))

Beginner DataFrame 26. How do you concatenate multiple columns into one?
Answer:
  df.withColumn("full_name", concat(col("first"), lit(" "), col("last")))
  df.withColumn("info", concat_ws(",", col("name"), col("age"), col("city")))

Beginner DataFrame 27. How do you handle missing values in a DataFrame?
Answer:
  df.na.drop()                              # Drop rows with any null
  df.na.drop(subset=["name", "age"])         # Drop if specific columns are null
  df.na.fill(0)                             # Fill all nulls with 0

Beginner DataFrame 28. How do you fill null values in a DataFrame?
Answer:
  df.na.fill(0)                             # Fill all nulls with 0
  df.na.fill({"name": "unknown", "age": 0})   # Fill per column with specific values
  df.fillna({"name": "unknown"})            # Pandas-style alias
  df.withColumn("salary", when(col("salary").isNull(), lit(0)).otherwise(col("salary")))
  Choose fill values based on business context (0 for numeric, "unknown" for strings, mean for averages).

Beginner DataFrame 29. What is na.drop() in DataFrame operations?
Answer:
  df.na.drop()               # Drop rows with any null value
  df.na.drop(subset=["col1", "col2"])  # Drop if specific columns are null
  df.na.drop(thresh=3)       # Drop if fewer than 3 non-null values
  df.na.drop(how="all")      # Drop only if ALL columns are null
  na.drop() removes rows with null values. Parameters: subset (columns to check), thresh (min non-null count), how (any/all).

Beginner DataFrame 30. How do you convert a DataFrame to an RDD?
Answer:
  rdd = df.rdd  # RDD of Row objects
  rdd = df.rdd.map(lambda row: row.asDict())  # Convert to dicts
  The RDD contains Row objects. You can use all RDD operations on it. Converting to RDD loses Catalyst optimization, so prefer DataFrame operations when possible.

Beginner DataFrame 31. How do you convert an RDD to a DataFrame?
Answer:
  df = rdd.toDF(["name", "age"])  # With column names
  df = spark.createDataFrame(rdd, schema)  # With explicit schema
  df = rdd.map(lambda x: Row(name=x[0], age=x[1])).toDF()  # Using Row objects
  The RDD must contain elements that match the schema (tuples, lists, or Row objects). Explicit schema is recommended for production.

Beginner DataFrame 32. What is explode() in DataFrame APIs?
Answer:
  df.select(col("name"), explode(col("hobbies")).alias("hobby"))
  Input: name='Alice', hobbies=['reading', 'hiking']
  Output: two rows: ('Alice', 'reading'), ('Alice', 'hiking')
  explode_outer() keeps rows with empty arrays (produces null). posexplode() includes position index. explode() converts an array column into multiple rows.

Beginner DataFrame 33. What is collect() on a DataFrame?
Answer:
  rows = df.collect()  # Returns all rows as a list of Row objects to the driver

Beginner DataFrame 45. What is parquet and why is it useful?
Answer: Parquet is a columnar storage file format. It is useful because:
  - Column pruning: Only needed columns are read.
  - Predicate pushdown: Min/max stats skip irrelevant row groups.
  - Compression: Built-in (snappy, gzip) reduces storage and I/O.
  - Schema: Embedded schema, no external definition needed.
  - Splittable: Parallel reads across tasks.
  - Vectorized: Spark's reader uses vectorized decoding.
  Parquet is the recommended format for Spark analytics.

Beginner DataFrame 46. What is the difference between reading a CSV and a Parquet file?
Answer:
  - CSV: Row-based, no built-in schema, no compression, no predicate pushdown, requires full scan. Must specify header/inferSchema. Slower for analytics.
  - Parquet: Columnar, embedded schema, compressed, predicate pushdown, column pruning, splittable, vectorized reads. Faster for analytics. Spark reads the schema automatically.
  Use CSV for data ingestion/exchange. Use Parquet for analytics and storage.

Beginner DataFrame 63. What is a column expression in Spark?
Answer: A column expression is a computation over one or more DataFrame columns. Examples:
  col("age") + 1                    # Arithmetic
  upper(col("name"))               # Function application
  col("age") > 25                   # Boolean comparison
  when(col("age") > 18, "adult").otherwise("minor")  # Conditional
  concat(col("first"), lit(" "), col("last"))  # String operations
  Column expressions are used in select, withColumn, filter, and agg. They are compiled by Catalyst into the physical plan.

Beginner DataFrame 64. How do you use functions like lit(), col(), and expr()?
Answer:

  df.select(col("name"))                      # Reference a column
  df.filter(col("age") > 25)                  # Filter with column reference
  df.select(expr("age * 2 as double_age"))   # SQL expression as column
  df.filter(expr("age > 25 AND city = 'NYC'")) # SQL expression as filter
  lit() creates a literal column. col() references a column by name. expr() parses a SQL expression string into a column.

Beginner DataFrame 65. What is the purpose of the functions module?

Beginner DataFrame 66. How do you use when() and otherwise() conditions?

Beginner DataFrame 69. What is schema validation in a DataFrame?
Answer: Schema validation ensures the DataFrame's schema matches expectations before processing:
  - Explicit schema: Define StructType and use it when reading.
  - Schema enforcement: Delta Lake enforces schema on writes—mismatched records are rejected.
  - Runtime validation: Check df.schema against expected schema and raise errors.
  - mergeSchema: Allow schema evolution (additive) with Parquet/Delta.
  Schema validation prevents downstream errors from type mismatches, missing columns, or unexpected nulls.

Beginner DataFrame 71. What is a nullable column?
Answer: A nullable column can contain null values. In the schema, nullable=True means nulls are allowed. Spark doesn't enforce nullability at write time for most formats (only Delta Lake can enforce it). Nullability affects: aggregate behavior (nulls are skipped), join behavior (null != null), and serialization. Use nullable=False in schema to indicate that a column should never be null, but note this is metadata, not enforced (except Delta).

Beginner DataFrame 73. What is an ArrayType in a DataFrame?

Beginner Scenario-Based 1. Scenario: A daily sales file has duplicate records and null values. How would you clean and validate it in PySpark?
Answer: Step 1: Read with schema inference: df = spark.read.csv("sales.csv", header=True, inferSchema=True). Step 2: Remove duplicates: df = df.dropDuplicates(["order_id", "date"]). Step 3: Handle nulls: For critical columns (order_id, date), drop nulls: df.na.drop(subset=["order_id", "date"]). For non-critical columns, fill: df.na.fill({"region": "unknown", "amount": 0}). Step 4: Validate: Check row count before/after, check for remaining nulls in critical columns, use df.summary() for profile. Step 5: Cache before downstream use if reused.

Beginner Scenario-Based 2. Scenario: A batch job reads millions of rows and takes too long. How would you analyze the bottleneck using Spark concepts?
Answer: 1. Check Spark UI > Stages: Identify the slowest stage. 2. Look at task duration distribution: If one task takes much longer than others, it is likely data skew. 3. Check shuffle read/write: High shuffle indicates wide transformations (join, groupBy). 4. Check the execution plan: df.explain(True) to see the physical plan. 5. Look at GC time: High GC indicates memory pressure. 6. Check input size per task: Large partitions may need repartitioning. 7. Verify partition count: Too few partitions = underutilization; too many = scheduling overhead. 8. Check for unnecessary collect/toPandas. 9. Verify data format: CSV is slower than Parquet. 10. Add appropriate caching for reused DataFrames.

Beginner Scenario-Based 3. Scenario: You need to join a 10 GB fact table with a 2 MB dimension table. Which join strategy would you choose and why?
Answer: Use a broadcast join. The dimension table (2 MB) is well under the autoBroadcastJoinThreshold (default 10 MB). Spark broadcasts the small table to all executors, performing a map-side join. No shuffle of the 10 GB table is needed. This dramatically reduces network I/O and execution time. In code: df_large.join(broadcast(df_small), "key"). If auto-broadcast does not kick in, explicitly call broadcast().

Beginner Scenario-Based 4. Scenario: A DataFrame is performing slowly because of data skew. How would you diagnose and fix the issue?
Answer: Diagnosis: 1. Check Spark UI > Stages: Look for one task taking much longer than others in a shuffle stage. 2. Check partition sizes: df.rdd.mapPartitions(lambda iter: [len(list(iter))]).collect(). 3. Look at the key distribution: df.groupBy("join_key").count().orderBy(col("count").desc()).show(). Fix: 1. Salting: Add a random prefix to hot keys: df.withColumn("salted_key", concat(col("key"), lit("_"), rand())). 2. Broadcast join: If one side is small enough, broadcast it to avoid shuffle. 3. AQE: Enable adaptive query execution (spark.sql.adaptive.enabled=true) which can split skewed partitions automatically (Spark 3.0+). 4. Repartition by a different key to redistribute.

Beginner Scenario-Based 5. Scenario: A pipeline reads a CSV file with malformed rows. How would you handle bad records in PySpark?
Answer: 1. Use mode option: spark.read.csv("file.csv", header=True, mode="DROPMALFORMED") to skip bad rows. Or mode="PERMISSIVE" with columnNameOfCorruptRecord to capture them. 2. Capture bad records: df = spark.read.option("columnNameOfCorruptRecord", "_corrupt_record").csv("file.csv"). 3. Separate: bad = df.filter(col("_corrupt_record").isNotNull()), good = df.filter(col("_corrupt_record").isNull()). 4. Log bad records for investigation. 5. For production, use schema validation and quarantine bad records to a separate table.

Beginner Scenario-Based 6. Scenario: You need to aggregate transaction data by day and region. How would you write the DataFrame logic?

Beginner Scenario-Based 11. Scenario: A batch process repeatedly reads the same dataset. How would caching or persistence help?

Beginner Scenario-Based 14. Scenario: Your PySpark job crashes due to memory pressure. What areas would you inspect first?
Answer: 1. Driver memory: If collect(), toPandas(), or broadcast variables are too large. Increase spark.driver.memory. 2. Executor memory: If tasks OOM. Increase spark.executor.memory or reduce data per partition (repartition). 3. Shuffle spill: Check Spark UI > Stages > Shuffle spill. Reduce shuffle by using reduceByKey instead of groupByKey. 4. Broadcast threshold: If broadcasting too large a table, reduce spark.sql.autoBroadcastJoinThreshold. 5. GC overhead: Check Spark UI > Executors > GC time. Use G1GC, reduce executor memory, or use off-heap. 6. Python memory: UDFs and toPandas can cause Python OOM. 7. Partition size: Large partitions cause task OOM. Repartition to increase parallelism.

Beginner Scenario-Based 15. Scenario: A dataset is too large to fit in memory on a single worker. How does Spark handle it?
Answer: Spark handles large datasets through: 1. Partitioning: Data is split into partitions distributed across workers. Each partition is processed independently. 2. Lazy evaluation: Only needed data is computed. 3. Column pruning: Only requested columns are read. 4. Predicate pushdown: Filters are pushed to the data source. 5. Spill to disk: When memory is insufficient, Spark spills data to disk (shuffle spill, sort spill). 6. Streaming: For very large data, process in micro-batches. 7. Caching with MEMORY_AND_DISK: Cached partitions that do not fit in memory spill to disk. No single worker needs to hold the entire dataset.

Beginner Scenario-Based 16. Scenario: You need to combine streaming-like batch data from multiple sources. What is the safest approach in Spark SQL?

For schema differences, use select to align columns first. For incremental loads, use Delta Lake MERGE to upsert data safely. For validation, add source tags and load timestamps. Example: df1.withColumn("source", lit("A")).unionByName(df2.withColumn("source", lit("B"))).

Beginner Scenario-Based 17. Scenario: A dataset contains hundreds of columns. How would you select only necessary fields efficiently?
Answer: 1. Use column pruning: df.select("col1", "col2", "col3") early in the pipeline. 2. With Parquet, column pruning is automatic—only requested columns are read from disk. 3. With CSV, select early but all columns are still read (no column pruning). 4. Use df.select() before any expensive transformations. 5. Drop unused columns: df.drop("unused_col1", "unused_col2"). 6. For schema management, maintain a list of needed columns and use it programmatically.

Beginner Scenario-Based 19. Scenario: A job is reading a Parquet dataset with mismatched schemas. How would you handle the issue?

Beginner Scenario-Based 41. Scenario: A cluster job fails on one executor, but the dataset is still recoverable. How does Spark handle it?
Answer: Spark handles executor failure through: 1. Detection: The driver detects the lost executor via heartbeat timeout (spark.network.timeout, default 120s). 2. Answer: Standard join (==) does not match nulls (null != null in SQL). Fix options: 1. Use null-safe equality: df1.join(df2, df1.key <=> df2.key) (null <=> null is true). 2. Filter nulls before joining: df1.filter(col("key").isNotNull()).join(df2.filter(col("key").isNotNull()), "key"). 3. Handle nulls explicitly: Fill nulls with a sentinel value before joining, then filter them out after. 4. Use COALESCE: df1.join(df2, coalesce(df1.key, lit("NULL_SENTINEL")) == coalesce(df2.key, lit("NULL_SENTINEL"))).

Beginner Scenario-Based 69. Scenario: You need to process 100 million rows with simple transformations. How would you maximize throughput?
Answer: 1. Use DataFrame API (not RDDs) for Catalyst/Tungsten optimization. 2. Store data in Parquet for fast reads. 3. Ensure sufficient partitions: 100M rows / ~1M rows per partition = ~100 partitions minimum. 4. Use native Spark functions (not UDFs). 5. Apply filters early (predicate pushdown). 6. Select only needed columns (column pruning). 7. Use broadcast join for small lookups. 8. Avoid collect/toPandas. 9. Set appropriate spark.sql.shuffle.partitions. 10. Use coalesce before writing output. 11. Consider batching if writing to a database.

Beginner Scenario-Based 70. Scenario: A team wants to avoid repeated schema definitions. How would you use a DataFrame schema consistently?
Answer: 1. Define schema once in a shared module: schema = StructType([...]). 2. Import and reuse: from schemas import sales_schema; df = spark.read.schema(sales_schema).csv("file.csv"). 3. For Delta tables, schema is stored in the metastore—use spark.read.table("name"). 4. For JSON/Parquet, schema is embedded. 5. Validate at runtime: assert df.schema == expected_schema. 6. Use schema registry for team-wide consistency. 7. Version schemas for evolution tracking.

--- Intermediate - Fundamentals ---
Intermediate Fundamentals 1. Explain how Spark organizes work across the driver, executors, and cluster manager.
Answer: The driver runs the user's main() function, creates the SparkSession, builds the logical plan (DAG), and converts it into stages and tasks via DAGScheduler and TaskScheduler. The cluster manager (YARN, K8s, Standalone) allocates resources and launches executor processes on worker nodes. Executors are JVM processes that run tasks, store cached data, and write shuffle output. The driver dispatches tasks to executors, monitors their progress via heartbeats, and collects results. The driver is the brain; executors are the muscle; the cluster manager is the resource broker.

Intermediate Fundamentals 2. What is the lifecycle of a Spark job from submission to completion?
Answer: 1. User submits code (spark-submit or notebook). 2. Driver process starts and creates SparkSession. 3. Transformations build a logical plan (lazy). 4. An action triggers job submission. 5. DAGScheduler converts the DAG into stages (split at shuffle boundaries). 6. TaskScheduler submits tasks for each stage to executors. 7. Tasks execute on executors (process data, write shuffle output). 8. Results are collected to the driver or written to storage. 9. On failure, tasks/stages are retried. 10. On completion, the driver releases resources and the application exits.

Intermediate Fundamentals 3. How do transformations get translated into tasks?
Answer: 1. Transformations build a logical plan (a tree of relational operators). 2. Catalyst optimizes the plan into a physical plan. 3. The physical plan is converted into RDD operations. 4. DAGScheduler splits the RDD DAG into stages at shuffle boundaries (wide dependencies). 5. Within each stage, partitions are processed by tasks—one task per partition. 6. Narrow transformations are pipelined within a stage (no shuffle). 7. Wide transformations create stage boundaries. 8. Tasks are submitted to executors by the TaskScheduler.

Intermediate Fundamentals 4. What is the difference between application, job, stage, and task in Spark?
Answer: Application: A Spark program (one SparkSession, one driver). Can have multiple jobs. Job: Triggered by an action (collect, count, write). Each action = one job. Stage: A job is divided into stages at shuffle boundaries. Stages run sequentially (map stages before reduce stages). Task: The smallest unit of work. One task processes one partition. Multiple tasks run in parallel within a stage (one per core). Hierarchy: Application > Job > Stage > Task.

Intermediate Fundamentals 5. How does Spark use partitions to parallelize work across executors?
Answer: Partitions are the unit of parallelism. Each partition is processed by one task on one executor core. If a DataFrame has 200 partitions and the cluster has 20 cores, 20 tasks run simultaneously (20-way parallelism). More partitions = more parallelism (up to the number of cores). Too few partitions = underutilization. Too many partitions = scheduling overhead. Optimal: 2-4 partitions per core for good load balancing.

Intermediate Fundamentals 6. What is a dependency graph and how does it relate to Spark execution?
Answer: A dependency graph (DAG) is a directed acyclic graph where nodes are RDDs/DataFrames and edges are transformations. It represents the lineage of data. The DAGScheduler analyzes the graph to determine: 1. Which operations can be pipelined (narrow dependencies, same stage). 2. Where shuffle boundaries occur (wide dependencies, new stage). 3. The order of stage execution. 4. Which partitions to recompute on failure. The DAG is the execution blueprint.

Intermediate Fundamentals 7. How do wide and narrow dependencies affect scheduling?
Answer: Narrow dependencies (map, filter): Each parent partition is used by at most one child partition. Operations can be pipelined within a stage (no shuffle). Efficient. Wide dependencies (groupByKey, join, repartition): Each parent partition contributes to multiple child partitions. Requires a shuffle, creating a stage boundary. Stages with wide dependencies must complete before downstream stages start. Narrow = same stage, wide = new stage. Narrow = fast, wide = expensive (network I/O).

Intermediate Fundamentals 8. Why does Spark prefer immutable distributed data structures?
Answer: Immutability provides: 1. Fault tolerance: If a partition is lost, it can be recomputed from the lineage (the original data + transformations). Mutable data cannot be safely recomputed. 2. Consistency: No race conditions from concurrent modifications. 3. Lineage tracking: The DAG is a record of transformations. With mutable data, the DAG would be invalid. 4. Lazy evaluation: Transformations return new DataFrames/RDDs without modifying the original. 5. Parallelism: Immutable data can be safely shared across tasks without synchronization. 6. Caching: Cached data is stable and can be reused safely.

Intermediate Fundamentals 9. What is the role of serialization in performance tuning?
Answer: Serialization converts objects to bytes for transfer across the network and storage. In Spark: 1. Task serialization: Functions (closures) are serialized and sent to executors. 2. Shuffle data: Key-value pairs are serialized for network transfer. 3. Caching: RDD/DataFrame data can be serialized (MEMORY_ONLY_SER) for compact storage. 4. Broadcast: Variables are serialized before broadcasting. Java serialization (default) is slow. Kryo serialization is 10x faster and more compact. Set spark.serializer=org.apache.spark.serializer.KryoSerializer for better performance.

Intermediate Fundamentals 10. How does Spark compute execution plans for DataFrames?
Answer: Spark uses the Catalyst optimizer with four phases: 1. Parsing: SQL/DataFrame code is parsed into an unresolved logical plan (tree of operators). 2. Analysis: The analyzer resolves column names, types, and functions using the catalog. Produces a resolved logical plan. 3. Optimization: The optimizer applies rules (predicate pushdown, constant folding, column pruning, join reordering). Produces an optimized logical plan. 4. Physical planning: The planner generates one or more physical plans (strategies for joins, aggregations). Cost-based optimization picks the best one. The physical plan is executed as RDD operations.

Intermediate Fundamentals 11. What is the role of DAG in Spark optimization?
Answer: The DAG (Directed Acyclic Graph) enables: 1. Pipeline optimization: Narrow transformations are pipelined into a single stage, reducing intermediate data. 2. Stage splitting: The DAG identifies shuffle boundaries, allowing independent stages to be scheduled efficiently. 3. Fault tolerance: The DAG (lineage) allows recomputation of lost partitions. 4. Parallelism: The DAG shows which partitions can be processed independently. 5. Lazy evaluation: The DAG is built but not executed until an action triggers it, allowing global optimization.

Intermediate Fundamentals 12. Describe how Spark handles data locality for efficient computation.
Answer: Data locality means processing data on the node where it resides, avoiding network transfer. Spark locality levels (best to worst): 1. PROCESS_LOCAL: Data is in the same JVM as the task. 2. NODE_LOCAL: Data is on the same node (different JVM or disk). 3. RACK_LOCAL: Data is on the same rack (requires network transfer within rack). 4. NO_PREF: Data is available from any node equally. 5. ANY: Data is on a different rack. Spark waits for a configurable timeout (spark.locality.wait, default 3s) before jumping to a lower locality level. For HDFS, Spark uses block locations. For cached data, Spark knows which executors hold it.

Intermediate Fundamentals 13. What is the purpose of a partitioner in key-value operations?
Answer: A partitioner determines how key-value pairs are distributed across partitions. Spark provides: 1. HashPartitioner: hash(key) % numPartitions. Default for shuffle operations. 2. RangePartitioner: Sorts keys and divides into roughly equal ranges. Used for sortByKey. 3. Custom partitioner: User-defined logic (e.g., PartitionByDate, PartitionByRegion). A good partitioner ensures even data distribution, reducing skew. For DataFrames, partitioning is controlled by repartition(col) which uses hash partitioning. Custom partitioners are available via RDD API.

Intermediate Fundamentals 14. How do shuffle partitions influence performance?
Answer: Shuffle partitions (spark.sql.shuffle.partitions, default 200) determine the number of output partitions after a wide transformation. Impact: 1. Too few: Large partitions, OOM risk, low parallelism, long task times. 2. Too many: Small partitions, scheduling overhead, small files, resource waste. 3. Optimal: Each partition should be 128MB-1GB. Rule of thumb: set to 2-4x the number of cores. For large datasets, use AQE (Adaptive Query Execution) to coalesce partitions automatically. Tune based on data size: 100GB data / 128MB per partition ~ 800 partitions.

Intermediate Fundamentals 15. What happens when a job has too many small partitions?
Answer: Problems from too many small partitions: 1. Scheduling overhead: Each task has startup cost (~100ms). 10,000 tasks = 1000s of overhead. 2. Small files: Each partition writes a file. Too many small files hurt HDFS and downstream reads. 3. Underutilization: Tasks may finish too quickly, not utilizing the full parallelism of the cluster. 4. Network overhead: For shuffles, many small partitions create many small network transfers. Fix: Use coalesce() to reduce partitions. Set spark.sql.shuffle.partitions appropriately. Use AQE for automatic coalescing.
Intermediate Fundamentals 16. How do you decide the optimal number of partitions?
Answer: Guidelines: 1. Target partition size: 128MB-1GB per partition. Calculate: total_data_size / target_partition_size. 2. Parallelism: 2-4 partitions per executor core (allows for skew and task scheduling flexibility). 3. For shuffle: spark.sql.shuffle.partitions = 2-4x total cores. For 100GB data with 128MB partitions: ~800 partitions. 4. For RDDs: default is spark.default.parallelism. 5. Use df.rdd.getNumPartitions() to check. 6. Adjust based on Spark UI task duration and partition size metrics. 7. AQE can auto-tune. 8. For output: coalesce to reduce files, target 128MB-256MB per output file.

Intermediate Fundamentals 17. What is the relationship between partition count and executor cores?
Answer: Each executor core processes one task at a time. One task processes one partition. So the number of simultaneously running tasks = total_cores = num_executors * cores_per_executor. If partitions > total_cores: tasks are queued and run in waves. If partitions < total_cores: some cores are idle (underutilized). Optimal: partitions should be 2-4x total_cores so that: 1. All cores are utilized. 2. There is enough work to fill a second wave after stragglers finish. 3. Load is balanced even if some partitions are larger. Example: 10 executors * 4 cores = 40 cores. Target: 80-160 partitions.

Intermediate Fundamentals 18. What is memory overhead and how does it affect Spark jobs?
Answer: Memory overhead (spark.executor.memoryOverhead, default = 10% of executor memory) is off-heap memory allocated per executor for: 1. Python worker memory (for PySpark UDFs). 2. Netty buffers (network I/O). 3. Internal JVM overhead (thread stacks, metaspace). 4. Off-heap storage (if enabled). If memory overhead is too low, you get OOM in off-heap or Python workers. Too high, and you waste cluster resources. Increase it when: using heavy Python UDFs, large broadcast variables, or heavy network I/O. Total executor memory = spark.executor.memory + spark.executor.memoryOverhead.

Intermediate Fundamentals 19. What is the difference between cached data and recomputed data?
Answer: Cached data: Stored in memory/disk after first computation. Subsequent actions read from cache (fast, no recomputation). Uses memory resources. Must be explicitly cached (df.cache()). Recomputed data: Not cached. Each action triggers full recomputation from the source (slow but uses no extra memory). Trade-off: Caching trades memory for speed. Use caching when the DataFrame is used multiple times and the computation is expensive. Use recomputation when memory is scarce or the DataFrame is used only once.

Intermediate Fundamentals 20. How does Spark decide whether to spill to disk?
Answer: Spark spills to disk when: 1. Shuffle: During a shuffle, if the shuffle data doesn't fit in memory, Spark spills to local disk. This is controlled by spark.shuffle.spill (default true). 2. Sort: Sorting large datasets spills to disk when the sort buffer is full. 3. Aggregation: reduceByKey/aggregateByKey may spill if the hash table exceeds memory. 4. Cache: With MEMORY_AND_DISK storage level, cached partitions that don't fit in memory are spilled to disk. Spill is automatic and transparent but adds I/O latency. Reduce spill by: increasing executor memory, using more partitions (smaller per-partition data), or using reduceByKey (map-side aggregation) instead of groupByKey.

Intermediate Fundamentals 21. What are the trade-offs of persisting intermediate DataFrames?
Answer: Pros: 1. Avoids recomputation for reused DataFrames. 2. Faster subsequent actions. 3. Reduces source I/O. Cons: 1. Uses memory (or disk) resources. 2. Can cause OOM if too many DataFrames are cached. 3. First action is slower (materialization cost). 4. Must manage lifecycle (unpersist when done). 5. Can cause memory pressure for other jobs. Best practice: Cache only when the DataFrame is used 2+ times and the computation is expensive. Use MEMORY_AND_DISK if memory is uncertain. Always unpersist.

Intermediate Fundamentals 22. Explain the effect of file format on read and write performance.
Answer: CSV: Row-based, no compression, no schema, no column pruning, no predicate pushdown. Slowest for analytics. JSON: Similar to CSV but supports nested types. Slightly faster. Parquet: Columnar, compressed, embedded schema, column pruning, predicate pushdown, splittable. Fastest for analytics. Recommended for Spark. ORC: Columnar, similar to Parquet, optimized for Hive. Avro: Row-based, schema-evolved, good for streaming and data exchange. Delta: Parquet + ACID transactions, schema enforcement, time travel. Best for production. Choose based on use case: Parquet/Delta for analytics, Avro for streaming, CSV for external exchange.

Intermediate Fundamentals 23. Why is Parquet commonly used in PySpark analytics pipelines?
Answer: Parquet is preferred because: 1. Columnar storage: Only needed columns are read (column pruning), reducing I/O. 2. Predicate pushdown: Min/max statistics per row group skip irrelevant data. 3. Compression: Built-in (snappy default) reduces storage and I/O. 4. Splittable: Parallel reads across tasks. 5. Schema embedded: No external schema needed. 6. Vectorized reads: Spark uses vectorized decoding for fast reads. 7. Nested types: Supports arrays, structs, maps. 8. Wide adoption: Supported by Spark, Hive, Presto, Impala, and more. For analytics workloads, Parquet is 5-10x faster than CSV.

Intermediate Fundamentals 24. What is columnar storage and how does it help queries?
Answer: Columnar storage stores data by column, not by row. In a row-based format (CSV), each row is stored contiguously. In a columnar format (Parquet), each column is stored contiguously. Benefits: 1. Column pruning: If a query selects 3 of 50 columns, only 3 columns are read from disk. 2. Compression: Similar values in a column compress better (e.g., run-length encoding, dictionary encoding). 3. Vectorized processing: Column data is processed in batches (vectors) for CPU cache efficiency. 4. Predicate pushdown: Statistics (min/max) per column block skip data that doesn't match the filter. Columnar is ideal for analytical queries (aggregations, filters, column selection) but worse for row-level updates.

Intermediate Fundamentals 25. How does Spark process nested data types?
Answer: Spark supports nested types: StructType (struct), ArrayType (array), and MapType (map). Processing: 1. Struct fields: Accessed with dot notation: col("address.city"). Can be nested: col("a.b.c"). 2. Arrays: Exploded into rows with explode(). Elements accessed with getItem() or []. Functions: array_contains, size, array_distinct, array_sort, flatten. 3. Maps: Accessed by key: col("settings")["theme"]. Functions: map_keys, map_values, map_concat. 4. Schema: Defined with StructType containing StructField entries. 5. JSON: from_json() parses JSON strings into structs; to_json() converts back. 6. Flattening: Select nested fields directly to flatten structs.

Intermediate Fundamentals 26. Why is schema inference sometimes risky?
Answer: Schema inference (inferSchema=True) scans the data to determine column types. Risks: 1. Performance: Inference requires an extra pass over the data (slower reads). 2. Incorrect types: If a column has mixed types (e.g., mostly integers but some strings), inference may choose the wrong type. 3. Inconsistency: Different files may infer different schemas, causing merge issues. 4. Null handling: Inference may not distinguish between truly null and empty string. 5. Type mismatch: Inferred DoubleType vs IntegerType can cause issues in joins. Best practice: Define explicit schemas for production pipelines. Use inference only for exploration.

Intermediate Fundamentals 27. What is the cost of using Python UDFs in Spark SQL?
Answer: Python UDFs are expensive because: 1. Serialization: Data is serialized from JVM (Spark) to Python (worker) and results are serialized back. 2. No Catalyst optimization: UDFs are black boxes—Catalyst cannot push down predicates, prune columns, or reorder operations through them. 3. No Tungsten: UDFs bypass Tungsten's off-heap, vectorized execution. 4. Python GIL: Python's Global Interpreter Lock limits true parallelism within a Python worker. 5. Memory: Each executor spawns a Python worker process, consuming additional memory. 6. Performance: UDFs are 3-100x slower than equivalent built-in functions. Mitigation: Use built-in functions, SQL expressions, or pandas_udf (vectorized UDF using Arrow).

Intermediate Fundamentals 28. How do you reason about computational complexity in distributed processing?
Answer: Consider: 1. Data size (N): How much data is processed? 2. Complexity per element: O(1), O(log N), O(N) for operations like sort, join, aggregate. 3. Shuffle cost: Wide transformations add O(N) network I/O. 4. Number of stages: Each stage boundary adds latency (shuffle read + write). 5. Parallelism: P partitions reduce wall time by P for embarrassingly parallel operations. 6. Skew: Worst-case task determines total wall time (not average). 7. Memory: Per-partition memory, not total memory, determines OOM. 8. I/O: Disk reads, network transfers, and writes are often the bottleneck. Total time ~ max(partition_processing_time) + shuffle_cost + scheduling_overhead.

Intermediate Fundamentals 29. What does a shuffle boundary mean in Spark execution?
Answer: A shuffle boundary is a point in the DAG where data must be redistributed across partitions (a wide dependency). At a shuffle boundary: 1. Data from all upstream partitions is written to local disk (shuffle write). 2. Downstream tasks fetch data from across the cluster (shuffle read). 3. A new stage begins. Shuffle boundaries are created by: groupBy, join, repartition, distinct, sortBy, and any wide transformation. Shuffle boundaries are the most expensive part of Spark execution—minimize them for performance.

Intermediate Fundamentals 30. How does Spark minimize data movement during joins?
Answer: 1. Broadcast join: If one side is small (< autoBroadcastJoinThreshold, default 10MB), it is broadcast to all executors. No shuffle of the large table. 2. Sort-merge join: Both sides are sorted by key and merged. Requires sorting but is scalable. 3. Shuffle hash join: The smaller side is shuffled and hashed. Used when one side is small enough to fit in memory but too large for broadcast. 4. Predicate pushdown: Filters are pushed before the join to reduce data. 5. Column pruning: Only join columns are read. 6. AQE: Can dynamically switch join strategy based on runtime statistics. 7. Bucketing: Pre-partitioning by join key avoids shuffle.
Intermediate Fundamentals 31. What affects the size of a Spark task?
Answer: Task size is determined by the partition size, which depends on: 1. Input data size per partition: Total data / number of partitions. A 100GB file with 200 partitions = ~500MB per partition. 2. Schema and column count: Wide rows (many columns) make partitions larger in memory. 3. Compression: Compressed data (Parquet) is smaller on disk but expands in memory. 4. Filters and projections: If filters are pushed down, less data is read. Column pruning reduces data read. 5. Repartitioning: repartition(n) changes partition count and thus per-task size. 6. Shuffle: After a shuffle, the output partition count (spark.sql.shuffle.partitions) determines task size. 7. Joins: Join operations can amplify data size (e.g., one-to-many joins). 8. Data types: String columns consume more memory than numeric columns. Ideal task processing time is 100ms-10s. Tasks shorter than 100ms have scheduling overhead; tasks longer than 10s risk long recovery times on failure.

Intermediate Fundamentals 32. Why is data skew a performance problem?
Answer: Data skew occurs when one or a few partitions contain significantly more data than others. This is problematic because: 1. Straggler effect: The largest partition's task takes the longest, and the stage cannot complete until all tasks finish. One slow task delays the entire stage. 2. Underutilization: While the skewed task runs, other executors are idle (they finished their smaller partitions). 3. OOM risk: The skewed partition may not fit in executor memory, causing spills or OOM errors. 4. Cascading delays: Downstream stages must wait for the skewed stage to complete. 5. Unpredictable performance: The same job may run fine on one dataset but fail or slow down on another with different key distribution. Common causes: uneven key distribution (e.g., one customer has 90% of transactions), null keys all mapping to one partition, or temporal concentration (all events on one day). Mitigations: salting, broadcast joins for small tables, adaptive query execution (AQE) skew joining, custom partitioners.

Intermediate Fundamentals 33. How do you detect skew in a Spark job?
Answer: Detect skew using these methods: 1. Spark UI: In the Stages tab, look at the task duration distribution. If the max task time is much larger than the median (e.g., one task takes 10 minutes while others take 10 seconds), that indicates skew. 2. Summary statistics: The Stages tab shows min, 25th, median, 75th, max task duration and data size. A large gap between median and max indicates skew. 3. Event timeline: The Stages tab has an event timeline that shows when tasks finish. If most finish quickly but a few drag on, that's skew. 4. Partition inspection: Use df.rdd.glom().map(len).collect() to see the number of rows per partition. If one partition has significantly more rows, that's skew. 5. Key distribution: Group by the key and count: df.groupBy("key").count().orderBy(col("count").desc()).show(). If one key dominates, join/groupBy on that key will be skewed. 6. Shuffle read/write metrics: In the Spark UI, compare shuffle read sizes across tasks. Uneven shuffle read indicates skew in the shuffle stage. 7. AQE metrics: If AQE is enabled, it logs when it detects and splits skewed partitions.

Intermediate Fundamentals 34. What is the significance of executor memory overhead?
Answer: Executor memory overhead (spark.executor.memoryOverhead) is off-heap memory allocated per executor beyond the JVM heap. It covers: 1. Python worker memory: PySpark runs Python UDFs in separate processes; their memory comes from overhead. 2. Netty buffers: Network I/O buffers for shuffle data transfer. 3. JVM internal overhead: Thread stacks, metaspace, direct byte buffers, and code cache. 4. Off-heap storage: If spark.memory.offHeap.enabled=true, off-heap execution memory comes from this pool. Default: 10% of executor memory (min 384MB). Significance: If overhead is too low, Python workers OOM or Netty runs out of buffer space, causing executor crashes. If too high, you waste cluster resources (total container = executor memory + overhead). Tune it up when: using heavy Python UDFs, large pandas UDFs, large broadcast variables, or high network I/O. In Databricks, it's often auto-configured but can be adjusted. The total container request to the cluster manager is spark.executor.memory + spark.executor.memoryOverhead.

Intermediate Fundamentals 35. What is the purpose of spill and how does it impact latency?
Answer: Spill is the process of writing in-memory data to local disk when it exceeds available memory. It occurs during: 1. Shuffle: Shuffle data that doesn't fit in memory is spilled to local disk before being fetched by downstream tasks. 2. Sort: Sort operations spill sorted runs to disk and merge them later. 3. Aggregation: Hash aggregations that exceed memory spill the hash table to disk. 4. Join: Sort-merge join spills sorted data. Impact on latency: 1. Disk I/O: Spill adds disk read/write latency (10-100x slower than memory). 2. CPU overhead: Serializing/deserializing and compressing/decompressing spilled data adds CPU cost. 3. Increased wall time: The task takes longer because of the additional I/O. 4. Reduced throughput: More disk I/O competes with other tasks for disk bandwidth. Mitigation: Increase executor memory, increase partition count (smaller per-partition data), use reduceByKey (map-side aggregation) instead of groupByKey, use built-in functions instead of Python UDFs, tune spark.shuffle.file.buffer and spark.shuffle.spill.numElementsForceSpillThreshold.

Intermediate Fundamentals 36. What is dynamic allocation and when is it useful?
Answer: Dynamic allocation allows Spark to dynamically adjust the number of executors based on workload. It adds executors when there are pending tasks and removes idle executors after a timeout. Configuration: spark.dynamicAllocation.enabled=true, spark.dynamicAllocation.minExecutors, spark.dynamicAllocation.maxExecutors, spark.dynamicAllocation.initialExecutors, spark.dynamicAllocation.executorIdleTimeout (default 60s), spark.dynamicAllocation.schedulerWaitTimeout (default 5s). When useful: 1. Mixed workloads: Jobs with varying resource needs throughout execution benefit from scaling up during heavy phases and down during light phases. 2. Shared clusters: Multiple applications can share cluster resources more efficiently—idle executors are returned to the pool. 3. Cost optimization: In cloud environments (AWS, GCP, Azure), you only pay for the executors you use. Dynamic allocation reduces cost by removing idle executors. 4. Unpredictable workloads: When you don't know the data size in advance, dynamic allocation adapts. Caveats: Not ideal for streaming workloads (constant resource needs). Requires external shuffle service (spark.shuffle.service.enabled) to preserve shuffle data when executors are removed.

Intermediate Fundamentals 37. How does adaptive query execution change the execution plan?
Answer: Adaptive Query Execution (AQE), introduced in Spark 3.0, dynamically adjusts the query plan at runtime based on actual execution statistics. Key features: 1. Coalesce shuffle partitions: After a shuffle, AQE merges small adjacent partitions to reduce the number of tasks. This eliminates the need to manually tune spark.sql.shuffle.partitions. 2. Switch join strategy: AQE can switch from sort-merge join to broadcast join at runtime if it discovers one side is smaller than the broadcast threshold. 3. Skew join handling: AQE detects skewed partitions (partition size >> median) and splits them into smaller sub-partitions, distributing the load. This mitigates data skew without manual salting. Configuration: spark.sql.adaptive.enabled=true (default true in Spark 3.2+). AQE runs between stages—it collects statistics from completed stages and re-plans subsequent stages. This means the plan is not fully determined at submission time; it adapts as the job runs. AQE is particularly valuable for complex queries with multiple joins where the optimal plan depends on actual data sizes and distributions.

Intermediate Fundamentals 38. What are predicate pushdowns and why do they matter?
Answer: Predicate pushdown moves filter conditions as close to the data source as possible, reducing the amount of data read into Spark. Examples: 1. Parquet/ORC: When reading Parquet files, Spark pushes filters (e.g., year = 2023) to the file reader, which skips row groups whose min/max statistics don't match the predicate. This avoids reading irrelevant data blocks. 2. JDBC: When reading from a database via JDBC, Spark pushes filters into the SQL query (WHERE clause), so the database filters the data before sending it to Spark. 3. Partition pruning: Filters on partition columns (e.g., date = '2023-01-01') skip entire partitions—no files are read. 4. Delta Lake: Data skipping uses min/max statistics on Z-ordered columns to skip irrelevant files. Why it matters: 1. Reduced I/O: Less data read from disk/network. 2. Faster execution: Fewer rows to process. 3. Lower memory: Smaller in-memory footprint. 4. Cost savings: In cloud environments, less data scanned = lower cost. Catalyst automatically pushes predicates down when possible. To verify, check the explain plan for PushedFilters in the FileScan node.

Intermediate Fundamentals 39. How do stats-based optimizations work in Spark SQL?
Answer: Spark SQL uses statistics for cost-based optimization (CBO). Statistics include: 1. Table-level stats: Row count, total size (bytes). 2. Column-level stats: Distinct count (cardinality), min, max, null count, average length. How they're used: 1. Join reordering: CBO chooses the join order that minimizes intermediate result size (e.g., joining the most selective filters first). 2. Join strategy selection: If stats show one side is small enough for broadcast, Spark uses BroadcastHashJoin. 3. Cardinality estimation: Stats help estimate the output size of each operator, which guides plan selection. 4. Partition pruning: Stats on partition columns help skip irrelevant partitions. Collecting stats: ANALYZE TABLE db.table COMPUTE STATISTICS (table-level) or ANALYZE TABLE db.table COMPUTE STATISTICS FOR COLUMNS col1, col2 (column-level). In Databricks, Delta Lake auto-collects stats. Without stats, Spark uses heuristics (size-based estimates) which may lead to suboptimal plans. With accurate stats, CBO can significantly improve performance for multi-join queries. Note: AQE supplements CBO with runtime statistics.

Intermediate Fundamentals 40. What is a broadcast variable and how does it reduce network transfer?
Answer: A broadcast variable is a read-only variable cached on each executor, sent only once per executor instead of with every task. Usage: broadcast_var = spark.sparkContext.broadcast(large_dict). On executors: value = broadcast_var.value. How it reduces network transfer: Without broadcast: If each task needs a 100MB lookup table, and there are 1000 tasks across 50 executors, the table is sent 1000 times = 100GB total network traffic. With broadcast: The table is sent once per executor = 50 * 100MB = 5GB total. This is a 20x reduction. Use cases: 1. Lookup tables: Join a small dimension table with a large fact table (broadcast join). 2. Configuration: Distribute configuration parameters to all tasks. 3. Machine learning models: Broadcast model weights for distributed inference. 4. Reference data: Small dictionaries, maps, or sets needed by UDFs. Key properties: Broadcast variables are read-only (cannot be modified after broadcast). They are cached in memory (or disk if memory is insufficient) on each executor. They are automatically cleaned up when the driver terminates or when unpersist() is called. In Spark SQL, broadcast joins use broadcast variables internally: broadcast(small_df) or automatic broadcast when the table is under spark.sql.autoBroadcastJoinThreshold.

Intermediate Fundamentals 41. What is the difference between broadcast and join optimization?
Answer: Broadcast and join optimization are related but distinct concepts: 1. Broadcast variable: A mechanism to distribute read-only data (e.g., a lookup dictionary) to all executors efficiently. It's a general-purpose tool usable in RDD and DataFrame code. 2. Broadcast join: A specific join strategy where the smaller side of a join is broadcast to all executors as a broadcast variable, enabling a map-side join (no shuffle of the large table). The broadcast join is an optimization that uses the broadcast mechanism internally. Other join optimizations include: sort-merge join (scalable for large-large joins), shuffle hash join (when one side fits in memory after shuffle), and AQE join re-planning (dynamically switching strategies at runtime). In summary: broadcast is a data distribution mechanism; broadcast join is a join strategy that leverages it. Other join optimizations (join reordering, predicate pushdown, bucketing) are separate from the broadcast mechanism itself.

Intermediate Fundamentals 42. How does Spark leverage local file system cache for repeated reads?
Answer: Spark leverages the local file system cache in several ways: 1. OS page cache: When Spark reads data from disk (local or network storage), the OS caches recently read blocks in the page cache. Subsequent reads of the same blocks are served from memory, bypassing disk I/O. This is automatic and requires no configuration. 2. HDFS data locality: When running with HDFS, Spark tries to schedule tasks on nodes that have the data blocks locally. The first read populates the page cache; subsequent reads are cache hits. 3. Spark cache/persist: Spark can cache DataFrames/RDDs in executor memory (MEMORY_ONLY) or memory + disk (MEMORY_AND_DISK). This is application-level caching controlled by df.cache() or rdd.persist(). 4. Shuffle data: Shuffle output is written to local disk. Downstream tasks read it from local disk, benefiting from the page cache. 5. Broadcast data: Broadcast variables are cached on each executor's local disk (if they don't fit in memory) and read from local disk on subsequent uses. 6. Iterative algorithms: ML algorithms (e.g., ALS, KMeans) that re-read the same data benefit greatly from caching. Best practice: For repeated reads, use df.cache() for in-memory caching. For single reads, rely on OS page cache. In cloud environments (S3, ADLS), the page cache is less effective because data is read over the network—use Spark caching or Delta caching instead.

Intermediate Fundamentals 43. What is the purpose of checkpointing for iterative workloads?
Answer: Checkpointing saves an RDD/DataFrame to stable storage (HDFS, S3) to truncate the lineage graph. In iterative workloads (e.g., machine learning algorithms, graph processing), the lineage DAG grows longer with each iteration because each transformation adds a new node to the graph. Problems with long lineages: 1. Recovery cost: If a partition is lost, Spark must recompute from the source through all transformations, which gets increasingly expensive with each iteration. 2. Stack overflow: Very deep lineage chains can cause stack overflow errors in the DAGScheduler. 3. Memory for lineage metadata: The driver must maintain the full lineage graph in memory. Checkpointing solves this by: 1. Saving the RDD to stable storage (sc.setCheckpointDir("hdfs://checkpoint-dir"); rdd.checkpoint()). 2. After checkpointing, the lineage is truncated—the checkpointed RDD's parents are removed from the DAG. 3. If a partition is lost, it's read from the checkpoint file (fast) instead of recomputed (slow). Usage: Set checkpoint directory early. Call checkpoint() on the RDD after each iteration (or every few iterations). The checkpoint is materialized lazily—trigger it with an action (e.g., rdd.count()). Difference from caching: Checkpointing writes to stable storage and truncates lineage; caching stores in memory and preserves lineage.

Intermediate Fundamentals 44. How do lineage and recomputation interact during failure recovery?
Answer: When a partition is lost (executor failure, node crash, disk failure), Spark uses lineage to recover: 1. Detection: The driver detects the failure (task failure, heartbeat timeout, or fetch failure). 2. Lineage tracing: The DAGScheduler traces the lost partition's lineage backward to find the nearest cached or checkpointed ancestor, or the source data. 3. Recomputation: Spark re-submits tasks to recompute only the lost partition (not the entire dataset). For narrow dependencies, only the specific parent partitions are recomputed. For wide dependencies (shuffle), all parent partitions may be needed. 4. Recomputation is automatic: No user intervention required. The driver resubmits the failed task to a different executor. 5. Caching reduces recomputation: If an intermediate RDD/DataFrame is cached on a surviving executor, recovery starts from the cache instead of the source. 6. Checkpointing eliminates recomputation: If the RDD is checkpointed, the lost partition is read from stable storage. Trade-off: Lineage-based recovery is efficient (no data replication) but can be expensive for very long chains. Checkpointing trades storage for faster recovery. In practice, combine caching (for frequently used DataFrames) and checkpointing (for long iterative pipelines).

Intermediate Fundamentals 45. What happens when a transformation references a non-serializable object?
Answer: When a transformation (e.g., map, filter) references a variable from the driver, Spark must serialize that variable and send it to executors as part of the task closure. If the referenced object is not serializable (e.g., a database connection, a file handle, a SparkSession, a SparkContext, a custom class without Serializable), Spark throws a NotSerializableException at task submission time. This is a common error in PySpark. Causes: 1. Referencing a SparkSession or SparkContext inside a UDF or RDD transformation—these are JVM objects that cannot be serialized. 2. Using a database connection object inside a map function—connections are not serializable. 3. Custom classes that don't implement Serializable (Java/Scala) or can't be pickled (Python). Solutions: 1. Don't reference Spark objects inside transformations. Use broadcast variables for shared data. 2. For database connections, create them inside the task (e.g., in mapPartitions, open a connection per partition). 3. For custom Python classes, ensure they are picklable (no file handles, no thread locks). 4. Use functools.partial or closures carefully—avoid capturing non-serializable objects. 5. For Java/Scala, implement Serializable or use @transient for non-serializable fields.

Intermediate Fundamentals 46. How does Spark interpret Python functions in UDFs?
Answer: In PySpark, a Python UDF is a user-defined function written in Python that operates on DataFrame columns. Execution flow: 1. Registration: udf = spark.udf.register("my_udf", my_python_func, ReturnType()) or using @udf decorator. 2. When the UDF is called in a DataFrame operation, Spark serializes the function (using cloudpickle) and sends it to each executor. 3. On each executor, Spark starts a Python worker process (separate from the JVM). 4. For each row (or batch), the executor serializes the input data (using Arrow or pickle), sends it to the Python worker, the Python worker executes the function, and sends the result back (serialized again). 5. The JVM deserializes the result and integrates it into the DataFrame. Performance implications: 1. Serialization overhead: Each row's data crosses the JVM-Python boundary twice (in and out). 2. No Catalyst optimization: UDFs are opaque to Catalyst—no predicate pushdown, no column pruning through the UDF. 3. No Tungsten: UDFs bypass the Tungsten execution engine. 4. Python GIL: Each Python worker processes one task at a time. Mitigation: Use pandas_udf (vectorized UDF with Arrow) for batch processing—10-100x faster than row-at-a-time UDFs. Better yet, use built-in Spark SQL functions whenever possible.

Intermediate Fundamentals 47. Why are DataFrames usually preferred over RDDs for SQL-like transformations?
Answer: DataFrames are preferred because: 1. Catalyst optimizer: DataFrames have a logical plan that Catalyst optimizes (predicate pushdown, column pruning, join reordering, constant folding). RDDs are opaque—the optimizer cannot see inside the lambda functions. 2. Tungsten execution: DataFrames use Tungsten's off-heap memory, binary processing, and code generation, which is significantly faster than RDD's Python-based processing. 3. SQL interface: DataFrames support SQL queries (spark.sql("SELECT ... FROM table")), enabling BI tools and SQL users to use Spark. 4. Schema: DataFrames have a schema (column names and types), enabling type-safe operations and schema validation. RDDs are untyped (Python objects). 5. Built-in functions: Spark SQL has hundreds of built-in functions (string, date, math, aggregate, window) that are optimized. RDDs require custom Python functions. 6. Performance: For equivalent operations, DataFrames are typically 10-100x faster than RDDs due to Catalyst + Tungsten. 7. Interoperability: DataFrames integrate with Delta Lake, BI tools, and the broader Spark ecosystem. When to use RDDs: When you need fine-grained control over partitioning, have non-tabular data, or need low-level algorithms not expressible as DataFrame operations.

Intermediate Fundamentals 48. How do DataFrames translate to Catalyst plans?
Answer: A DataFrame operation translates to a Catalyst plan through these stages: 1. Construction: Each DataFrame operation (select, filter, join, groupBy) creates a logical operator node (Project, Filter, Join, Aggregate). These are chained into an unresolved logical plan—a tree of operators. 2. Analysis: The Analyzer resolves column names, types, and function calls using the Catalog (table metadata, function registry). Ambiguous or non-existent columns cause analysis errors. Produces a resolved logical plan. 3. Optimization: The Catalyst optimizer applies rule-based optimizations: predicate pushdown (move filters before joins), column pruning (remove unused columns), constant folding (evaluate constants at compile time), join reordering (based on statistics). Produces an optimized logical plan. 4. Physical planning: The SparkPlanner generates physical operators: FileScan vs TableScan, BroadcastHashJoin vs SortMergeJoin, HashAggregate vs SortAggregate. Multiple physical plans may be generated; cost-based optimization selects the best. 5. Code generation: Tungsten generates Java bytecode for the physical plan using whole-stage code generation, fusing multiple operators into a single function for each stage. To inspect: df.explain(true) shows all four plans.

Intermediate Fundamentals 49. Explain the role of the storage layer in Spark execution.
Answer: The storage layer is where data is read from and written to. It affects Spark performance more than any other component because I/O is typically the bottleneck. Key aspects: 1. File format: Columnar formats (Parquet, ORC, Delta) enable column pruning, predicate pushdown, and compression—dramatically reducing I/O. Row formats (CSV, JSON) require full scans. 2. Compression: Snappy (fast, moderate compression), Gzip (slow, high compression), LZO (splittable). Compression reduces disk I/O but adds CPU cost. 3. Partitioning: Partitioning data by date, region, or category allows Spark to skip irrelevant partitions (partition pruning), reducing data scanned. 4. Bucketing: Pre-partitioning data by join key avoids shuffle in bucketed joins. 5. Data layout: Z-ordering (Delta Lake) co-locates frequently co-filtered columns, improving data skipping. 6. Storage location: Local disk (fast, limited), HDFS (distributed, replicated), cloud object stores (S3, ADLS, GCS—scalable, but higher latency). 7. Caching: Spark's in-memory cache (MEMORY_ONLY, MEMORY_AND_DISK) reduces repeated I/O. The storage layer determines how much data Spark reads, how fast it reads, and how much network transfer is needed. Choosing the right format (Parquet/Delta) and partitioning strategy is the single most impactful performance optimization.

Intermediate Fundamentals 50. What is the difference between physical memory and virtual memory in Spark?
Answer: Physical memory is the actual RAM on the machine. Virtual memory is the OS abstraction that combines physical RAM with disk swap space. In Spark: 1. Executor JVM heap (spark.executor.memory): Allocated from physical memory. The JVM heap is where Spark stores execution memory (shuffles, joins, aggregations) and storage memory (cached blocks). 2. Off-heap memory (spark.memory.offHeap.size): Allocated outside the JVM heap, directly from the OS. Managed by Spark's Tungsten engine for binary processing. Avoids GC overhead. 3. Executor memory overhead: Off-heap memory for Python workers, Netty buffers, and JVM internals. 4. OS page cache: The OS uses free physical memory to cache recently read file blocks. This is not part of any Spark memory allocation but significantly speeds up repeated reads. 5. Spill to disk: When execution or storage memory is full, Spark spills data to local disk. This uses virtual memory (disk-backed). 6. Swapping: If the total process memory exceeds physical RAM, the OS swaps to disk, causing severe performance degradation. Avoid by sizing executors to fit in physical memory. Key distinction: Spark memory allocations (heap, off-heap, overhead) are bounded and managed. OS page cache and swap are unmanaged by Spark but affect performance. Best practice: Size executors so that executor memory + overhead + page cache fits in the node's physical RAM to avoid swapping.

Intermediate Fundamentals 51. How do partitions map to tasks for a given transformation?
Answer: Each partition maps to exactly one task. For a given transformation: 1. Narrow transformation (map, filter, select): Each input partition maps to one output partition. N input partitions = N tasks. No data exchange between partitions. Tasks are pipelined within the same stage. 2. Wide transformation (groupBy, join, repartition): Each input partition may contribute to multiple output partitions. The number of output partitions is determined by spark.sql.shuffle.partitions (default 200) or the repartition argument. After the shuffle, each output partition = one task in the next stage. 3. Stage composition: A stage consists of all narrow transformations pipelined together. The number of tasks in a stage = the number of partitions at the stage's input. 4. Example: df.filter(col("x") > 10).select("x", "y").groupBy("x").agg(sum("y")): The filter and select are narrow (same stage, N tasks). The groupBy creates a shuffle boundary. The aggregate stage has spark.sql.shuffle.partitions tasks (default 200). 5. Parallelism: At any time, the number of simultaneously running tasks = min(partitions_in_current_stage, total_executor_cores). More partitions than cores means tasks run in waves.

Intermediate Fundamentals 52. What is the effect of a large number of small files?
Answer: Too many small files causes several problems: 1. Too many tasks: Each file becomes at least one partition (or a portion of a partition). 10,000 small files = 10,000 tasks. Each task has ~100ms scheduling overhead = 1000s wasted. 2. Driver overhead: The driver must track and schedule all tasks. 10,000+ tasks cause driver memory pressure and slower scheduling. 3. HDFS NameNode pressure: HDFS stores metadata for each file. Millions of small files exhaust NameNode memory. 4. Small read I/O: Reading many small files is slower than reading one large file of the same total size due to file open/close overhead and random I/O patterns. 5. Shuffle overhead: If the small-file stage feeds into a shuffle, the shuffle has many tiny inputs, increasing network overhead. 6. Output problems: Writing many small output files causes the same problems downstream. Mitigations: 1. coalesce(n) to reduce partition count before writing. 2. Use Hadoop's CombineFileInputFormat to combine small files into larger splits. 3. Use Delta Lake OPTIMIZE to compact small files. 4. Set spark.sql.files.maxPartitionBytes (default 128MB) to control partition size. 5. Target 128MB-256MB per output file.

Intermediate Fundamentals 53. How does Spark read compressed data files?
Answer: Spark reads compressed files using the Hadoop compression codec infrastructure. For each file format: 1. Text files (CSV, JSON): Spark uses the compression codec inferred from the file extension (.gz, .snappy, .lzo, .bzip2, .zstd). It decompresses on the fly during read. Gzip files are NOT splittable—one gzip file = one partition (no parallel reading). Bzip2, LZO (with index), and Zstd are splittable. 2. Parquet/ORC: Compression is built into the format (snappy, gzip, lz4, zstd, brotli). The reader decompresses column chunks on demand—only the columns being read are decompressed. Parquet files are always splittable regardless of compression because column chunks are independently compressed. 3. Configuration: spark.sql.compression.codec (for writing), io.compression.codecs (Hadoop-wide codec list). 4. Performance: Snappy is fast (low CPU, moderate compression). Gzip is slow (high CPU, high compression). LZO and Zstd offer a good balance. 5. Best practice: Use Parquet with Snappy for analytics. Avoid gzipped CSV/JSON for large datasets (not splittable, no column pruning). Use Parquet with Zstd for higher compression ratios when storage is a concern.

Intermediate Fundamentals 54. When would you choose to repartition a DataFrame?
Answer: Use repartition() when you need to increase or control the number of partitions, or when you need to redistribute data by a specific key. Scenarios: 1. Increase parallelism: If the current partition count is too low (e.g., reading a single large file = 1 partition), repartition(100) creates 100 partitions for parallel processing. 2. Before a shuffle-based join: If both sides of a join have very different partition counts, repartitioning can balance the workload. 3. Partition by key: repartition("key") hash-partitions by the key, which can benefit downstream operations that use the same key (avoids re-shuffle). 4. After filtering: A filter that removes 90% of rows leaves many small partitions. Repartition to consolidate. 5. Before writing: Control output file count—repartition(n) produces n output files. Cost: repartition() always triggers a full shuffle (network I/O, disk I/O). Use it when the downstream benefit outweighs the shuffle cost. Contrast with coalesce(): coalesce(n) reduces partitions without a full shuffle (merges adjacent partitions), but can only decrease, not increase.

Intermediate Fundamentals 55. When would you choose to coalesce a DataFrame?
Answer: Use coalesce() when you need to reduce the number of partitions WITHOUT a full shuffle. Scenarios: 1. After filtering: A filter removes most rows, leaving mostly empty partitions. coalesce(n) merges them into fewer, fuller partitions without shuffling. 2. Before writing: If you have 200 partitions but want only 10 output files, coalesce(10) avoids the expensive shuffle of repartition(10). 3. Memory efficiency: coalesce doesn't shuffle, so it uses minimal memory and network. 4. Downstream efficiency: Fewer, larger partitions are more efficient for subsequent operations. Key properties: 1. coalesce(n) can only decrease partitions (n < current partitions). If n >= current, it's a no-op. 2. No shuffle: Data is merged within each executor—no cross-network transfer. 3. Uneven partitions: Because it merges adjacent partitions, the resulting partitions may be uneven in size. 4. If you need to increase partitions or redistribute by key, use repartition() instead. 5. In practice: coalesce(1) is commonly used to write a single output file, but be careful—it forces all data through one task (no parallelism, OOM risk for large data).

Intermediate Fundamentals 56. What is a shuffle and why does it impact performance?
Answer: A shuffle is the process of redistributing data across partitions so that all records with the same key end up in the same partition. It occurs during wide transformations: groupBy, join, distinct, repartition, sortBy, window functions. Shuffle mechanics: 1. Shuffle write: Each upstream task writes its output to local disk, organized by target partition. Data is sorted by key, serialized, and compressed. 2. Shuffle read (fetch): Each downstream task fetches its partition's data from all upstream tasks across the network. Data is fetched from every upstream executor that contributed to its partition. 3. Merge/sort: The fetched data is merged and optionally sorted. Why it impacts performance: 1. Network I/O: Data is transferred across the network (all-to-all communication). 2. Disk I/O: Shuffle data is written to and read from local disk. 3. CPU: Serialization, deserialization, sorting, and compression consume CPU. 4. Memory: Shuffle buffers and sort buffers consume executor memory. 5. Stage barriers: Downstream stages cannot start until all upstream tasks complete (synchronization point). 6. Skew sensitivity: Uneven key distribution causes some partitions to receive much more data, creating stragglers. Minimizing shuffle is the most impactful Spark optimization. Use broadcast joins, filter early, use reduceByKey (map-side aggregation), and leverage AQE.

Intermediate Fundamentals 57. How does PySpark handle worker-node failures?
Answer: When a worker node fails (hardware crash, OOM, network partition): 1. Detection: The driver detects the failure via heartbeat timeout (spark.network.timeout, default 120s). The executor on the failed node stops sending heartbeats. 2. Executor marked lost: The driver marks the executor as lost. All tasks running on it are marked as failed. 3. Task retry: Failed tasks are retried on other available executors, up to spark.task.maxFailures (default 4) times. 4. Shuffle data loss: If the lost executor held shuffle output, downstream tasks that need that data get fetch failures. Spark re-submits the entire upstream stage that produced the shuffle data. 5. Cache loss: Cached RDD/DataFrame partitions on the lost executor are gone. They are recomputed from lineage when next needed. 6. Dynamic allocation: If enabled, Spark requests a new executor from the cluster manager to replace the lost one. 7. Block manager: The BlockManager on the driver updates its registry, removing the lost executor's blocks. 8. If enough executors are lost that the application cannot make progress (all retries exhausted), the job fails. In PySpark specifically, Python worker processes on the failed node are also lost; they are restarted on the new executor when tasks are assigned.

Intermediate Fundamentals 58. What is task retry logic in Spark?
Answer: When a task fails (exception, OOM, fetch failure, executor loss), Spark retries it: 1. Retry count: Up to spark.task.maxFailures (default 4). Each failure increments the failure count. After maxFailures, the stage fails and the job is aborted. 2. Different executor: Retried tasks are assigned to a different executor (the driver avoids re-sending to the failed executor). 3. Fetch failure handling: If a task fails because it can't fetch shuffle data (the source executor died), Spark re-runs the entire upstream stage that produced the shuffle data, not just the failed task. This ensures the shuffle data is available. 4. Stage retry: If all tasks in a stage fail, the stage is resubmitted. Multiple stage retries may cascade upstream. 5. Impact on latency: Each retry adds the task's execution time to the total wall time. 4 retries of a 5-minute task = 20+ minutes. 6. When retries indicate a problem: Consistent failures on the same task suggest data skew (one partition too large), bad data (corrupt records), or a code bug (NPE, serialization error). Transient failures (network blip, temporary OOM) are expected and handled by retries. 7. Configuration: Increase maxFailures for flaky clusters. Decrease for faster failure detection in development.

Intermediate Fundamentals 59. What is speculative execution in Spark?
Answer: Speculative execution launches duplicate copies of slow-running tasks on other executors, and takes the result of whichever finishes first. How it works: 1. Spark monitors task progress. If a task is running significantly slower than the median task time (spark.speculative.multiplier, default 1.5x) and at least 75% of tasks in the stage are complete (spark.speculative.quantile, default 0.75), the task is marked as a straggler. 2. Spark launches a speculative copy of the straggler task on a different executor. 3. Both the original and speculative task run concurrently. 4. Whichever finishes first is used; the other is killed. Purpose: 1. Mitigates stragglers: Slow tasks (due to bad hardware, GC pauses, data skew, or network issues) are supplemented by speculative copies. 2. Improves job completion time: Instead of waiting for one slow task, the job finishes when any copy completes. 3. Does NOT fix data skew: If the slowness is due to a large partition, both the original and speculative task will be equally slow (they process the same data). Speculative execution helps with hardware/infrastructure issues, not data distribution issues. Configuration: spark.speculation=true (default false). Use with caution: speculative tasks double the resource usage for straggler tasks. In shared clusters, this can impact other jobs.

Intermediate Fundamentals 60. Why is data locality important for cluster efficiency?
Answer: Data locality means processing data on the node where it resides, minimizing network transfer. Importance: 1. Network I/O reduction: Moving computation to data is cheaper than moving data to computation. Network transfer is typically 10-100x slower than local disk reads. 2. Faster execution: Local reads (PROCESS_LOCAL or NODE_LOCAL) avoid network latency, reducing task time. 3. Resource efficiency: Less network bandwidth used means more bandwidth available for shuffles and other tasks. 4. Lower cost: In cloud environments, network egress is expensive. Data locality minimizes cross-node transfers. Spark's locality levels (best to worst): 1. PROCESS_LOCAL: Data in same JVM as task (fastest). 2. NODE_LOCAL: Data on same node, different JVM or disk. 3. RACK_LOCAL: Data on same rack (network transfer within rack). 4. NO_PREF: Data equally accessible from any node. 5. ANY: Data on a different rack (slowest). Spark waits for a configurable timeout (spark.locality.wait, default 3s) before lowering the locality level. If a PROCESS_LOCAL slot isn't available within 3s, Spark schedules the task at NODE_LOCAL, and so on. For HDFS, Spark uses block location metadata. For cloud storage (S3, ADLS), all data is remote, so locality is less relevant—use Spark caching or Delta caching instead.

Intermediate Fundamentals 61. How do you handle skewed keys in distributed aggregations?
Answer: Skewed keys in aggregations cause one partition to process far more data than others, creating stragglers. Mitigations: 1. Salting: Add a random salt (0-9) to the skewed key, aggregate by (key, salt), then remove the salt and re-aggregate. This splits the large partition into 10 smaller ones. Example: df.withColumn("salt", (rand()*10).cast("int")).groupBy("key","salt").agg(sum("val")).groupBy("key").agg(sum("sum_val)"). 2. Adaptive Query Execution (AQE): Enable spark.sql.adaptive.enabled=true and spark.sql.adaptive.skewJoin.enabled=true. AQE detects skewed partitions at runtime and splits them into smaller sub-partitions automatically. 3. Broadcast join: If the skewed side is small enough, broadcast it to avoid shuffling. 4. Pre-aggregation: Use reduceByKey or aggregateByKey (map-side aggregation) instead of groupByKey. Partial aggregation happens locally before the shuffle, reducing shuffle data volume. 5. Custom partitioner: Use a custom partitioner that distributes the skewed key across multiple partitions. 6. Repartition by another column: If the aggregation doesn't depend on the skewed key, partition by a different column first. 7. Two-phase aggregation: Phase 1: aggregate by (key, salt) to distribute load. Phase 2: aggregate by key to get final results. This two-phase approach is the most general and robust solution for severe skew.

Intermediate Fundamentals 62. How do executors and partitions interact in Spark?
Answer: Executors and partitions interact through task assignment: 1. One task per partition per stage: Each partition is processed by exactly one task, and each task runs on exactly one executor core. 2. Parallelism = total cores: The number of simultaneously running tasks = num_executors * cores_per_executor. If you have 10 executors with 4 cores each, 40 tasks run in parallel. 3. Waves: If partitions > total cores, tasks run in waves. 200 partitions with 40 cores = 5 waves of 40 tasks each. 4. Data locality: Spark tries to assign partitions to executors that already hold the data (cached blocks or local file blocks). 5. Cache: When df.cache() is called, the cached partitions are stored on the executors that computed them. Subsequent actions read from those executors. 6. Shuffle: After a shuffle, each downstream task fetches data from all upstream executors. The shuffle output is written to the executor's local disk. 7. Executor loss: If an executor is lost, all partitions cached on it are lost and must be recomputed. Shuffle data on that executor is also lost, triggering upstream stage re-execution. 8. Dynamic allocation: Executors can be added (when there are pending tasks) or removed (when idle). The external shuffle service preserves shuffle data when executors are removed.

Intermediate Fundamentals 63. Why does Spark use a DAG scheduler instead of a simple loop?
Answer: A DAG (Directed Acyclic Graph) scheduler provides critical optimizations that a simple sequential loop cannot: 1. Pipeline optimization: Narrow transformations (map, filter) are pipelined into a single stage. Instead of reading, mapping, filtering as separate passes, they execute in one pass per partition. 2. Parallelism: The DAG identifies independent stages that can run in parallel (e.g., two branches of a union). 3. Stage splitting: The DAG identifies shuffle boundaries and splits work into stages that can be scheduled independently. 4. Fault tolerance: If a partition is lost, the DAG traces the lineage to recompute only the lost partition, not the entire pipeline. 5. Lazy evaluation: The DAG is built during transformations but not executed until an action. This allows global optimization (Catalyst) to see the entire plan before execution. 6. Data locality: The DAG scheduler knows which partitions need which data and can schedule tasks on nodes with the data. 7. Minimized I/O: By seeing the full plan, the scheduler can minimize shuffles, combine operations, and prune unnecessary reads. A simple loop would execute each operation sequentially, re-reading data for each step, with no parallelism, no fault recovery, and no optimization.

Intermediate Fundamentals 64. How do you reason about the cost of wide transformations?
Answer: Wide transformations (groupB, join, repartition, distinct, sortBy) require a shuffle. Cost components: 1. Shuffle write: Each upstream task writes its output to local disk, sorted by target partition. Cost: O(N) disk I/O where N = data size. 2. Network transfer: Each downstream task fetches data from all upstream tasks. Cost: O(N) network I/O. For a join of two tables of size A and B, the shuffle transfers A + B bytes. 3. Shuffle read: Each downstream task receives, deserializes, and optionally sorts the fetched data. Cost: O(N) CPU. 4. Memory: Shuffle buffers and sort buffers consume executor memory. If data exceeds memory, spill to disk adds more I/O. 5. Stage barrier: Downstream stages cannot start until ALL upstream tasks finish. This is a synchronization point that prevents pipelining. 6. Skew amplification: Uneven key distribution causes some downstream partitions to receive more data, creating stragglers. Reasoning framework: Total shuffle cost = data_size * (disk_write_factor + network_factor + disk_read_factor + cpu_factor). To minimize: reduce data before the shuffle (filter early, aggregate early), use broadcast joins (no shuffle), use bucketing (pre-shuffle), or use AQE (adaptive partitioning).

Intermediate Fundamentals 65. What is the difference between memory-only and disk-backed storage?
Answer: Memory-only storage (MEMORY_ONLY): Cached partitions are stored in executor JVM heap. If memory is insufficient, partitions are not cached (they are recomputed from lineage on next use). Fastest access (in-memory reads). No disk I/O. Risk: if too many DataFrames are cached, evictions occur (LRU), and evicted partitions must be recomputed. Disk-backed storage (MEMORY_AND_DISK): Partitions are cached in memory if space is available; if memory is full, excess partitions are spilled to local disk. On next use, in-memory partitions are read from memory (fast); spilled partitions are read from disk (slower but no recomputation). Guarantees persistence: once cached, data is always available (either from memory or disk). Trade-offs: 1. Speed: MEMORY_ONLY is faster for cached partitions. MEMORY_AND_DISK is slower for spilled partitions but faster than recomputation. 2. Reliability: MEMORY_AND_DISK is more reliable—data survives memory pressure. 3. Resource usage: MEMORY_ONLY uses only memory. MEMORY_AND_DISK uses memory + disk. 4. Use MEMORY_ONLY when: the DataFrame fits in memory and is used frequently. 5. Use MEMORY_AND_DISK when: the DataFrame may not fit in memory, or memory pressure is a concern, or recomputation is expensive. Choose storage level with df.persist(StorageLevel.MEMORY_AND_DISK).

Intermediate Fundamentals 66. How do you avoid excessive recomputation in iterative pipelines?
Answer: Iterative pipelines (ML algorithms, graph processing, iterative joins) re-read the same data multiple times. Without caching, each iteration recomputes from the source, which is extremely expensive. Solutions: 1. Cache/persist: Call df.cache() or df.persist(StorageLevel.MEMORY_AND_DISK) before the loop. The first action materializes the cache; subsequent iterations read from cache. Always call df.unpersist() after the loop to free memory. 2. Checkpoint: For very long lineages (many iterations), call sc.setCheckpointDir("path") and rdd.checkpoint() every few iterations. This truncates the lineage, preventing recomputation from the source on failure. 3. Materialize before iteration: Trigger cache materialization with a lightweight action (e.g., df.count()) before the loop, so the cache is populated and iterations are fast. 4. Broadcast static data: If a small DataFrame is used in every iteration (e.g., model parameters), broadcast it to all executors. 5. Use DataFrames over RDDs: DataFrames benefit from Catalyst optimization and Tungsten, which cache more efficiently. 6. Minimize lineage depth: Avoid chaining many transformations before caching—cache early to keep the lineage short. 7. Monitor cache: Use the Spark UI Storage tab to verify cached partitions and memory usage. If evictions occur, increase executor memory or use MEMORY_AND_DISK.

Intermediate Fundamentals 67. What is the role of the Spark UI in diagnosing job behavior?
Answer: The Spark UI (default http://driver:4040) is the primary diagnostic tool for Spark jobs. Key tabs and their uses: 1. Jobs tab: Shows all jobs triggered by actions. Click a job to see its stages. Use it to identify which action triggered a job and how long it took. 2. Stages tab: The most important tab. Shows stage duration, task count, and task-level statistics (min, median, max duration and data size). Use it to identify: stragglers (max >> median = skew), long stages (bottleneck), failed tasks, and spill (disk spill indicates memory pressure). 3. Tasks within a stage: Click a stage to see individual tasks. Sort by duration to find the slowest. Sort by shuffle read/write to find uneven data distribution. Check locality level to see if tasks ran locally or remotely. 4. Storage tab: Shows cached RDDs/DataFrames, memory usage, and cache hits/misses. Use it to verify caching is working and detect evictions. 5. Executors tab: Shows executor resource usage (CPU, memory, task count, shuffle read/write). Use it to identify uneven workload distribution and executor failures. 6. SQL tab: Shows the DataFrame/SQL query plan with execution metrics per operator. Use it to identify expensive operators (scans, shuffles, joins). 7. Environment tab: Shows Spark configuration, classpath, and system properties. Use it to verify config settings.

Intermediate Fundamentals 68. How do you read a Spark job plan in the UI?
Answer: The Spark UI SQL tab shows the execution plan with runtime metrics. Steps to read it: 1. Open the SQL tab and click on a query. 2. The plan is displayed as a tree of operators (bottom = data source, top = result). 3. Key operators: Scan (reads data from files/tables), Filter (predicate pushdown), Project (column selection), Exchange (shuffle), Sort, Aggregate, Join (BroadcastHashJoin, SortMergeJoin, ShuffledHashJoin). 4. Click on an operator to see metrics: number of rows, data size (bytes), duration, spill size, shuffle read/write. 5. Use the metrics to identify bottlenecks: A Scan with large bytesRead = reading too much data (add filters or use columnar format). An Exchange with large shuffle bytes = expensive shuffle (consider broadcast join or bucketing). A SortMergeJoin with long duration = expensive join (consider broadcast or optimize key distribution). An Aggregate with spill = memory pressure (increase partitions or executor memory). 6. The plan also shows PushedFilters (for Parquet/Delta) and partition pruning. 7. Compare the planned and actual metrics to identify estimation errors (Catalyst estimated 100 rows but actual was 10M = stats issue). 8. Use df.explain(true) in code to see the same plan without the UI.

Intermediate Fundamentals 69. What metrics help you evaluate a Spark job?
Answer: Key metrics for evaluating Spark job performance: 1. Job duration: Total wall time. The primary metric—is the job meeting SLAs? 2. Stage duration: Per-stage time. Identifies which stage is the bottleneck. 3. Task duration distribution: Min, median, 25th, 75th, max. If max >> median, there's skew. 4. Shuffle read/write bytes: Total data shuffled. High shuffle = expensive. Target: minimize. 5. Spill (memory/disk) bytes: Data spilled to disk. High spill = memory pressure. Target: zero or minimal. 6. Input bytes read: Data scanned from source. High input = full scan (no pruning). Target: only needed data. 7. Output bytes written: Data written to storage. Check for small files or oversized output. 8. GC time: Percentage of task time spent in GC. High GC (>10%) = executor memory too small or too many cached objects. 9. Serializer/deserializer time: Time spent serializing data (especially for Python UDFs). 10. Task locality: Percentage of tasks at PROCESS_LOCAL vs. ANY. Low locality = network-heavy. 11. Cache hit ratio: For cached DataFrames, ratio of cache hits to total accesses. Low ratio = evictions or insufficient memory. 12. Executor utilization: CPU usage per executor. Idle executors = over-provisioned. All metrics are available in the Spark UI and can be exported to metrics systems (Prometheus, Datadog) via the Spark metrics API.
